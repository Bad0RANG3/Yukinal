# 架构决策记录（ADR 0001–0070）

这一节是决策记录本身。**代码注释里 `ADR 0004` 这类编号指向的就是下面每一条**；「决定变了就新增一条，并在旧记录里标明被哪一条取代」是这里的规矩，所以有些条目的状态里带着「某节由某条取代」的注记——那是历史，不是笔误。

每条都记三样东西：**决定**是什么、**为什么**是这个形状、以及**代价**是什么。没有代价的决定不值得记，所以代价那一栏从简不了。

## ADR 0001：Agent Runtime 作为独立 Node.js sidecar，由 Rust 拥有其生命周期

`Accepted` · 2026-09-09。**两处已被取代**：「发布成安装包时必须随应用分发受信任的 Node 运行时」由 [ADR 0013](#adr-0013安装包分发随包分发-agent-bundle但使用用户自己的-node) 取代；「当前不自动重启崩溃的 sidecar」由 [ADR 0010](#adr-0010崩溃后的自动恢复有界且只恢复能力不复活状态) 取代。独立进程、stdio 协议、宿主独占原生能力与凭据这些结论仍然有效。

**决定。** Agent 运行时做成独立 Node.js 进程，由 Rust 宿主拥有其启动、通信和退出，不由 React 或用户操作拥有。

**为什么。** Agent 循环需要三样 WebView 给不了的东西：成熟的流式 HTTP 客户端、可快速迭代的工具与 schema 生态、能在运行中途被取消的执行环境。窗口生命周期、进程生命周期与凭据边界若纠缠在一起，界面刷新就会杀掉一次正在等待用户批准的运行。同时 Agent 也不能拥有远程访问能力，否则权限决策退化为「模型说要连，那就连」。

**怎么落地。** React 只调用白名单命令（`agent_spawn`、`agent_status`、`agent_kill`、`agent_logs`、`agent_run_start`、`agent_run_stop`、`agent_approval_respond`），不知道 Node 路径、PID 或 bundle 位置。sidecar 不连 SSH、不访问 SQLite 与凭据库；需要远端数据时发 `host.tool.execute` 或 `host.context.fetch`，这些请求发出前已过 ToolRegistry 与 Permission Engine，宿主收到后**还会再校验一次目标**。

**代价。** 要维护整套额外契约（JSON-RPC 方法、双向请求、schema 校验、跨语言集成测试、进程监督）；发布安装包要处理运行时与 bundle 的绝对路径；帧有界，日志与模型输出必须在各层截断或分页。

**备选与否决理由。** 把 Agent 放进 Tauri WebView（没有 Node 运行时，且让「窗口是否打开」成为前提）；用 Rust 实现整个 agent loop（失去 TS 迭代速度，并把模型协议差异带进原生核心）；由 React 直接派生子进程（多给界面一项系统能力，且进程状态与界面状态耦合）；让 sidecar 自己持有 SSH 与凭据（授权决策失去唯一入口）。

## ADR 0002：SSH 后端采用 russh，并封装在 `SshBackend` 之后

`Accepted` · 2026-09-09。**认证一节已被后续实现取代**：现在还有 ssh-agent、带口令的私钥，以及用户证书认证。选型本身仍然有效。

**决定。** `crates/ssh` 用 russh 作默认实现，通过 `SshBackend` trait 向上层暴露能力，russh 类型不越过 crate 边界。

**为什么。** 不自研 SSH 协议；不调用系统 `ssh` 子进程——那会继承用户的 `~/.ssh/config`、agent 与 known_hosts 行为，导致「同一份配置在不同机器上权限含义不同」。

**具体取舍。** 用 `ring` 而不是默认的 `aws-lc-rs`，因为后者需要每个平台上都有 C 工具链和 cmake，而 `ring` 提供预编译汇编，CI 不必再加一套构建链；保留 `rsa` 特性，因为仍有大量服务器协商 `rsa-sha2-*`。连接与认证整体受 15 秒硬超时约束，会话空闲超时 60 秒，keepalive 间隔由配置决定（桌面端 30 秒，0 表示关闭），keepalive 失败只记录日志。命令执行分两条路径：只读命令允许在传输错误上重连并重试一次；**有副作用的命令必须走 `execute_once()`，不重试**——一次丢失的响应不能变成第二次重启。单条命令输出传输层上限 4 MiB。SFTP 子系统按需惰性建立并缓存在会话里。

**代价。** 需自维护主机密钥策略与自己的 `known_hosts` 文件格式，不能复用用户已有的语义；首次信任模式意味着第一次连接本身就是信任决策；认证覆盖不全（见[当前限制](./limitations.md#当前限制)）；老旧服务器兼容特判必须留在 crate 内部。

**备选与否决理由。** libssh2 绑定（C 工具链与线程模型适配成本高）；调用系统 `ssh` 子进程（见上）；同时支持多种后端让用户选（会让主机密钥、超时、取消出现多套实现，测试面翻倍——等真需要再加，且必须走同一条 trait）。

## ADR 0003：只实现一个 OpenAI-compatible Provider，两种请求方言覆盖兼容端点

`Accepted` · 2026-09-09。**两处已被取代**：「只实现一个 Provider」由 [ADR 0011](#adr-0011增加原生-anthropic-与-gemini-provider身份分支仍只允许发生在装配点) 取代；「`reasoning_delta` 与 `usage` 不会产出」同样失效——两个原生适配器都会发这两个事件，**只有 OpenAI-compatible 这条路确实仍不产出**。「Provider 身份只在装配点分支」与「不做方言自动探测」两条仍然有效。

**决定。** 当时唯一的 Provider 实现是 `openai-compatible.ts`，实现 `LLMProvider`，把不同兼容端点收敛成模型目录与统一的 `StreamEvent` 流；方言由 `wireApi` 选择（`chat` 或 `responses`）。

**为什么。** 协议差异会立刻扩大状态空间与测试面，而且容易顺着调用链渗进权限判断与工具执行逻辑，而这两者都不应该知道上游是谁。绝大多数实际可用端点（OpenAI 官方、OpenRouter、Ollama、LM Studio、vLLM、企业内部网关）都能说一种兼容方言。

**代价。** 兼容方言的差异真实存在（有的网关拒绝 `tool_choice`、有的不接受 `temperature: 0`、有的在流里插空 delta），目前表现为连接失败或空回复；超时与用户取消在事件层表现不同。

**备选与否决理由。** 三个原生 Provider 一次做完（第一阶段风险在权限与执行链路，所以推迟——而 [ADR 0011](#adr-0011增加原生-anthropic-与-gemini-provider身份分支仍只允许发生在装配点) 后来做了）；引入第三方统一抽象库（把上游差异转成第三方库差异，并多一层不可控中间件）；在 loop 里按 Provider ID 分支；把 `wireApi` 做成自动探测（探测失败要发两次真实请求，且让「发出去的到底是什么」不可解释）。

## ADR 0004：内部工具名用点号，Provider 边界用双下划线，映射集中在一处

`Accepted` · 2026-09-09。成本一节「未来接入 MCP 时外来名称必须先被命名空间化并经过冲突检查」**已经落地**，见 [ADR 0014](#adr-0014mcp-接入宿主独占进程与目录agent-只注册与调用)。

**决定。** 内部一律用点号名称（`docker.ps`、`filesystem.read`）；发给 Provider 的名称改为双下划线（`docker.ps` → `docker__ps`）；映射只有一个实现——规则定义在 `packages/shared/src/naming/tool-name.ts`，映射与声明列表由 `packages/provider-sdk/src/name-index.ts` 生成，任何工具实现、Provider 实现或界面代码都不允许手写这套转换。

**为什么。** 多数 function calling 网关对函数名有更严格的字符集与长度限制（常见规则是不允许点号），**静默改写比拒绝更严重**——模型回传一个没见过的名字，若进了日志和审计，调用链就再也无法与真实工具对应。

**可判定性规则。** 内部名称必须是 `namespace.action` 形式，每段匹配小写标识符规则，整体不得包含双下划线；因为各段不允许下划线，`__` 与 `.` 互换无歧义。索引构建时检查两个内部名是否映射到同一个 Provider 名，命中即抛错；注册期有同样的宽松检查。**不猜测**：模型返回未声明过的工具名时返回「未知工具」错误结果而不是模糊匹配；宿主在握手阶段检查冲突列表，只要 sidecar 报告存在名称冲突就拒绝发布这个运行中的 sidecar。名称受 64 字符上限约束。

**代价。** 多一层间接（调试时须记住模型看到的 `docker__ps` 与内部 `docker.ps` 是同一个东西，这层刻意只存在于两个文件里）。

**备选与否决理由。** 内部也用双下划线（命名风格取决于上游网关，审计可读性差）；每个 Provider 各自做转换（规则复制、冲突检查分裂）；网关拒绝点号时自动降级为下划线（映射一旦不确定，审计就不可信）；用哈希作 Provider 侧名称（模型无法从名字推断用途，排障可读性归零）。

## ADR 0005：Permission Engine 是唯一的执行授权决策者

`Accepted` · 2026-09-09。**已知缺口：无。**

**决定。** 风险**事实**可以有多个来源，但只有一个地方能把事实变成**决策**——`PermissionEngine.evaluate()`。

**三层事实。** 工具声明（工具作者声明的静态风险底线）、命令分析（16 条规则）、目标环境的风险下限（本机与开发 `low`、预发布 `medium`、生产与未知 `high`）。合成过程是确定的五步，细节与三档的分工见 [执行与授权模型](./execution-model.md#执行与授权模型)。

**危险档位的加严（已决策）。** 曾经存在一处分裂：引擎命中会话授权时按**内在风险**判断，而执行闸口拒绝任何 dangerous 且非逐项批准的调用；生产环境的风险下限是 `high`，于是任何普通写入都被升级到 dangerous，「在生产目标上批准本会话」会得到一个引擎报自动、执行必然拒绝的决策。收敛方向是**收紧引擎**，三条理由：引擎在更早位置已确立同一不变式，会话授权分支把它重新打开属于自相矛盾；引擎是唯一授权决策入口，它**不能宣布一个执行层会拒绝的批准**——错误的自动批准不可见，而安全的失败（多一次确认点击）是可见的；执行闸口是唯一防线，放宽它等于让未经逐项批准的写入通过。因此会话授权的判断依据是**环境升级后的最终风险**。代价：在生产或未标注环境上，普通写入不再能通过「批准本会话」免除确认。

**代价。** 需维护风险事实与票据两套契约，新增工具必须声明风险、超时和重试策略否则注册被拒；需区分「内在风险」与「最终风险」；未来的团队策略或 RBAC 只能扩展策略来源，不能在其他模块建立第二个授权决策点。

**备选与否决理由。** 每个工具自行判断（规则复制 N 处，无法统一解释）；由 Provider 或模型声明风险等级（模型输出是最不可信的输入，用它决定自己的权限等于没有权限）；只按环境做策略不做命令分析（会漏掉「同一条只读工具被塞进破坏性命令」；误报的代价是一次确认点击，漏报的代价是生产事故）；把审批做成全局开关（一次同意会覆盖它没有涵盖的操作）。

## ADR 0006：sidecar 通过 stdio 上的 NDJSON JSON-RPC 通信，协议版本 1.0

`Accepted` · 2026-09-09。**两处注记**：`capabilities.mcp` 取值为假时的**理由**由 [ADR 0014](#adr-0014mcp-接入宿主独占进程与目录agent-只注册与调用) 取代——取值没变，解释变了；方法面已经扩大，多了 `provider.test` 与 `host.mcp.catalog`。协议版本、帧规则与受理凭证的幂等语义都没变。

**决定。** Rust 启动 sidecar 并持有句柄，双方通过 stdin/stdout 传 NDJSON 编码的 JSON-RPC 2.0。细节（握手顺序、方法表、帧上限、畸形帧、受理表、错误码、转发闸门）见 [架构总览](./architecture.md#架构总览)。

**为什么。** 不需要端口和本机防火墙配置；父进程关闭管道即可发现子进程退出；帧是可读 JSON，冒烟脚本用真实传输跑完整握手；三语言共享同一份定义；双向复用一条流，「Agent 请求宿主」不需要第二套连接或超时模型。

**代价。** 浏览器开发模式无法复用 stdio sidecar；两侧各有一份版本常量须手工保持一致，不一致的后果是启动失败（「半懂协议的组合比启动失败更危险」）；大块内容必须在各层截断；NDJSON 没有 schema 版本协商能力，字段变更只能靠加可选字段或提升协议版本。

**备选与否决理由。** 本地 HTTP 或 WebSocket（端口分配与冲突，并把能执行工具的接口暴露给本机其他进程）；让 WebView 直接连 sidecar（绕过 Tauri 命令白名单）；用 Tauri 自带 sidecar 通道（无法满足双向请求与自定义取消语义，也难在纯 Node 环境测试）；gRPC 或消息包编码（需代码生成与额外运行时依赖，收益只是体积更小）。

## ADR 0007：pnpm 与 Cargo 双 workspace，并优先稳定变化最频繁的边界

`Accepted` · 2026-09-09。**一处更正**：决定里列的 workspace 成员写于 `crates/time` 出现之前，**漏了它**——根 `Cargo.toml` 现在还有 `crates/time`（时间戳的唯一实现）。双 workspace、依赖集中声明、契约库先构建与 fixture 双向校验这些结论不变。

**决定。** pnpm workspace 管 TypeScript 包、Cargo workspace 管 Rust crate，优先把**变化最频繁、被引用最多**的边界固定成可编译、可测试的接口。依赖版本集中声明在根 `Cargo.toml` 的 `[workspace.dependencies]`，内部 crate 以路径引用。`rusqlite` 用 `bundled` 省掉系统 SQLite 差异；`keyring` 启用三个平台的原生后端。

**三条工程规则。** 实现细节只能向内依赖，`crates/*` 的公开类型不含后端库类型（没有 russh 类型出现在 `SshBackend` 之上）；**契约库先构建**——消费方导入 `packages/*/dist/*.d.ts`，本地门禁第一步就是构建它们，之后才做类型检查，顺序不能颠倒；契约在运行时也被校验——每个 Tauri 命令在界面侧用 schema 解析参数与返回值，Rust 侧用对齐的 serde 结构，fixture 被两侧同时解析。

**代价（含两处自我更正，值得原样保留）。**

① 目录与抽象比「一个应用目录搞定」多得多，初期样板与阅读成本更高；② 门禁要覆盖两套工具链和跨语言测试，`pnpm check` 步骤较多，这也是把它做成单一入口并让 CI 跑同一条命令的原因；③ **抽象容易过剩**——`crates/filesystem` 曾长期只有文档注释，既没实现也没被任何 crate 引用，而「远端文件能不能碰」的真实规则同时散落在两个 command 文件里。占位符本身没有价值，价值在于它逼出的问题：**到底谁该拥有这条规则**。它现在有了实现与消费方，成本的准确说法是「先写下边界、再证明它值得存在」这段时间里规则会继续留在错误的地方，而这段时间必须短；④ `Cargo.toml` 里两条目性质不同——`[workspace.dependencies]` 的别名在没人引用时确实惰性，但 `members` 里那条会让它进入 `cargo check --workspace`，所以**新增边界之前要先确认真的有两个以上消费方**；⑤ `packages/shared` 会变成热点，必须保持没有副作用、没有运行时依赖，否则会拖慢每一次构建。

**备选与否决理由。** 每个应用一个独立仓库（跨语言契约会被复制多份）；单一语言实现（纯 Rust 失去 Provider 与工具迭代速度，纯 TS 无法直接操作 SSH、PTY、系统凭据库、SQLite）；只做类型共享不做运行时校验（类型在 JSON 边界上无效）；不做内部抽象让上层直接用后端库类型（后端库升级变成全仓库改造）。

## ADR 0008：Rust 负责 sidecar 的启动、握手、监督与回收

`Accepted` · 2026-09-09。**三处已被取代**：「不自动重启」与「随包分发 Node 运行时」及「`bundle.active` 为 `false`」分别由 [ADR 0010](#adr-0010崩溃后的自动恢复有界且只恢复能力不复活状态) 与 [ADR 0013](#adr-0013安装包分发随包分发-agent-bundle但使用用户自己的-node) 取代。另有一处随之失效：「上一次异常退出的退出码保留到下一次成功启动」——自动恢复落地后该记录只在用户主动启动时清除，自动重启会**刻意把它留下**，界面因此可能同时显示「正在运行」与「上次崩溃过」。

**决定。** 进程与传输归 `yukinal-core` 的 sidecar 模块，状态、日志、单实例和退出记录归同 crate 的 supervisor 模块；Tauri 命令只做参数编组。

**启动顺序是固定的：`spawn → subscribe → initialize 握手 → 发布运行状态`。** 必须先订阅事件再握手，否则握手期间的输出会丢失；握手失败（含协议版本不匹配、工具名冲突）必须关闭子进程，不能发布半初始化的运行状态。解析顺序见 [打包与分发](./packaging.md#打包与分发)。

**生命周期规则。** 一个 supervisor 只保留一个运行中的 sidecar；启动与停止**共用同一把锁**（避免两个并发启动各自看到空槽位、最后留下无人管理的进程）；stderr 保留最近 200 行；sidecar 监听父进程 stdin，父进程消失时主动结束，Rust 正常关闭时先请求 sidecar 退出、`kill_on_drop` 作为兜底；Windows 上以 `CREATE_NO_WINDOW` 启动避免控制台闪窗；**崩溃不会被伪装成「运行完成」**——supervisor 清空运行状态并记录退出信息，界面通过状态轮询发现（运行时 1.5 秒一次，未运行时 5 秒一次）。

**界面看到的是事实，不是推断。** 状态里回报是否在运行、PID、协议版本、Agent 版本、握手时登记的工具数量、**实际启动的入口路径**以及上次退出记录。报告入口路径是有意的：开发机上有多个构建产物时，「到底启动了哪一个」必须能从界面直接读出。

**代价。** 发布安装包时必须提供绝对 bundle 路径；当时 `bundle.active` 为 `false`；不自动重启的代价是崩溃中断用户会话（若做自动重启，必须同时解决「正在等待的审批怎么办」）。

**备选与否决理由。** 由 React 启动子进程；把 sidecar 做成操作系统服务或开机自启（引入安装、升级、权限、生命周期成本，与「桌面应用按需工作」不符）；崩溃后立刻自动重启（重启风暴，且让在途审批与运行状态含义模糊——「先做可见性，再考虑自动恢复」）；把 Node 运行时静态链接进桌面二进制（推迟到真正做安装包时决定）。

## ADR 0009：Agent 权限采用显式的运行级委托

`Accepted` · 2026-09-09。

**决定。** 每次 Agent 运行可在请求里带一个用户选择的委托模式：`ask`（只读自动执行；写入、部署、重启和危险操作执行前等待用户批准，**即使策略表允许自动执行**）、`auto`（用户明确委托 Agent 在**开发或预发布**目标上批准 `write` 档位操作；高危与 critical、本机、未知和生产操作仍需逐项人工批准，策略拒绝仍然拒绝）、省略（保持「只按环境策略执行」）。

**为什么。** 仅按环境策略执行无法同时服务两种真实用法——逐项审查变更，与委托明确任务（「把这个容器重启一下，确认健康后再看日志」）；反复弹确认框只会让人习惯性点批准，反而降低警觉。而放开自动执行又带来「模型输出不能等于授权」的问题：若模型在文本里说「用户已经同意」，协议里必须有东西能证明这句话是假的。系统还需区分三种自动执行理由，否则活动记录无法说明责任落在谁身上。

**委托不是新的授权入口。** `auto` 只让引擎在既有策略之上做一次收窄判断——只有档位是 `write`、目标环境是开发或预发布、且策略本身没有拒绝时，结果才变成自动，且**来源标记为 agent**；其余一律回落 `ask`。

**第二个正交轴。** 运行模式决定这次运行**能改到什么程度**，批准方式决定**允许的部分由谁点头**；两者独立，所以「只做计划 + 自动批准计划里允许的部分」是合法组合。只读与计划模式下的非读操作由引擎直接拒绝，判断发生在策略、委托和会话授权**之前**——限制是被执行的，不是被请求的。

**区分体现在审计而不只是提示词。** 引擎生成带来源的决策，loop 依来源生成三种自动票据，registry 复核自洽性，数据库允许的来源从两种扩展为三种（通过一次表重建迁移完成并保留已有数据）。

**代价。** 需维护票据与决策两套结构的自洽性；两轴增加界面与文档复杂度（必要——合并成一个「权限等级」会让「只读 + 自动批准」无法表达）；**自动委托边界硬编码在权限引擎里，放宽它需要一条新的 ADR 而不是一次配置改动**（有意的防误改设计）；会话授权作用域需 loop 主动维护。

**备选与否决理由。** 只提供「本次运行全部允许」总开关；把委托做成持久化用户偏好（会让授权脱离具体任务与具体目标，而整条审计链都建立在「这次是谁批准的」之上）；让模型在工具调用里声明「用户已授权」；用提示词请求模型遵守只读（提示词不是执行机制，所以只读限制实现在权限引擎里）。

## ADR 0010：崩溃后的自动恢复有界，且只恢复能力、不复活状态

`Accepted` · 2026-09-12。带一段**后续修订注记**：原文说「由下一次启动的 sidecar 收尾为中断」写错了前提——持久化的执行记录只在结果事件到达时写一行，没有任何代码会在调用开始时写「在途」记录，所以崩溃留下的形态是「这一行不存在」而不是「这一行停在 running」。真正要守住的是相反的一条：**别让在途状态被写进账本**，这一点已经实现并有测试钉住。本次**有意没做**的是为在途调用写一行并在崩溃时标记中断——那会让账本重新出现需要收尾的行，而应用自身被杀时同样会留下。

**决定。** 只重启**不是被要求的**退出；重启有界；重启必须留下痕迹；重启只恢复能力、不复活任何状态。

**「只重启不是被要求的退出」的判据是 pid 而不是标志位。** 停止路径在关闭子进程**之前**先取走运行槽位，因此「观察到的退出，其 pid 已经不是当前记录的 pid」只有两种可能——用户要求过，或已有更新的进程顶替了它。用标志位意味着要信任现在和将来每一个调用方都会去设置它；用槽位状态则不需要。这条约束写在代码注释里，并由一条集成测试固定（一次被要求的停止不会被重启）。

**有界策略。** 默认最多 5 次，延迟从 1 秒开始翻倍、上限 30 秒；连续服务超过 60 秒视为新基线（跑几小时后的偶发崩溃不应消耗上次事故留下的预算）；预算用尽后 supervisor **停止尝试**并把这件事写进状态，不静默永远重试；**重启本身失败也消耗同一次预算**（失败的重启不产生退出事件，没有其他机制会注意到它）。

**留下痕迹。** 上次退出记录不被清除（只有用户主动启动才清），界面因此能同时显示「正在运行」与「它是被重启回来的」；状态里的重启记录报告第几次尝试、上限是多少、是否已放弃；stderr 尾部插入**进程代次标记**与重启原因——否则上一个进程的遗言和新进程的开场白会连在一起，而「这一行是死掉的那个进程说的吗」恰好是最需要答案的时候。

**只恢复能力。** 崩溃时在途的每一次运行与每一条审批都随进程消失、不会被恢复；用户看到的是一句「sidecar 已退出，本次运行已中断」，重启后重新发起即得到一条新运行。

**顺带修掉的双重转发。** 事件转发器过去由每次启动创建、并依赖退出事件结束自己的任务，而 supervisor 刻意不转发该事件——于是崩溃重启后会挂上第二个转发器，每一帧被转发两次，**每一个宿主请求都会被「执行两次」**。它现在是窗口级单例。这不是自动重启引入的问题，是自动重启会把它从「偶发」变成「每次崩溃必现」。

**代价。** 崩溃循环会消耗最多 5 次尝试后才停手；重启后的进程是全新的（没有会话记忆、没有待审批请求、没有正在执行的工具）；上次退出记录与重启记录会在自动重启后继续存在；判断「这次退出是不是被要求的」依赖「取走槽位」这一约定，是隐式耦合；重启策略目前是编译期默认值，没有用户可调开关。

**备选与否决理由。** 维持不自动重启（把恢复成本转嫁给用户，而崩溃最常见场景恰是用户正在等长任务时）；无条件重启每一次退出（停止按钮会变成谎言）；把运行状态检查点化、重启后接着跑（「上一个进程执行到哪一步、哪些副作用已经发生」在工具已经发出请求之后无法可靠回答）；由界面负责重启（WebView 与窗口生命周期绑定）；用指数退避无限重试（坏 bundle 会形成后台重启风暴，日志尾部被同一段错误刷满，真正原因反而被挤掉）。

## ADR 0011：增加原生 Anthropic 与 Gemini Provider，身份分支仍只允许发生在装配点

`Accepted` · 2026-09-12。

**决定。** ① `AiProviderKind` 变成真正的多值轴，在所有层同步；② `kind`（谁翻译）与 `wireApi`（同一种翻译里的哪套方言）是两个**正交轴，不合并**；③ 唯一允许按身份分支的地方仍是装配点的 `buildProvider()`，agent loop 继续只认 `LLMProvider` 与 `StreamEvent`；④ 凭据边界不变；⑤ 模型目录按各自协议读取，**目录读取失败不阻止运行**（用户始终可手填 model id）；⑥ 保存与配置路径必须按 `kind` 分派——「一个只能保存一种 kind 的设置页等于实现了一个用户配不出来的 Provider」；⑦ 适配器可以产出 `usage` 与 `reasoning_delta`，消费方必须继续容忍它们缺席。

**为什么（推迟的代价可直接观察，且不是「多一点工作量」）。** 兼容端点只能覆盖请求与响应的**形状**，覆盖不了协议本身表达的东西：Anthropic 把系统提示放在顶层字段、工具调用是内容块、参数以增量分片到达、鉴权是 `x-api-key` 加一个**按日期版本化**的头；Gemini 用 `systemInstruction` 与 `functionCall` part、流式需要 `alt=sse`、而且**不返回工具调用 id**。这些翻译不是可选装饰：写错它们会体现在工具调用能不能闭环、取消能不能及时生效、错误信息是不是可读上。用兼容端点凑意味着用户自己搭代理并承担同样的翻译工作——把问题从我们的代码挪到用户的运维里。

**代价。** 三套方言一起维护，其中两套有会过期的版本化头——升级不是可选项，是一次必须跟随的维护动作；Gemini 不返回工具调用 id，所以同一回合里同名函数被调用两次是协议层面的歧义，实现里必须把这个不对称写在注释与工具结果里而不是假装有 id；新增两类真实失败模式（拒答、缺少终止事件的截断流）；`AiProviderKind` 从单值变多值暴露出一处既有隐式错误——数据库读路径曾忽略 `kind` 列并硬编码 openai-compatible，不修它新 kind 存进去会被读错，因此属于本次改动的一部分而不是后续优化。

**备选与否决理由。** 继续只用兼容端点；只做 Anthropic、Gemini 以后再说（两套翻译不同但同构，一次做两个比分两次便宜，且「另一种 kind」这件事本身需要先被证明架构撑得住）；引入统一第三方多 Provider 抽象库（会把权限、命名映射与错误脱敏这些属于我们的决定交给库的形状）；把 `kind` 与 `wireApi` 合并成扁平枚举；自动探测 dialect 或 kind（探测要花真实请求，且让「到底发出去了什么」无法从配置解释）。

## ADR 0012：主机指纹默认 TOFU，但必须能人工核验、钉住与遗忘

`Accepted` · 2026-09-12。

**背景（能力已经在，但没有出口）。** 存储层能存能查，严格策略能在建立 TCP 之前拒绝未钉过的主机，也能钉住指纹；问题是钉住的动作**全仓库零调用方**——没有命令、没有界面元素，而桌面端唯一的生产配置把策略写死为首次信任，所以严格模式只存在于测试里。最糟的一条是**验证失败时用户看不到该看的指纹**：未钉住的主机报一个占位说明，而「钉住的与出示的不一致」最终表现为一次通用握手失败——一次可能的中间人攻击与一次完全正当的服务器密钥轮换对用户呈现相同，且都没给出新指纹，用户既无法判断也无法接受。

**决定。** ① 默认仍是首次信任，已钉住则按 pin 校验，不一致即拒绝；② **新增三个显式入口**——探针（真的连一次，返回服务器**实际出示**的指纹但**不写入任何东西**）、钉住（把用户确认过的指纹写进 store，这是唯一会写 pin 的用户动作）、遗忘（删除某个 `host:port` 的 pin，下一次连接回到首次信任）；③ 验证失败必须同时给出两个指纹；④ **探针结果在被用户确认之前是不可信的**——界面文案必须写「服务器出示的指纹」而不能写「已验证」，探针不得持久化任何状态；⑤ **不提供「不一致时仍然继续」**——没有「记住并继续」按钮，一次变更只能由用户先遗忘再重新探针确认；⑥ 指纹格式与存储位置不变，存文件不存 SQLite；⑦ **pin 按 `host:port` 关联，不按 server id 关联**（同一台机器在两个条目下必须共用同一条 pin，否则会出现两份互相矛盾的信任状态）。

**为什么不是强制严格模式。** 真实结果是用户到处复制粘贴指纹而不是核验，或者干脆绕开这个应用；而维持「只 TOFU 无出口」的现状更糟——一次合法的服务器密钥轮换会让用户永久无法连接，那种「安全」是假的。

**代价。** 探针会真的发起一次连接并在服务器上留下一次（通常未认证的）连接与日志记录，它不是纯本地操作；首次连接仍然是 TOFU，不加一步确认意味着第一次连接仍可能被中间人利用，**这是接受下来的风险，不是遗忘**；pin 与服务器条目不是一对一，用户可能对「我在一个条目上忘了 pin，为什么另一个条目也放行了」感到意外，必须写在界面文案里；遗忘是危险动作（下一次连接会静默重新首次信任）。探针结果可能被误当成「已验证」，只能靠文案缓解，无法靠机制消除。

**后续注记（未发布）。** 每台服务器现在还可配置显式 host CA、principal 模式，以及本地路径或 HTTPS URL 形式的 OpenSSH KRL。该策略一启用，客户端就同时广告 host-certificate 算法并要求服务器出示证书；普通 host key 会被拒绝，因此不会从 CA 信任降级回 TOFU；KRL 会继续拒绝被序列号、key ID、CA/公钥或指纹撤销的证书。带签名的 KRL 会验证每条签名，并要求至少一条由配置的 host CA 签出；尚未支持独立 KRL 签名者。在线下载只接受无凭据、无 query/fragment 的 HTTPS URL，不跟随重定向或代理，并以 16 MiB 上限失败关闭。未配置 CA 的服务器仍完整保留上面的指纹/TOFU 流程。

**被取代（未发布）。** 上面第 ① 条里「默认仍是首次信任」这一半已由 [ADR 0071](#adr-0071桌面端-ssh-首连不再自动信任主机密钥) 取代：桌面端所有连接入口现在统一要求已知指纹，未知主机在认证前拒绝，核验入口由界面闸门提供。本记录中的探针/钉住/遗忘三个显式入口、失败时并列两个指纹、失败时不得静默接受、pin 按 `host:port` 关联，以及「不提供不一致时仍然继续」全部继续有效；被取代的只是「桌面端默认自动信任」这一个取值。

**备选与否决理由。** 强制严格模式；维持现状；把 pin 存进 SQLite 并按 server id 关联（两个条目会得到两份矛盾 pin，且与已有 `known_hosts` 文件形成两个真相来源）；在不一致时提供「记住并继续」（那是一个把中间人攻击变成一次点击的按钮）。

## ADR 0013：安装包分发：随包分发 agent bundle，但使用用户自己的 Node

`Accepted` · 2026-09-12。

**背景。** 仓库当时**没有安装包**：`bundle.active` 为 `false`，完整图标没有地方引用，没有打包步骤，CI 从不构建桌面应用。当时的形状还有第二个问题：agent 由 tsc 产出并依赖 workspace 包，运行时需要 `node_modules` 在它上面——安装包里没有 `node_modules`，也没有仓库树可供向上查找。

**决定。** ① 启用 Tauri 打包，显式列目标平台与图标；② agent 以**单个自包含 ESM 文件**随包分发，因此安装包里不需要 `node_modules`；③ **不随包分发 Node 运行时**，安装后的应用使用用户系统上的 Node，版本下限与 `engines.node`、esbuild 的 `--target` 一致（Node 24），`YUKINAL_NODE` 仍可把这件事钉死到绝对路径；④ 解析顺序里插入安装包一项，且排在开发兜底之前；⑤ **bundle 在安装包里的位置是契约**，单边改名只会被已安装用户发现；⑥ **缺少 Node 必须是可执行的错误**，但**不做**版本预检；⑦ 本次**不做代码签名、公证与自动更新**——需要本项目并不持有的凭据。

**与早期 ADR 的冲突是知情的。** ADR 0001 与 0008 都要求随包分发受信任的 Node 运行时，这里明确选择不分发：随包分发意味着每个平台一份约 100 MB 的运行时、CI 里每平台一次带完整性校验的下载、以及随之而来的许可与声明义务，而目标用户是开发者、机器上几乎必然已有 Node。ADR 0001 关于「PATH 上的 `node` 可以被替换」的论点被承认为**残留风险**（本应用不是用户自己机器的安全边界；需要钉死的用户可用 `YUKINAL_NODE`）。**这不是永久否决**：当「用户机器上没有 Node」成为真实反馈时应当重新评估，届时本记录要被**取代**而不是被改写。

**代价。** 安装包未签名，是本次留下的最大可用性缺口；「装了但太旧」不会被专门识别（Node 因解析失败退出，用户看到一行语法错误加退出码——不要声称我们能诊断版本过旧）；打包不在本地门禁里，`pnpm check` 保持平台无关、不构建安装包，因此在只装了部分平台工具链的开发机上本地产出的安装包无法被验证——**不能让「配置了」被读成「验证过了」**。多平台构建需要各自工具链，打包工作流是 CI 里最慢也最容易因环境而红的一步。

**后续注记（未发布）。** 决定 ⑥ 中「不做版本预检」已被后续实现取代：正常 Node 路径在启动前执行有 5 秒上限的 `node --version`，低于 24、缺失或输出不可解析都会得到明确错误。`YUKINAL_AGENT_COMMAND` 仍不探测，因为它可能不是 Node。上面的原始决定保留作历史记录；其余关于用户自备 Node、平台签名和安装验证的边界不变。

**备选。** 随包分发受信任的 Node 运行时；把 Node 静态链接进桌面二进制或改用嵌入引擎（前者在 Tauri + Rust 上没有可维护路径，后者不是「打包 Node」而是换掉整个 agent 运行时）；用 Node SEA 之类编译成自包含二进制（仍是实验特性、需按平台各出一份，且会让用户无法用自己熟悉的 `node` 跑同一份代码）；维持不打包（一个装不上的应用不是产品）；只把前端作为静态站点分发（原生能力才是存在理由）。

## ADR 0014：MCP 接入：宿主独占进程与目录，agent 只注册与调用

`Accepted` · 2026-09-12。**一处注记**：背景里「17 个集成测试」这个计数不准，实际是 18 个，跑在同一个已提交的 Node fixture 上——这个数字在记录写下时就已经错了，所以它仍只证明「与 fixture 的行为一致」。**处理注记（未发布）**：最初「拒绝 HTTP transport」的决定已由 [ADR 0016](#adr-0016mcp-streamable-http-只在宿主内实现且凭据不进入-url) 取代；本记录中关于 stdio 进程、目录、权限与来源归属的决定继续有效。

**背景。** MCP 客户端早已存在（进程、握手、工具列表、工具调用、超时、退出记录、stderr 尾部），配置表与 repository 也在，但**没有任何东西把它们连起来**：没有命令读写配置表，没有代码把远端工具变成注册表里的工具，而能力标志必须保持真实。三条既有约束（进程归 Rust、唯一授权决策者、内部名点号分段）决定接入只能有一个形状。还有一件必须在设计期承认的事：**MCP 没有静态工具表**——想知道一个服务器有哪些工具，唯一的办法是把它的进程起起来问它，这让「读取工具列表」成为一个有副作用的操作，而它恰好又是 sidecar 启动时最想要的东西。

**决定。** 九条，逐条与实现对照见 [外部工具（MCP）](./boundaries/mcp.md#边界外部工具mcp)。

**收益。** 可配置、启动、观察、调用一个 stdio MCP 服务器；「Rust 拥有进程」在 MCP 上仍然成立且**只有一个** MCP 客户端实现；一次 MCP 调用的归属在审计里能落到具体服务器；失败带退出码与「不会自动重启」的说明而不是挂住；`http` 被拒绝这件事只有一个来源，界面、命令、目录都复述同一句话。

**代价与限制。** 取消不撤回副作用（线上协议没有取消一次 `tools/call` 的方法）；目录请求会在启动时派生第三方进程（一个启用但从未启动过的服务器会被起起来，因此 agent 启动多了一次最多 4 秒的等待）；`capabilities.mcp` 在握手时可能仍为假（目录必须在 stdio RPC 之后取，否则宿主握手会等一个永远不来的请求）；没有信任评审流程，所以 `trustLevel` 永远停在 `unreviewed`、`allowedTools` 永远是空表——这是当前唯一诚实的状态；结构化归属没有落库；任务管理器强杀仍会留下子进程；**没有真实的第三方 MCP 服务器被验证过**。

**备选与否决理由。** 让 sidecar 直接派生 MCP 进程（会把「谁回收孤儿进程、谁记录退出码、stderr 归谁」变成两个实现）；给 MCP 工具单独一条执行方法（会造出第二条执行通道，取消、审计、目标校验、错误词汇都要写两遍）；在握手之前同步取目录让能力标志一定为真（宿主在握手完成前不会转发 sidecar 请求，这会死锁到超时；要改就得动启动顺序，需要单独一条 ADR）；采信 MCP 工具注解来定风险档位（那是让服务器决定自己的授权级别；注解可作为**展示**信息但不能作为档位来源）；崩溃后自动重启一次（可能重复执行一个已经产生副作用的调用）；支持 `http` 传输并在失败时提示「暂不可用」（出站网络策略还不存在，这不是「暂时不可用」而是一条尚未定义的安全边界；类型层面拒绝比运行期拒绝更早、更难绕过）。

## ADR 0015：Agent 回复用自建的 Markdown 渲染，且不产生可导航链接

`Accepted` · 2026-09-12。决定与代价见 [Agent 回复的 Markdown 渲染](./boundaries/markdown.md#agent-回复的-markdown-渲染)；这里记的是为什么不用现成方案。

**为什么不用 Markdown 库加净化库。** 那套做法是「**默认放过、列举禁止**」：漏掉一条规则就是一个洞，而每加一个语法特性都要重新审视那张净化规则表。把整条「字符串变成标记」的路径去掉，比把过滤写得更好更可靠。仓库自己的解析器只认对话正文需要的那一小撮语法，并且只产出数据结构；渲染层只创建元素，于是没有一张规则表需要维护对错，也没有第二条把不可信文本变成标记的路径。

**为什么链接不可点。** 窗口只申请了 `core:default` 能力，没有 opener/shell，所以 `<a href>` 被点击时不会交给系统浏览器，而是让 webview 自己导航过去——「点一下，整个工作区就没了」。让它可点意味着给桌面端加一条受限于 `http(s)` 的出站通道，而这一版还没有对它的策略；先做到「地址看得见、能复制」是这一步能给出的正确答案。

**备选与否决理由。** 用 Markdown 库加净化库走 `dangerouslySetInnerHTML`（换两个依赖、一张净化规则表，以及一条把字符串变成标记的路径）；只用 `white-space: pre-wrap` 保住换行不做结构化渲染（改动最小，但问题没被解决）；现在就让链接可点（见上）。

## ADR 0016：MCP Streamable HTTP 只在宿主内实现，且凭据不进入 URL

`Accepted` · 2026-09-14。

**背景。** ADR 0014 把 MCP 明确收在 stdio：配置类型拒绝 HTTP，因为当时不存在出站网络策略。后续接入需要覆盖远端 MCP，但把 HTTP 客户端放进 sidecar 会破坏「宿主独占进程、网络与凭据」的边界：agent 将直接持有远端连接、认证材料与重试策略，权限与目标校验也可能被绕过。HTTP transport 本身又比一次简单 POST 复杂：MCP Streamable HTTP 使用 `Mcp-Session-Id`、POST JSON/SSE 回包、可选 GET 事件流、`notifications/cancelled` 和 DELETE 会话终止。

**决定。** ① HTTP 客户端仍在 `yukinal-core::mcp`，由 Rust 宿主持有 client、session、GET stream 与取消任务；sidecar 继续只注册与调用目录中的工具。② 配置必须显式给出 URL；远程 endpoint 只允许 HTTPS，明文 HTTP 仅限回环地址。③ 拒绝 URL 内嵌用户名/密码、查询参数与 fragment，并关闭 HTTP redirect；保存的 URL 不承载凭据。④ 同时接受 POST 的 `application/json` 与 `text/event-stream` 回包，并支持通过 GET SSE 交付响应。⑤ 取消只发送标准通知并停止等待，不承诺回滚；关闭会话会尽力发送 DELETE。⑥ 可配置最多 16 条有序静态认证头，或使用手填 issuer / RFC 9728 protected-resource metadata 自动发现的 RFC 8414 OAuth authorization code + PKCE S256：header 名与 OAuth 元数据写入 SQLite，secret 与 token bundle 只进系统凭据库，并随 POST、GET SSE 与 DELETE 派生认证；client id 留空且元数据声明 registration endpoint 时，以 RFC 7591 注册 `token_endpoint_auth_method: none` 的公共客户端，返回的 client id 写入 SQLite。token 过期前自动刷新，401 强制刷新一次。设备码、client secret 与动态签名不支持。⑦ 改变 transport、command、args、URL 或认证配置会清空旧工具审核；标签变更不会。

**收益。** 远端 MCP 可用，同时保持目标解析、权限、取消、目录与审计仍在宿主的唯一路径上。HTTP 的会话生命周期与 GET stream 不会进入 agent 的提示词或工具实现。明文、内嵌凭据和 redirect 这三类常见泄漏路径在建立连接前就被拒绝。

**代价。** OAuth 只有公共客户端路径：client id 可手填，或由 RFC 7591 动态注册；设备码、client secret 与按请求签名仍不能直接接入。动态注册不保存 registration access token，也不提供后续远程更新或注销。静态 secret 轮换需要用户重新保存配置。HTTP 会话失效不会像 stdio 崩溃那样后台重建，用户必须显式启动新会话。系统代理被刻意关闭，企业网络环境需要用户提供可直连的 endpoint。SSE 长连接的恢复重放也没有实现；断开后当前调用等待超时，后续调用仍可使用同一会话。

**备选与否决理由。** 让 sidecar 直接发 HTTP（把网络、凭据与重试从宿主边界移走）；允许任意 `http://` 远端（明文凭据与响应可被旁路窃听）；在 URL 中携带 token（会进入 SQLite、界面与日志）；跟随 redirect（会把请求和未来认证头带到另一个来源）；把远端 `readOnlyHint` 当授权依据（仍然是让服务器决定自己的权限等级）。

**后续补充（2026-09-15）。** 上面这条决定里的范围声明——「设备码、client secret 与动态签名不支持」——已经过时：设备码（P0-1）与 client secret（P0-2）随后都实现了。决定本身的形状没有改变，也不需要改：客户端仍在宿主内、凭据仍不进 URL、仍不跟随 redirect，新加的两条认证路径仍然走同一个 token 源与同一个刷新点。按请求动态签名仍未实现，它需要单独一条记录。

## ADR 0017：`filesystem.edit` 的替换阶段有守卫，但仍不是 compare-and-swap

`Accepted` · 2026-09-14。决定与代价也写在 [安全与数据边界](./security.md#安全与数据边界) 与 [当前限制](./limitations.md#当前限制) 里。

**背景。** 「先读、按 revision 校验、再写回」听起来像 CAS，但 SFTP v3 里没有任何原语能把它变成 CAS：`SSH_FXP_RENAME` 只保证改名这一步由服务器实现（OpenSSH 映射到 POSIX `rename`，可覆盖既有目标），既没有原子比较并交换，也没有可比较的版本号、inode 或文件锁；SFTP v4/v5 也没有补上。检查与替换之间因此必然存在窗口，而旧实现把它藏了起来：staging 文件创建失败、目标不是普通文件、元数据读不出来，都会**静默退回原位覆盖写** —— 那既不原子，也不比 rename 更安全，只是把「可能被覆盖」从可检测变成了不可检测。

**决定。** 七条：

1. **只有一条替换路径。** 同目录 staging → 守卫复核 → rename；没有退回原位写的分支。远端做不到安全替换时返回**能力错误**（`unsupported`），不换一种更弱的写法继续。
2. **两次守卫。** 内容 revision（读到的原始字节）在读取阶段检查；元数据 guard（`size` + `mtime`，在读取**之后**取）由替换操作在 rename 之前再比一次，不一致就删掉 staging 并报「并发修改」。rename 之后再 stat 一次目标：发布出来的必须就是我们写进去的那一份（大小一致），否则同样报并发修改。
3. **窗口被缩小并被命名。** 它没有被消除：`stat → rename` 之间发生的「同样大小、同一时间粒度」的改写仍然不可检测。这一点写在错误文案与文档里，而不是含糊过去。
4. **硬链接明确拒绝。** `nlink > 1` 时 rename 会让其他名字留在旧内容上。SFTP 属性里没有链接数，所以它由远端 `stat` 探针读取（GNU `stat -c %h`，退回 BSD/macOS `stat -f %l`）；探针不可用时**也拒绝** —— 「无法确认没有硬链接」不是「确认没有」。
5. **symlink 明确拒绝。** rename 会替换链接本身而不是它的目标，那与「编辑这个路径指向的文件」的期望相反。
6. **metadata 逐项保留、逐项复核。** staging 文件在 rename 之前带上目标的 `mode`、`mtime`、`owner`、`group`，然后读回 staging 的属性逐项比对；无法保留时整次编辑失败，错误里点名是哪一项（例如 `owner/group`），而不是笼统地说失败。
7. **ACL 与 xattr 不在承诺范围内。** SFTP v3 既不能读也不能写它们；既不假装保留，也无法检测，所以这条限制写进文档，而不是写成一个「尽力而为」。非 UTF-8 内容照旧按字节搬运（读路径的有损解码只用于显示）。

**收益。** 「被拒绝的编辑不碰文件」这条性质从检查阶段扩展到替换阶段；并发修改从静默覆盖变成一条可区分的失败；不支持的远端、不支持的路径与保不住的 metadata 各有明确的能力错误；`filesystem.edit` 与 `filesystem.write` 的分工变得清楚：前者承诺守卫与原子发布，后者是用户/模型明确要求的覆盖写。

**代价与限制。** 每次编辑多两三个往返（读取后的 stat、staging 属性复核、发布后的 stat），硬链接探针还会多一条远端命令。没有 `stat` 的远端（例如 Windows 上的 OpenSSH）不能使用 `filesystem.edit`，只能用 `filesystem.write`。ACL/xattr 会随新 inode 消失，这一点没有机制能阻止；需要保住它们的文件不该用这个工具。`mtime` 被刻意保留成编辑前的值，所以「文件什么时候改的」不会因为一次编辑而更新。

**备选与否决理由。** 用远端 helper 做真正的 CAS（`renameat2(RENAME_EXCHANGE)` 包装，或自建锁文件）：SFTP 通道不执行命令，要为它多开一条 exec 通道并处理引用、平台差异与失败语义，而任何 helper 都拦不住不遵守约定的写入者（编辑器、构建脚本）；`renameat2` 只在 Linux 存在。用 `SSH_FXP_OPEN` 的 `EXCL` 建锁文件：只能互斥同样遵守约定的客户端，代价是多一个必须回收的远端文件（崩溃就留下垃圾），换不到对任意写入者的保护。保留旧的原位回退：它让「原子」这句话在失败路径上变成假话。rename 之后再用远端 `sha256sum` 复核内容：多一次整文件往返，且仍排除不掉同一窗口内的改写。

## ADR 0018：MCP 的 OAuth 令牌可以绑定到本机密钥（DPoP），但默认仍然只是 bearer

`Accepted` · 2026-09-15。决定与代价也写在 [安全与数据边界](./security.md#安全与数据边界) 与 [当前限制](./limitations.md#当前限制) 里。

**背景。** 现在的 access token 是 bearer：字符串落到谁手里，谁就能用。MCP 的远程端点会把 token 转给别的服务、写进访问日志、经过中间层，而一次泄漏就是长期身份。RFC 9449 的 DPoP（Demonstrating Proof-of-Possession）用一把只存在本机凭据库里的私钥把令牌绑到客户端：每个请求既要出示令牌，也要出示一个只对**这一次请求**有效的 proof（签名的 JWT，声明方法与 URL），服务器还可以用 nonce 挑战要求客户端证明「此刻在线」。代价是这是本仓库第一次自己生成密钥并签名 —— 密码学实现错了比不做更糟，一个「看起来加固了」却仍可重放的 proof 比明说「只有 bearer」更危险。

**决定。** 七条：

1. **Ed25519（`EdDSA`）**，用 `ring` 实现：它已经在构建图里（rustls 用它做 TLS），不引入新依赖；JWK 是 `OKP`/`Ed25519`，公钥 32 字节、签名 64 字节，没有 P-256 那种坐标与 ASN.1 签名的编码面。
2. **每台服务器一把密钥，私钥只进系统凭据库**：数据库里只有 `dpop_key_ref`（与 client secret 同一条规则），设置页只说「已启用/未启用」，从不回显任何密钥材料，`Debug` 里也没有。
3. **默认关闭，开关是服务器级的**：只有用户明确勾选才启用。启用后 token 响应的 `token_type` 必须是 `DPoP`，否则整次连接失败 —— 不降级成 bearer，否则「已加固」就成了假话。切换这个开关等于换身份：已存令牌会被回收并要求重新授权。
4. **每个请求一个 proof**：`jti` 128 位随机、`iat` 取当前时间、`htu` 是去掉 query/fragment 的 URL、`htm` 是大写方法；带 access token 的请求另加 `ath = base64url(SHA-256(token))`（RFC 9449 §7.1）。token 端点请求（code exchange、device 轮询、refresh）也带 proof，但不带 `ath`。
5. **nonce 挑战只重试一次**：401 且带 `DPoP-Nonce`（或 `WWW-Authenticate: DPoP error="use_dpop_nonce"`）时，把 nonce 记进内存缓存（按 origin）并用新 proof 重试**恰好一次**；再失败就是失败。加上「刷新 token 后重试一次」，一次请求最多发三次，任何组合都不会无限循环。
6. **时钟与重放**：proof 的 `iat` 只来自本机时钟，接受窗口由服务器决定；服务器以过期或重放为由拒绝时，我们换新的 `jti` 与 `iat` 重试一次（就是第 5 条那一次），仍失败就报错并说明服务器拒绝了 proof。我们不复用自己的 proof，也不复用 `jti`。
7. **密钥丢失即不可用**：私钥读不出来（换机器、被清理）时，已绑定的令牌已经用不了 —— 直接报「需要重新授权」并回收令牌，而不是退回 bearer。

**收益。** 令牌被复制到别处也换不来请求：proof 绑定方法与 URL，并且（有 nonce 时）绑定服务器当前发的那一个挑战。这把「令牌泄漏 = 身份泄漏」变成「令牌泄漏 = 需要同时拿到本机私钥」。

**代价与限制。** 需要服务器真的验证 proof（不验证的服务器只是多收一个头，客户端无法分辨）；本机时钟漂移会让 proof 被拒；换机器或清空凭据库之后只能重新授权；只支持 Ed25519，遇到只认 `ES256` 的服务器会明确失败而不是换算法重试。这些都是写进 [当前限制](./limitations.md#当前限制) 的公开代价，而不是藏起来的回退。

**备选与否决理由。** 用 P-256（`ES256`）：JWK 要 `x`/`y` 两个坐标，`ring` 的 ECDSA 签名是 ASN.1/DER、还要处理随机数与低 S 归一化，实现面明显更大，而 RFC 9449 两者都推荐。复用 `ssh-key` 里的 Ed25519：它服务于 OpenSSH 的密钥与签名编码，与 JWS 的 JWK/base64url 不是一回事，把私钥在两种格式间搬运只会多一处出错的余地。不做 DPoP：那是目前唯一能把令牌绑到本机的机制，所以做，但默认关闭 —— 多数 MCP 服务器还不支持它。

## ADR 0019：按请求动态签名不实现，先把协议定下来

`Accepted` · 2026-09-15。决定与代价也写在 [当前限制](./limitations.md#当前限制) 里。

**背景。** 有一条需求叫「按请求动态签名」，但它没有说是哪一种：HTTP Message Signatures（RFC 9421）、MCP 专用签名，还是某个网关的自定义方案。签名覆盖哪些组件、`keyid` 怎么指向凭据、canonicalization 用哪一套、时间戳与 nonce 怎么定 —— 每一条都能写出三种互不兼容的做法，而**只有服务器端采用同一套时才成立**：客户端单方面签名等于自娱自乐。

**决定。** 不写占位开关，也不自创一套。要做的前提是：服务端文档明确写出协议与覆盖范围；密钥只从系统凭据库读，模型既不能提供密钥、也不能提供签名头或 canonical request；有一个真实的 socket E2E 能证明签名被服务器接受。在满足这些之前，需要网关自定义签名的用户只能用静态认证头或 MCP 自己的 OAuth。

**收益与代价。** 不引入一个没人验证的自定义密码学协议 —— 一个「签名了但谁都不认」的实现比不签名更糟，因为用户会以为请求已被保护。代价是这类网关目前无法接入。

**备选与否决理由。** 先按 RFC 9421 实现 HTTP Message Signatures：它是目前唯一有标准的选项，但 `components`/`keyid`/`created`/`expires` 仍要服务端逐条约定，`Signature-Input` 的规范化细节也很多；等真的有网关要对接时按它的要求实现，并同样新开一条 ADR。

## ADR 0020：Host KRL 的信任分发仍留在本地静态配置

`Accepted` · 2026-09-15。决定与代价也写在 [当前限制](./limitations.md#当前限制) 里。

**背景。** 现在每台服务器可以保存受信 host CA、最多 8 把独立 KRL 签名公钥，以及本地路径或 HTTPS URL 的 KRL；KRL 的签名链会逐条验证，并且至少一条要由 host CA 或配置的 signer 签署，否则失败关闭（[ADR 0009 一节](./security.md#安全与数据边界) 里写着这些规则）。需求想做的是**远程自动分发新的签名者**。

**决定。** 不加自定义的远程信任分发。理由是它换不来信任，只能把信任搬个地方：任何「从 URL 拉一份新的 signer 列表」都要先回答「这份列表由谁签」，而这个引导问题没有标准答案 —— OpenSSH 自己也只有 `RevokedKeys` 与 `HostCertificate`，没有 trust bundle 协议。轮换已经可以在本地完成：新旧 signer 并存即可。

**如果以后要做，必须同时满足。** bundle 由独立密钥签名或按指纹 pin；带版本号并拒绝回滚；有到期时间；离线缓存有上限且过期即失效；多源冲突时失败关闭而不是「取最新的」；网络失败不影响已有连接的继续使用。这些条件写在这里，是为了下一次不必重新推一遍。

**代价。** 换签名者要人工改配置，签名者频繁轮换的环境需要人工同步；远端自动更新这条便利性没有。

**备选与否决理由。** 「用 host CA 签一份 trust bundle 从远端拉取」：CA 已经能签 host 证书，多签一份列表不增加攻击面，但把「改本地配置」换成「改远端文件」之后，任何能写那个 URL 的人就能加入新的 KRL signer，而 KRL 的意义正是抗撤销 —— 这条等价关系不能接受，除非那份 bundle 有独立的签名密钥（那就回到上面那组条件）。

## ADR 0021：任意二进制附件不内联进消息

`Accepted` · 2026-09-15。决定与代价也写在 [当前限制](./limitations.md#当前限制) 里。

**背景。** 现支持文本、图片、PDF 与音频附件，它们都按字节内联进 sidecar 的 prompt 帧（单帧 8 MiB 上限，图片/PDF/音频共享 5 MiB 原始字节预算）。问题是还要不要支持任意二进制文件。

**决定。** 不支持「任意二进制」。理由三条：一是内联 base64 会让帧迅速塞满，任何有意义的二进制都得先分块或裁剪，那不是「支持二进制」，而是「支持很小的二进制」；二是各 Provider 的文件接口语义不同（OpenAI Files、Anthropic Files、Gemini File API 的生命周期、删除与配额各有一套），跨 Provider 没有一致含义；三是**默认值问题**：把可执行文件与凭据文件自动传给第三方是最坏的默认值之一。

**如果以后要做，必须同时满足。** 走 Provider 的原生上传/远端引用接口而不是内联；明确远端文件的生命周期、删除、重试与清理失败时的行为；默认拒绝可执行文件与疑似凭据文件；在 Provider 之间确实没有一致语义时要明说「不支持」，而不是假装支持。

**代价。** 想给模型看一个 `.zip`/`.bin` 时只能先自己转成文本或图片，或者干脆不发送。

## ADR 0022：系统代理要显式选择，只读平台设置，不执行 PAC

`Accepted` · 2026-09-15。决定与代价也写在 [安全与数据边界](./security.md#安全与数据边界) 与 [当前限制](./limitations.md#当前限制) 里。

**背景。** 宿主侧的每一条出站 HTTP（MCP Streamable HTTP、OAuth 的 discovery 与 token 请求、远端 KRL 下载）现在都是 `.no_proxy()`：行为可预测，但在必须经代理才能上网的环境里就是完全不通，而用户看到的只是一条「连接超时」。另一条路是「跟随系统代理」，但那会把「请求到底去了哪里」变成隐式行为：同一条配置在装了代理的机器上走代理、在别的机器上直连，用户看不出来，日志里也看不出来。

**决定。** 七条：

1. **应用级显式开关，默认直连。** 设置页只有两个选项：**直连**（默认，与现状一致）与**系统代理**。默认值不随机器变化 —— 装上代理软件不会悄悄改变应用的连接路径。
2. **选择系统代理时读哪些设置**，按顺序：环境变量（`HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY`，大小写都认）→ 平台设置（Windows 读当前用户的 `Internet Settings`：`ProxyEnable`/`ProxyServer`/`ProxyOverride`；macOS 读 `scutil --proxy`；Linux 只认环境变量）。读到的来源会显示在设置页上（「环境变量」/「Windows Internet 设置」），因为「用了哪条代理」必须是可回答的问题。
3. **不执行 PAC。** PAC 是一段 JavaScript，要执行它就得内置一个 JS 引擎 —— 那是本仓库不会为了这件事引的依赖。平台只配置了 PAC（Windows `AutoConfigURL` 或 `AutoDetect`、macOS `ProxyAutoConfigURLString` 或 `ProxyAutoDiscoveryEnable`）而没有静态代理时，选择系统代理会**明确失败**并说明原因，而不是静默直连：静默直连正是「绕过公司代理」这件事本身。
4. **代理不改变校验什么。** 代理只改变连接怎么走：endpoint 仍然必须 HTTPS（回环除外）、TLS 仍然端到端、重定向仍然不跟随、`Mcp-Session-Id` 与认证头照旧。代理地址本身也要过同一条 URL 规则（拒绝内嵌凭据、query、fragment），并且**代理不能把请求降级**：经代理访问明文远端的尝试会在建立连接之前被 URL 策略拒绝（与不经代理时同一条规则）。
5. **代理凭据只进系统凭据库**，设置里是只写字段（`user:password`），设置响应只说「有没有」；它只出现在 `Proxy-Authorization` 上，脱敏规则已经覆盖这个头名，错误与日志里没有它。
6. **NO_PROXY 的匹配规则写下来并测试钉住**：逗号或空白分隔；`*` 表示全部直连；条目可以是主机名、`.后缀`、`主机:端口` 或 IP 字面量；主机名按「相等或子域后缀」匹配。我们把这个字符串交给 HTTP 客户端库去匹配（它实现的就是这套语义），并且用一个真实代理 fixture 验证「命中的目标确实没走代理」。
7. **错误要能分辨是谁的问题**：代理连不上、代理拒绝、目标不可达是三条不同的信息，失败信息里点名是代理还是目标，并带上代理的来源（环境变量/平台设置），否则「连不上」这句话在这种环境里等于没说。

**收益。** 需要代理的环境里应用能用；不需要代理的环境里行为一字不变；任何时候都能回答「这次请求走了哪条路」。

**代价与限制。** PAC 用户要么自己在环境变量里写静态代理，要么选直连；代理设置是应用级的，不能按服务器分别配（按服务器配会让「这台机器为什么不通」变成 N 种答案）；平台设置只在**建立连接时**读一次，改了系统代理需要重连（MCP 传输会重启，KRL 下次连接生效）；代理凭据只支持 Basic（`Proxy-Authorization`），不支持 NTLM/Negotiate —— 那是另一套协议栈。

**备选与否决理由。** 默认跟随系统代理：省一个开关，但把「这条请求为什么走那里」变成隐式，与本仓库对网络路径的一贯态度相反。实现 PAC：需要 JS 引擎（依赖体积与攻击面），而且 PAC 的返回可以是任意字符串（`DIRECT`/`PROXY`/`SOCKS`），等于把一条 DNS+JS 的执行结果接到我们的连接路径上。只支持环境变量：Windows 用户绝大多数只在「Internet 选项」里配代理，那样这个功能对他们等于不存在。

## ADR 0023：任务证据先持久化为受限快照，原始写入仍由权限模型控制

`Accepted` · 2026-09-19。

**决定。** 第一阶段引入独立的运维任务、证据、Finding 和决策摘要对象。证据以任务为归属，记录稳定目标、来源工具、采集时间、输入摘要、内容哈希、截断状态和脱敏状态；持久化内容必须是已脱敏且有大小上限的快照。任务的状态、范围、成功条件和预算由宿主保存，不能由模型文本直接改写。Finding 只引用证据 id，决策摘要只引用 Finding 和候选动作。第一版只接入只读采集，不自动执行写入。

**为什么。** 现有工具执行记录回答了“调用发生过什么”，却不能回答“一个长期目标依据哪些资料得出判断”。把证据直接塞进聊天消息会失去来源、截断和范围属性，也会让上下文大小随日志增长。独立对象让 UI、Agent 和审计共享同一条可回查的资料路径，同时允许未来替换 SQLite 原文保存策略而不改变任务语义。

**代价。** 需要维护证据的保留期限、脱敏和大小上限；同一份工具输出会同时有审计摘要和任务证据两个视图；内容哈希只能证明字节一致，不能证明内容本身正确；第一阶段的证据仍受采集工具质量影响。跨服务器任务、自动写入和后台调度暂不纳入这条决定，等任务状态机和恢复语义稳定后再单独记录。

**备选与否决理由。** 只把原始输出存在聊天记录里，无法按任务和时间窗检索，也难以隔离敏感内容；把所有历史输出永久放在 SQLite，会让本地数据无限增长并扩大泄露面；让模型自行维护一份 JSON 事实表，模型就同时成了资料来源和资料裁判，无法由宿主验证范围与完整性。

## ADR 0024：Agent 终态事件只报告任务进度，宿主校验后才更新任务状态

`Accepted` · 2026-09-20。

**背景。** 任务启动时宿主会把任务置为 `investigating`，但 sidecar 是异步运行的：等待审批、完成、停止和失败都可能在另一个事件循环里发生。若只依赖 UI 的内存状态，重连后数据库会永远停在“排查中”；若让模型在文本里写“已完成”，又会绕过任务状态机。

**决定。** 相关 `agent.*` 终态事件携带可选的 `taskId`。Rust 宿主收到事件后查找任务，并用同一份状态转移表决定是否写入 `waiting_user`、`verifying`、`failed` 或 `stopped`；缺失任务、非法状态跳跃和过期事件全部忽略并记录诊断。事件仍照常转发给 UI，UI 不是状态裁判。一次只读排查成功先进入 `waiting_user`，让用户查看证据与决策摘要；任务是否最终 `completed` 由后续验证或明确的宿主命令决定。

**为什么。** sidecar 最了解一次运行何时结束，但不应该拥有 SQLite 或任务边界；宿主拥有数据库和权限规则，才可以把“运行结束”与“目标完成”区分开。携带任务 ID 比在宿主里维护易丢失的 run-to-task 内存映射更适合重连和异步通知，也让事件本身可审计。

**代价。** 旧 sidecar 的事件没有任务 ID 时不会更新任务状态，只保留启动时写入的状态；任务状态可能因此需要用户重新打开并恢复。完成事件不会直接把任务标成 `completed`，需要后续执行/验证阶段接管；这多一步状态，却避免把“模型回答完了”误报成“运维目标已经达成”。

## ADR 0025：任务运行与步骤使用宿主账本，重试前先中断旧运行

`Accepted` · 2026-09-20。

**背景。** 任务启动、sidecar 重启和界面重连可能发生在不同进程或不同时间。只保留一条任务状态无法区分第几次尝试、哪一步停住、错误是否可重试，也无法防止旧运行的迟到事件覆盖一次新的重试。

**决定。** 每个有状态任务运行都在 SQLite 中创建一次 `InvestigationRun`，工具调用映射为有序的 `InvestigationStep`。运行记录保存尝试次数、阶段、检查点、终态和受限失败摘要；步骤保存工具、目标、输入/输出摘要及失败分类。任务保存当前运行 id、预算和上一轮失败。重试前如果发现旧运行仍处于进行中，宿主先把它标成 `interrupted`，再创建新的尝试；只有当前运行 id 的终态事件可以更新任务。重复提交同一 run id 复用已有记录，不再增加尝试次数。sidecar 请求在真正开始前失败时，也要把已登记的运行收束为失败，避免留下永远“排查中”的幽灵任务。

**为什么。** 账本属于宿主和数据库，不依赖窗口是否在线；事件迟到时以任务当前运行 id 做栅栏，能把“旧结果”与“当前结果”分开。预算放在任务上，再以每次请求的较小值传给 Agent，防止 UI 或模型扩大限制。运行和步骤摘要不保存未脱敏的大输出，原文仍走已有证据封套和访问边界。

**代价与限制。** 目前步骤是从工具事件推导的运行观测，还没有完整的计划差异比较；执行、验证和回退 playbook 等待第三阶段。一次任务最多保留受限数量的运行与步骤，长期保留和清理策略另行决定。旧版本 sidecar 不发送任务 id 时不能推进任务状态，但已有运行仍可由用户恢复。

**备选与否决理由。** 只在内存里维护 run-to-task 映射会在重启后丢失；只把每次 Agent 输出存入聊天历史无法进行尝试级别的幂等和迟到事件隔离；让 sidecar 直接写 SQLite 会绕过宿主的范围、权限和审计边界。

## ADR 0026：持久任务的计划门控由宿主执行，调用必须携带计划绑定

`Accepted` · 2026-09-20。

**背景。** 有了持久任务和可替换的调查计划之后，只把计划写进 Agent 的提示词仍然不够：模型可能跳过证据、换工具或在旧计划上继续执行。若仅由 sidecar 自己比较计划，重启、迟到消息或恶意/过时的调用都可能绕过这条约束。

**决定。** 计划修订、当前步骤、允许工具、目标范围、证据前置条件和可解释的精确字符串参数绑定保存在宿主 SQLite。除 `investigation.plan` 和受限的 `investigation.playbook` 外，带 `taskId` 的工具调用必须先通过宿主的 `plan.check`；请求同时带上工具输入，宿主返回 `planId`、`planStepId` 和该步骤的 `evidenceIds`。sidecar 把这些字段原样带入工具请求、`agent.tool_call` / `agent.tool_result` 事件和运行步骤账本，宿主在真正执行前再次核对计划绑定与输入绑定完全一致。缺失、过时、篡改或路径/容器参数不匹配的绑定失败关闭并报告 `binding_mismatch` / `plan_deviation`，不会降级为普通工具调用。工具结果随后由宿主推进步骤、记录尝试次数，并在成功时移动到下一步。

**为什么。** Agent 可以提出计划并根据偏离重新规划，但不能把计划当成授权。把最终比较放在执行宿主一侧，才能同时覆盖远端工具、MCP、sidecar 重启和迟到事件；把绑定写进审计步骤，用户可以从一次真实调用回到它依据的计划和证据，而不是相信一段模型文字。

**代价与限制。** 旧版 sidecar 如果只发送 `taskId` 而没有新绑定，会被拒绝，需要重新启动任务；输入绑定目前只支持有界的精确字符串字段，不是通用 JSON Schema，也不能替代工具自身的参数校验。计划步骤仍是调查/执行的统一序列，完整的部署 playbook、验证窗口和回退流程留到第三阶段。当前测试使用 fixture、受控子进程和 `127.0.0.1`，没有把校园网下不可用的虚拟化网络当作验收条件。

**备选与否决理由。** 只在提示词中提醒「按计划执行」无法形成安全边界；只在 sidecar 中检查无法覆盖宿主重启后的请求；让宿主自动替模型改写计划会把提议变成隐式授权，因此只能通过显式的 `investigation.plan` 或受限 `investigation.playbook` 工具创建新修订。playbook 只生成固定模板的宿主计划，不是绕过门控的第二条执行路径。

## ADR 0027：阶段工件与失败选项由宿主受限持久化，计划步骤声明维护语义

`Accepted` · 2026-09-20。

**背景。** 任务账本能说明运行和工具调用发生过什么，但用户重开任务时仍需要一条短而稳定的路径，理解调查结论、实际影响、验证结果和失败后可以选择什么。与此同时，部署维护步骤不能只保存一个工具名：是否幂等、风险有多高、执行前要看什么、成功如何判断、失败如何回退，都必须在执行前可检查。

**决定。** 引入受限的阶段工件类型：调查计划、基线/证据集、决策摘要、变更计划、执行、验证和失败说明。Agent 只能提交已脱敏、大小受限的工件；宿主再次核对任务、运行、计划绑定和证据引用，再写入 SQLite 并在任务详情中返回。工件是审计和上下文材料，不是授权票据。失败记录可以带有重试、重新规划、等待用户、检查、停止和恢复等结构化选项；选项只描述下一步，用户选择后仍经过任务状态机、权限引擎和高风险审批。

计划步骤同时保存幂等性、风险级别、前置条件、命令/变更预览、验证标准和回退说明。宿主拒绝没有预览或验证标准的写入步骤；高风险步骤必须明确审批；不可安全重放的步骤必须声明回退方案。当前字段允许旧计划继续读取，但新建计划通过同一套校验后才可执行。

**为什么。** 只把这些内容放进模型上下文会在重启、重试和 UI 重连时丢失；只在 UI 展示会让审计与 Agent 使用不同事实；把失败按钮当作快捷授权则会让恢复路径绕过原有边界。由宿主保存受限内容并在接收时核对关联关系，可以让用户看到可回查的阶段记录，同时保持模型、浏览器和 sidecar 都不能扩大任务范围。

**代价与限制。** 工件会增加本地 SQLite 的保留量，内容仍必须遵守脱敏、大小和证据引用上限；当前只完成工件与元数据的持久化和离线验收，还没有一套完整的远端部署、观察窗口或自动回退 playbook。失败选项也不会自动替用户决定重试或变更。基线目前作为工件种类保存，跨任务的长期基线和清理策略留待第三、四阶段。

**备选与否决理由。** 让模型在每轮重新总结：重启后不稳定，也无法证明引用的证据和实际结果。把选项编码成 UI 特例：桌面端以外的恢复入口会失去一致性。允许任意步骤缺少验证和回退字段：会把「能发出命令」误当作「能安全维护」，因此宁可拒绝不完整的新计划。

## ADR 0028：变更基线与验证工件是行动步骤的宿主门槛

`Accepted` · 2026-09-20。

**背景。** ADR 0027 让计划步骤具备预览、验证和回退字段，但这些字段如果只停留在计划文本里，行动仍可能在没有变更前现场的情况下执行，验证也可能只靠模型一句「看起来正常」。第三阶段首先需要一个不依赖远端网络实验室、可以在 fixture 和回环宿主里证明的最小闭环。

**决定。** ① 行动步骤可声明 `requiresBaseline`，宿主在计划检查和步骤成功收束时都要求当前计划存在 `ready`/`succeeded` 的基线工件；② 基线工件必须绑定当前计划、绑定一个证据步骤，并引用至少一份已保存且属于同一任务的证据；旧计划、空证据和由行动步骤自报的基线不能通过；③ 成功的只读工具在证据写入成功后由 Agent 自动产生基线工件，成功的行动与验证分别产生执行/验证工件，内容经过摘要脱敏并受大小上限约束；④ 验证步骤在没有成功验证工件时不能推进；⑤ 不可重试的失败或耗尽重试预算时，宿主先保存阻塞的计划，再保存失败工件、失败分类和失败选项，并把任务置为失败；⑥ 工件是审计材料，不是权限票据，`investigation.artifact` 的记录仍必须经过当前计划绑定、目标和证据范围检查。

**为什么。** 这把「变更前知道什么」「实际做了什么」「做完如何判断」从模型叙述变成宿主可检查的状态。基线引用证据而非任意 JSON，能让验证回到可回查资料；自动阶段工件让重开任务时不必重放工具；验证工件门槛避免把工具成功误报为目标成功。所有路径都可由假宿主、受控子进程和 `127.0.0.1` fixture 验收，不把校园网下不能做的虚拟化网络当作完成条件。

**代价与限制。** 当前的基线是任务内、计划内工件，不是跨任务长期指标基线；自动工件记录失败会让计划步骤失败，但真实工具已经发生的副作用不会因此回滚。还没有通用的 dry-run 变更预览、部署 playbook 执行器、观察窗口或自动回退；回退仍需要另一个经过审批的行动步骤。宿主对 sidecar 提交的证据封套继续依赖既有脱敏契约，未来应把敏感内容校验进一步下沉到统一的宿主边界。

**备选与否决理由。** 只把基线/验证写进提示词：重启和重试后不可证明；允许行动步骤自己提交任意 ready 基线：会把模型自报现场变成执行前置条件；等完整部署引擎写完再做门槛：在更大改动前失去最小可验证的安全闭环；让失败自动触发回退：回退自身可能有副作用，且不能替用户决定影响范围和批准来源。

## ADR 0029：计划审批、观察窗口与持续巡检都由宿主持久化

`Accepted` · 2026-09-20。

**背景。** ADR 0027 和 ADR 0028 已经让计划拥有预览、基线、验证和失败选项，但仍有三处状态不能只放在 Agent 上：用户是否选择了提案、部署后的观察是否真的结束，以及长期巡检是否在应用重启后会重复或漏跑。如果这些状态只存在于提示词或 React 内存里，模型可能把“提出方案”误当成“获准执行”，窗口可能在第一个成功样本后提前完成，调度器也可能在断电后重复同一个周期。

**决定。** ① 宿主接收 `investigation.plan` 时忽略模型携带的审批字段，为行动计划建立 `pending` 的计划审批和 `ChangePlan` 工件；用户从决策摘要选择后，宿主写入 `user` 来源，只有当前计划的 `approved` 状态才允许提案任务进入行动步骤，拒绝或过期计划一律失败关闭。失败选项中的回退只进入重新规划状态，不提供自由格式的回退执行通道。② 观察窗口必须挂在计划最后的验证步骤上；宿主在验证成功后记录开始时间、截止时间和第一条样本，窗口期间只放行声明的只读工具，按间隔接收样本，到截止时间才推进计划，异常则保存失败工件并回到待处理状态。③ 持续巡检由 SQLite 的触发表和运行表表示。触发器只绑定 `readonly` 任务，不能保存 Provider 密钥；事务按到期时间、去重桶、冷却和并发上限原子地产生 claim/skip 运行，运行启动和完成继续使用现有 sidecar、目标校验、计划门控和审计路径；应用启动会把 claimed/running 运行标为 `interrupted`，不自动重放一个不确定的动作。

**为什么。** 三类状态都属于安全边界而不是展示细节。把审批、观察进度和调度幂等键放在宿主数据库，重连、重启和迟到事件就能看到同一个事实；把巡检严格限制为只读，才能在没有虚拟机、容器网络或共享校园网的情况下用 fixture、受控本机进程和 `127.0.0.1` 验收，同时不给后台路径增加写入权限。

**代价与限制。** 当前观察窗口能保证时间、采样间隔和工具范围，但还没有通用指标比较器、异常通知编排或跨任务长期基线；调度器已经持久化 claim、去重、冷却、并发和重启中断，却仍依赖桌面进程运行，不能替代系统级服务。提案审批、观察和调度均未声称真实远端部署能力，外部服务器、Provider 和第三方 MCP 仍需用户单独提供授权后验证。

**备选与否决理由。** 让 Agent 自己把计划标为已批准：模型输出不能改变权限边界；在第一个验证样本后完成观察：无法发现延迟回归或短暂故障；用内存定时器和“启动时直接重跑”：重启会重复不确定的调用，且无法审计跳过原因；让调度器保存 Provider 密钥：会产生绕过现有凭据解析和 sidecar 监督的第二条秘密路径。

## ADR 0030：持续巡检按宿主运行 ID 比较证据，并把变化转成通知与决策摘要

`Accepted` · 2026-09-20。

**背景。** ADR 0029 让调度器能可靠地启动只读任务，但如果证据只挂在任务上，下一轮样本就无法和上一轮严格分开；只比较采集时间也会把重叠运行、迟到事件和用户手动运行混在一起。调度器还需要在没有变化时保持安静，在确有变化时给出可回查的材料，而不是把一段模型文字直接当作告警或变更授权。

**决定。** ① `Evidence` 增加可选的 `runId`，但保存前由宿主用任务当前的活动运行覆盖 sidecar 提供的值；没有宿主运行上下文的旧证据仍可读取，但不能成为持续巡检的样本。② 数据库按运行 ID 计算当前样本的稳定指纹，指纹包含来源工具、工具输入摘要、证据种类、截断状态和脱敏内容哈希，不包含采集时间和随机证据 ID。首轮记为 `baseline`，指纹相同记为 `no_change`，不同记为 `changed`，没有证据记为 `insufficient_evidence`。③ `changed` 由宿主创建受限证据集工件、低置信度 Finding 和两个保守决策选项：继续有限只读复核，或等待用户要求新的 dry-run 方案；两者都不能直接扩大写入权限。④ 通知由已保存的 `silent`、`on_change`、`always`、`failed_runs_only` 策略决定，事件只携带有界的 ID、结果和摘要，UI 通过共享事件 schema 校验后展示。

**为什么。** 运行 ID 是宿主已有的迟到事件隔离边界，重启和并发条件下仍能把样本归属到一次真实运行；稳定指纹让“无变化”不受时间戳和行 ID 干扰。把差异变成 Finding、工件和决策摘要，用户可以回到具体证据并选择下一步，同时不会把异常检测误写成根因证明或自动变更授权。所有比较、通知和素材生成都可在 SQLite、fixture、受控 sidecar 与 `127.0.0.1` 范围内验收。

**代价与限制。** 指纹是变化候选，不是语义根因分析；动态日志、排序不稳定或证据截断会造成需要人工复核的变化。当前通知是桌面事件，不是系统级推送；调度器仍依赖桌面进程存活，长期基线清理、更多可配置 playbook 和真实外部目标仍未验证。

**备选与否决理由。** 只按任务最近 N 条证据比较会混入不同运行；只依赖模型自报的 `runId` 会让模型能伪造样本归属；变化后自动执行修复会把观测结论变成未批准的写入，因此必须先落 Finding、工件和决策摘要，等待用户重新选择。

## ADR 0031：持久任务可以由宿主直接启动 Agent

`Accepted` · 2026-09-20。

**背景。** 任务对象和调度器已经能保存目标、范围与运行账本，但用户创建一个目标后仍必须打开聊天面板、重新组织一段提示词，才能让 Agent 开始工作。这使“设置任务目标后自主推进”退化成普通聊天入口，也让只读排查无法在任务页直接启动。

**决定。** 增加宿主拥有的 `investigation_task_start` 入口。它只接受持久化任务 ID，由宿主读取目标、完成标准、目标范围、运行模式和权限模式，生成有界的任务启动提示词，再复用现有 `agent_run_start` 的 provider、凭据、sidecar、计划门控和运行幂等路径。只读任务创建成功后可以直接自动启动；计划/目标任务仍需用户在任务页明确启动，行动步骤继续经过计划选择与逐项审批。已有活动运行或终态任务拒绝重复启动。

**为什么。** 任务目标应是可恢复工作的第一类入口，而不是聊天文本的别名。把启动提示词和安全包络由宿主拼接，避免 UI 或模型自行扩大范围；复用单一运行入口则避免后台任务和用户运行产生两套权限、凭据或恢复语义。

**代价与限制。** 自动启动只解决“开始工作”的入口，不代表模型已经具备通用部署 playbook；完整的远端写入、验证和回退仍由计划、审批和现有工具能力限制。自动启动没有伪造聊天历史，任务运行和证据账本是权威记录；校园网验收仍只使用 fixture、受控进程和 `127.0.0.1`。

**备选与否决理由。** 只把目标填入聊天草稿仍要求人工发送，不能称为自主任务；另写一套调度专用启动器会绕过已有 `agent_run_start` 的凭据和状态收口；让 Agent 自己决定目标或权限会把用户任务变成未绑定的自然语言授权。

## ADR 0032：首批部署 playbook 只生成固定模板的宿主 dry-run 计划

`Accepted` · 2026-09-20。

**背景。** 计划步骤已经能声明基线、幂等性、风险、预览、验证和回退，但让 Agent 每次从自然语言重新拼接这些字段，仍会造成形状漂移，也无法在校园网约束下稳定验收。另一方面，直接实现通用远端部署执行器会同时扩大写入、回退和真实目标验证的范围。

**决定。** sidecar 增加 `investigation.playbook`，只接受五个有界模板：只读健康检查、受保护配置编辑、容器重启、systemd 服务重启、apt/dnf 包安装；首批模板要求任务已有明确的远程服务器目标。工具根据任务的宿主解析目标生成固定顺序的 `evidence`、`decision`、`action` 和 `verification` 步骤，并把行动步骤标成需要基线、明确预览、验证标准、回退说明和用户批准；随后通过与 `investigation.plan` 相同的 `host.recordPlan` 保存。工具本身不调用远端写入，不接收自由命令，也不接收可扩大任务范围的目标；真实工具调用仍经过计划绑定、目标校验、Permission Engine、审批和阶段工件路径。标准形状之外继续使用显式 `investigation.plan`，无法安全表达时停在等待用户。

**为什么。** 固定模板把最小可执行语义从提示词移到了可测试代码，同时不把模板生成误报成部署完成。每个模板都能在假宿主、受控进程和 `127.0.0.1` fixture 中检查步骤顺序与风险元数据；配置编辑仍依赖 `filesystem.read` 的 revision，容器重启仍是 high-risk 且不可被永久记住的动作。后续可以在不改变计划门控的前提下逐个增加模板。

**代价与限制。** 这不是通用编排器：包安装目前只覆盖显式 apt/dnf、包名和可选精确版本，仍没有真实远端部署、服务重载、文件备份、自动回退、更多包管理器或任意命令串联。所有 action 仍要用户逐项批准，失败只生成现场和回退建议，不会自行反向操作；模板适用性也必须由 Agent 根据证据判断。长期基线、更多 playbook 和外部目标仍未验证。

**备选与否决理由。** 让模型自由生成任意 playbook 会把命令、目标和回退边界重新交给不可信输入；直接实现“全自动部署”会把校园网下未验证的远端能力写成现状；只做 UI 里的预览又无法让宿主在重启后复核计划。因此先采用固定模板 + 宿主 dry-run，扩大范围时逐项新增契约和 fixture。

## ADR 0033：计划步骤绑定宿主可解释的精确工具参数

`Accepted` · 2026-09-20。

**背景。** ADR 0026 已经把工具名、目标、计划修订和证据集纳入宿主门控，但仅绑定工具名仍留下一个具体缺口：同一个 `filesystem.edit` 可以把计划中的路径换成另一个路径，同一个 `docker.restart` 也可以把计划中的容器换掉。模型工具 schema 能验证“参数形状”，却不能证明参数仍属于用户选择的那一步。

**决定。** 计划步骤可以声明最多 8 个有界的精确字符串 `inputBindings`。宿主在保存计划时限制字段和值长度；`plan.check` 接收本次工具输入，且真正的 `host.tool.execute` 再次要求每个绑定字段都是同名字符串并与计划完全相等。首批固定 playbook 为配置文件步骤绑定 `path`、为容器步骤绑定 `container`；没有绑定的旧计划保持兼容，但新增计划可以按同一规则逐步增加绑定。绑定失败使用既有 `binding_mismatch` / `plan_deviation`，不执行工具，也不把请求降级为普通调用。

**为什么。** 这把“计划写了哪个具体对象”落实到宿主，而不是留在提示词、UI 或 sidecar 内存里；同一比较函数覆盖预检查和最终执行，能防住重启、迟到请求和 sidecar 被篡改后的参数漂移。精确字符串足以覆盖路径、容器名等首批高风险范围字段，又不会为了通用表达式引入一套未经验证的 JSON Schema 解释器。

**代价与限制。** 绑定是精确相等而非通用约束语言，不能表达数值范围、集合或跨字段关系；工具自身仍必须继续做路径、revision、容器引用和权限校验。旧计划没有绑定时不会自动获得更严格的对象约束，因此创建新 playbook 时必须显式填入需要保护的字段。验收继续使用 shared schema、Rust 宿主单测、假宿主和 `127.0.0.1`，不要求校园网下的虚拟化网络。

**备选与否决理由。** 只把路径和容器名写进 `purpose` 或 preview 无法形成执行边界；让 Agent 自己在 sidecar 比较会在宿主重启或迟到调用时失效；直接支持任意 JSON Schema 会扩大宿主解释器和资源上限的攻击面，因此先采用有限的精确字符串字段。

## ADR 0034：证据保存后把宿主生成的 ID 回传给模型

`Accepted` · 2026-09-20。

**背景。** Agent 在只读工具成功后会由 sidecar 自动生成并保存证据，但宿主响应原本只有 `recorded: true`。下一轮模型看得到工具结果，却不知道这条证据的持久化 ID；它若自行猜一个 ID，Finding 或决策摘要会被宿主拒绝，若不引用则无法形成可回查的证据链。

**决定。** 证据保存成功时，Agent 将已经通过脱敏、哈希和范围校验的 `evidence.id` 写入同一工具调用的下一轮模型消息。模型可以据此把真实 ID 放进 Finding 和决策摘要；宿主仍再次验证所有引用属于当前任务，sidecar 不获得绕过校验的权限。内存假宿主验收覆盖证据、Finding、决策摘要、执行、验证和失败工件的完整链路。

**为什么。** 返回宿主已经生成的 ID 是最小的跨轮上下文补充，不需要让模型访问 SQLite、把完整证据塞进提示词或引入第二套 ID 分配器。引用仍以宿主为最终裁判，重启和迟到调用不会因为 sidecar 记住一个临时映射而改变归属。

**代价与限制。** 工具消息多一个有界 ID，但不携带原文；如果证据保存失败，模型只会看到失败并必须停下或重新调查。当前 fixture 只证明本地假宿主和回环边界，不能替代真实远端部署、网络故障或第三方 Provider 验证；宿主目前也不会自动把新证据 ID 回写成计划步骤的前置证据，复杂计划仍需显式重规划。

## ADR 0035：恢复事务必须关闭旧运行留下的未完成步骤

`Accepted` · 2026-09-20。

**背景。** 任务恢复会把仍在 `admitted`、`running` 或 `waiting_user` 的运行标记为 `interrupted`，并清空任务的 `active_run_id`。此前步骤账本没有同步收口：工具已经停止，时间线却还能看到 `running` 或 `pending` 的旧步骤。重开任务时这会制造“旧步骤仍可能继续”的错误暗示，也让新一轮恢复和旧账本之间缺少明确边界。

**决定。** `recover_task` 在同一个 SQLite 事务里处理运行、步骤和任务三张表。属于该任务且仍为 `running`/`waiting_user` 的步骤改为 `failed`，引用同一份有界的恢复失败对象并写入 `ended_at`；尚未开始的 `pending` 步骤改为 `skipped`，不伪造失败；已成功、已失败或已跳过的步骤保持不可变。只有事务全部提交后，任务才进入 `investigating`/`recovery`，等待新的 run 或明确的用户选择。

**为什么。** 恢复的语义是“旧运行已经停止，准备一条新路径”，而不是把旧运行的半开步骤留给下一轮猜测。共享时间戳和失败分类让用户能把任务失败、运行中断和具体未完成步骤对应起来；事务保证应用崩溃不会只写一半。所有行为可在 SQLite 重启测试中验证，不需要虚拟机、容器网络或真实远端。

**代价与限制。** `InvestigationStepStatus` 没有新增 `interrupted` 枚举，因此正在执行的步骤以 `failed` + `TaskFailureCode` 表示，UI 仍需通过运行状态和失败内容区分“动作失败”与“被恢复中断”；尚未开始的步骤显示为 `skipped`。这只关闭账本，不会也不应回滚已经发生的远端副作用；真正的回退仍须另一个经过计划、基线和审批门控的行动步骤。

**备选与否决理由。** 只中断运行、不改步骤，会留下悬挂的活动记录；把所有步骤都标为失败会把从未执行的步骤写成事实；增加新枚举虽然语义更细，但会扩大跨语言契约和迁移面，而当前恢复可由已有失败分类清晰表达。

## ADR 0036：计划 ID 只允许幂等重放，不允许携带新定义复用审批

`Accepted` · 2026-09-20。

**背景。** 计划审批属于某一组具体的工具、目标、输入绑定、预览、验证和回退元数据。宿主之前只用 `plan.id` 判断是否是同一修订；如果不可信 sidecar 重新提交同一个 ID，却替换了路径、容器名或行动描述，旧的 `approved` 状态可能被带到新定义上。计划表的同 ID 更新本来是为了抵抗重复投递，不能变成修改已批准内容的通道。

**决定。** 宿主把计划分成“定义”和“运行时状态”。定义包含任务、步骤 ID/顺序、允许工具、精确输入绑定、目标、风险、基线、前置条件、预览、验证、回退、证据和尝试上限，以及观察窗口配置；步骤状态、尝试次数、时间戳、偏离记录、当前步骤、审批和观察样本属于宿主运行时状态。同 ID 重投只有在定义结构相等时才幂等，并恢复宿主已保存的运行时状态；定义变化必须使用新 ID，产生新的修订并重新进入 `pending` 审批。一个已存在但已被旧修订占用的 ID 不能重新打开。

**为什么。** 这让重复消息安全，同时让审批真正绑定到用户看过的计划内容。精确字符串绑定和目标校验继续在 `plan.check` 与实际执行前各跑一次；计划 ID 比较只是更早的一层防止“换内容保审批”。定义比较使用结构化 JSON，忽略字段顺序但不忽略任何影响执行的字段。

**代价与限制。** 计划定义变化需要 Agent 生成新 ID，数据库会保留旧修订作为审计记录；不能用同 ID 做“局部编辑”。这仍然不是远端部署能力，也不会替用户自动批准新计划。当前验收在 Rust 宿主单测中覆盖同 ID 重放保留进度、输入绑定变化被识别，真实外部目标仍未验证。

**备选与否决理由。** 只比较计划 ID 会让批准票据可被重写；每次重投都强制新 ID 会让网络重试丢失运行进度；让 sidecar 自己比较会在宿主重启或被篡改后失效。因此保留同 ID 幂等语义，但只对宿主比较过的不可变定义开放。

## ADR 0037：中断恢复使旧审批、基线和观察窗口失效

`Accepted` · 2026-09-20。

**背景。** 运行在工具调用或观察采样期间断开时，宿主无法证明远端是否已经发生了副作用，也无法证明目标身份、文件 revision 或服务状态没有变化。若恢复只重新启动 Agent，却继续接受旧计划的 `approved` 状态和 `ready` 基线，重试就可能把不确定的现场当成原来的现场。

**决定。** 用户选择任意非 `inspect` 的恢复路径后，宿主先把当前计划的审批写回 `pending`，保留计划定义和步骤历史但不保留批准票据；属于该计划且状态为 `ready`/`succeeded` 的基线工件标记为 `superseded`；运行中的观察窗口改为 `cancelled` 并记录原因。失败详情带 `requiresFreshBaseline`，宿主启动提示词和 sidecar 上下文都明确要求重新核对目标身份、重新收集只读证据、重新生成或确认计划，并在新的基线和本轮审批前禁止重放行动。只读调查仍可在新的证据步骤中继续。

**为什么。** 这是对不确定副作用的保守收口：旧记录保留用于审计，新的执行路径必须经过当前现场、当前范围和当前审批。把失效状态写入宿主数据库而不是只写提示词，能在 sidecar 重启和 UI 重连后保持一致；观察窗口取消也避免把旧样本算进新的完成判断。

**代价与限制。** 每次中断后的变更恢复都需要重新采集基线和重新选择方案，可能增加往返；这不会自动回滚已经发生的副作用，回退仍必须是新的计划和审批。目标身份的真实远端验证仍依赖用户提供已授权服务器；当前验收只覆盖 SQLite/假宿主/回环路径。

**备选与否决理由。** 直接沿用旧审批和基线会把“可能已执行”误当成“未执行”；只在提示词里提醒而不改数据库会被迟到调用绕过；自动回退则会扩大未经用户确认的影响范围。因此选择可审计的失效标记和重新门控。

## ADR 0038：新计划的运行时进度由宿主初始化

`Accepted` · 2026-09-20。

**背景。** `InvestigationPlan` 同时携带声明性步骤和运行时字段。若宿主保存新计划时照抄 sidecar 提供的 `currentStepId`、步骤状态或尝试次数，模型可以把行动步骤伪装成已经通过调查，绕过前置证据和顺序门控。计划审批解决的是“是否允许这份定义”，不能替代宿主对执行位置的裁决。

**决定。** 新计划 ID 通过定义、目标、证据和元数据校验后，宿主覆盖其运行时字段：第一步为 `running`，其余步骤为 `pending`，所有尝试归零，结束时间和偏离记录清空，当前步骤指向第一步，计划状态为 `active`，时间戳由宿主生成。只有同一 ID 且定义结构完全一致的幂等重投，才从数据库恢复已有的运行时状态；定义变化必须使用新 ID。

**为什么。** 计划的顺序和前置条件由宿主拥有，sidecar 只提出声明。这样即使首条消息被重放或带有伪造的“已成功”字段，行动也必须从证据步骤开始；数据库中的步骤账本与计划状态保持同一事实来源。

**代价与限制。** 计划工具不能用同一 ID 携带人工编辑的进度，恢复进度要依赖宿主的步骤结果；模型输入中的时间戳只作为提议，审计使用宿主时间。此决定不证明真实远端执行，仍需经过基线、计划审批、权限票据和验证。

**备选与否决理由。** 只校验 `currentStepId` 是否存在仍允许跳过前置步骤；让 sidecar 自己维护尝试计数会在重启和重复投递时漂移；每次都拒绝重投会损坏正常网络重试。因此只允许定义相同的幂等恢复，其余运行时状态统一由宿主初始化或恢复。

## ADR 0039：已保存证据取回与阶段工件不推进远端计划

`Accepted` · 2026-09-20。

**背景。** 任务上下文需要允许 Agent 按 ID 取回之前保存的脱敏原文，模型也可能在一次远端调用后主动保存阶段工件。两者都属于本地调查记录：证据取回没有新的目标观测，工件保存也不是新的远端动作。如果把它们按普通只读工具处理，证据取回会被再次包装成一条现场证据，阶段工件还会让宿主把当前远端步骤提前推进或重复推进。

**决定。** sidecar 对 `investigation.evidence` 不发起远端计划检查，不自动生成新的 `Evidence`，也不提交 `plan.step_result`；宿主仍通过任务 ID 和证据 ID 做范围校验。`investigation.artifact` 继续携带当前计划绑定并接受宿主校验，但不会因为工件记录而提交步骤结果。真正读取服务器、文件、日志或容器的成功结果才进入自动证据封套；Finding、DecisionBrief、Plan 和 Artifact 的返回值只保留在各自领域对象中。

**为什么。** 这保留了“证据 = 一次有来源的目标观测”与“工件 = 对阶段状态的摘要”之间的语义边界，避免重复样本污染持续巡检比较，也让 Agent 能在计划执行中回看原文而不必把计划步骤改成允许一个额外的伪观测工具。远端步骤仍只能由其声明的真实工具完成并由宿主推进。

**代价与限制。** 证据取回本身不会刷新远端状态；若旧证据已经过期或恢复流程已使其不再适用，Agent 仍必须重新采集并遵守新的计划与基线要求。模型主动记录的工件不会替代自动执行/验证工件，重复记录可能覆盖同 ID 内容但不能扩大目标范围。当前验收使用内存假宿主和 `127.0.0.1`，不代表外部目标验证。

**备选与否决理由。** 把所有 `read` 结果都自动保存成证据会把内部元数据和重复取回混入现场样本；让 artifact 工具推进计划会使提示词要求的“记录工件”变成隐式状态转移；完全禁止取回则迫使模型重复读取远端，增加无意义调用和风险。因此采用显式的元工具边界，并让真正的步骤结果仍只来自计划绑定的目标工具。

## ADR 0040：宿主对可能产生副作用的工具实行持久化调用幂等

Accepted · 2026-09-20。

**背景。** sidecar 通过 stdio 请求宿主执行远端工具。响应可能在远端动作完成后、回到 sidecar 前丢失；sidecar 重启、事件转发重连或调用方重投时，如果只靠“上一次没有收到结果”判断，就会把文件写入、容器重启、systemd 服务重启或第三方 MCP 调用再执行一次。filesystem.edit 的 revision 保护只能覆盖一种文件并发情形，不能替代调用级的重投判断。

**决定。** ① 宿主对 filesystem.write、filesystem.edit、docker.restart、systemd.restart、package.install 和所有 mcp.* 调用，以 (traceId, callId) 为精确重投键，在真正执行前向 SQLite 写入一次 running 占位，并保存不含原文的请求 SHA-256 指纹；唯一键和数据库临界区保证并发事件只能有一个执行者。绑定持久化任务计划的调用还保存去除 provider 身份后的逻辑动作指纹，因此 sidecar 重启后即使生成新的 callId，只要仍是同一计划步骤和同一参数也会被挡住。② 相同键且指纹相同的请求，在桌面进程仍持有有界内存响应时重放原响应；没有响应、状态为 running 或状态为 uncertain 时返回 plan_deviation/duplicate_call，要求先核对目标，绝不再次执行。指纹不同的同键请求直接拒绝。③ 明确的成功或确定性参数/策略失败会写入终态并可在当前进程缓存；传输、超时、取消、宿主协议错误和行动执行失败都标为 uncertain，因为它们不能证明远端没有副作用。④ SQLite 只保存调用元数据、指纹和状态，不保存文件内容或 MCP 原文响应；桌面进程重启后的缺失响应按失败关闭处理。

**为什么。** 这把“是否已经尝试过这个具体动作”从 sidecar 内存和 UI 连接状态提升为宿主事实。数据库占位先于 SSH/SFTP/MCP 调用，能防住并发重投；不缓存不确定结果则避免用一次看似可重试的错误覆盖真实现场。读工具仍保持原有重试语义，第三方 MCP 按可能产生副作用处理，因为远端声明的注解不能降低宿主风险。

**代价与限制。** 桌面进程重启后，同一调用不会自动返回原输出，用户或 Agent 必须通过新的只读核对/新 call ID 判断现场；这比盲目重放更保守。调用账本当前不提供独立 UI 列表，工具结果事件和任务审计仍是用户看到的主路径；跨任务长期清理策略和通用幂等键协议仍待后续设计。该闭环用 SQLite、假宿主和回环 fixture 验收，不宣称真实外部网络或部署环境已验证。

**备选与否决理由。** 只在 sidecar 内存里记住 call ID 会被 sidecar 重启抹掉；只在工具返回后写审计行会错过“执行后响应丢失”的窗口；把完整响应写进数据库会把敏感远端内容变成第二份持久化副本；遇到不确定结果自动重试会把安全边界交给网络时序，因此选择宿主持久占位、有限重放和不确定即停。

## ADR 0041：活动运行栅栏拒绝停止/恢复后的迟到事件

`Accepted` · 2026-09-20。

**背景。** sidecar 的通知和宿主的停止、恢复、重试请求经过同一条异步通道，旧 run 的帧可能在宿主已经把它标记为 `interrupted`、或任务已经换到新的 `active_run_id` 后才抵达。此前终态收口只在最终化分支检查活动 run，迟到的 `agent.completed`、`agent.failed` 或审批事件仍可能先把当前任务推进到错误阶段，甚至把已恢复的旧 run 改回完成。

**决定。** ① 宿主同步任务状态前必须确认事件 `runId` 等于任务当前的 `active_run_id`；没有活动 run 或属于旧 run 的事件直接丢弃。② 事件持久化前确认 `taskId`（若携带）与持久化 run 的任务归属相同。③ `completed`、`failed`、`cancelled` 和 `interrupted` 的 run 都是不可重新打开的终态，任何后续 sidecar 帧不再改变它；旧 run 和已完成步骤仍保留用于审计。④ 当前活动 run 的正常事件顺序不变，最终化仍在任务活动 run 栅栏下清空 `active_run_id`。

**为什么。** 运行 ID 是宿主已经用于重试隔离和调度证据归属的事实边界，把它同样用于事件接收可以让“停止/恢复”在异步传输下保持单调。恢复后重新采集、重新审批的要求不会被旧连接的一个迟到完成帧绕过；丢弃旧帧不会损失可审计信息，因为旧 run、失败原因和步骤账本都已持久化。行为可以在桌面 Rust 单测、SQLite 恢复测试和受控 sidecar fixture 中验收，不需要虚拟机或网络共享。

**代价与限制。** 迟到帧被丢弃后不会自动补写新的运行结果，用户必须查看旧 run 或重新启动当前任务；这对可能已经发生副作用的场景是有意的保守选择。真实外部目标、断网时序和第三方 Provider 仍需单独授权验证，不能由本地 fixture 代替。

**备选与否决理由。** 只在最终 `agent.completed` 分支检查 run 会留下中间状态倒退窗口；按事件时间戳覆盖任务会把不可信 sidecar 时钟变成裁决；让 React 过滤迟到帧无法保护 SQLite 或后台调度。因此由宿主以活动 run 和终态状态双重拒绝，保持旧记录只读。

## ADR 0042：用受限操作序列扩展部署 playbook，而不是接受自由命令

`Accepted` · 2026-09-20。

**背景。** 现有 `investigation.playbook` 能生成单一配置编辑或单一容器重启的 dry-run 计划，但一个常见维护目标往往需要“先读配置、应用精确改动、再重启服务并验证”的连续动作。直接让模型把 shell 命令串塞进计划，会绕过现有目标校验、参数绑定、幂等账本和逐项审批；只增加一个更大的自然语言模板又无法保证步骤顺序。

**决定。** `investigation.playbook` 增加 `deploy_sequence` 形状。输入最多四个有界操作，每项只能是带绝对路径的 `edit_file`、带受限容器引用的 `restart_container`、带 `.service` 后缀的白名单 `restart_service`，或显式 apt/dnf、包名和可选版本的 `install_package`；工具自动生成服务器基线、每项只读前置证据、Finding、决策摘要、逐项行动和逐项验证。行动继续绑定精确 `path`/`container`/`service`/`manager`/`package`/`version`，配置编辑要求 revision，容器、systemd 重启和包安装保持 high-risk；systemd 重启前后分别由 `systemd.inspect` 读取状态，包安装前后由 `package.inspect` 读取状态。所有写入仍由宿主的计划门控、Permission Engine、调用幂等账本和审计路径执行。模板不接收自由命令、任意 unit、任意包管理器或任意回退文本，也不会在生成计划时执行远端操作。

**为什么。** 这把“多个已知安全动作的顺序”变成可执行、可审计的计划，同时保留宿主对每一步的最终裁决。多步骤 fixture 可以证明证据—决策—审批—编辑—重启—验证确实串联，失败时计划停在具体步骤而不是把整段 shell 当成一个不可解释的副作用。它在校园网限制下可用内存假宿主验收，不把真实远端部署伪装成本地测试已经证明。

**代价与限制。** 操作集合目前覆盖配置精确编辑、Docker 容器重启、systemd `.service` 重启和 apt/dnf 包安装，最多四项；本决定本身没有定义 systemd 重载、自动回退、更多包管理器或任意命令执行。文件编辑的受限备份/恢复后来由 [ADR 0043](#adr-0043文件备份与守卫恢复只由宿主决定路径) 单独加入。每个行动仍需独立审批，验证失败不会自行反向操作；更多操作必须增加独立的输入绑定、目标校验和 fixture，而不能把 `deploy_sequence` 放宽成脚本解释器。

**备选与否决理由。** 让模型生成 shell 脚本会把目标范围和回退边界重新交给不可信输入；把两个现有模板简单拼接会漏掉跨动作的基线、审批和验证关联；一次性实现通用编排器会扩大未经验证的执行面。因此先采用有限操作代数，沿用现有计划执行器，逐项扩展。

## ADR 0043：文件备份与守卫恢复只由宿主决定路径

`Accepted` · 2026-09-20。

**背景。** 配置编辑已经有 revision 守卫和原子发布，但验证失败后只有一段“另行规划反向编辑”的文字。让 Agent 自己拼接备份目的地或用自由命令复制文件，会重新打开路径越界、覆盖旧备份、符号链接和部分复制的风险；把恢复自动接在失败后，又会把另一项有副作用的变更变成隐式授权。

**决定。** ① 新增 `filesystem.backup` 与 `filesystem.restore` 两个宿主拥有的文件工具。backup 只接受一个已通过 Agent 路径策略的远端绝对路径，宿主生成 32 位小写十六进制随机 token，并据源路径哈希派生同目录备份名；Agent 不能提供 destination。② backup 只处理普通、单硬链接、大小不超过 512 KiB 的文件，复制前后复核 stat 和完整字节，使用 SFTP `CREATE|EXCLUDE` 独占创建，任何失败都删除不完整副本；成功后只把服务器、目标路径、revision、任务归属、来源调用和生命周期写入本地 SQLite，不写入远端原文。③ restore 先要求宿主账本中存在同一服务器、同一目标路径和同一任务（或同一无任务会话）的 `available` 备份，再接受与目标路径匹配的备份和调用方给出的当前 `expectedRevision`；目标或备份发生 drift、不是普通单链接文件、路径不匹配、账本不存在或 revision 过期时失败关闭。发布沿用受保护的同目录 staging/replace 路径，并复核最终字节数与 revision；成功后账本把该备份标记为 `restored`，不允许第二次消费。④ backup 是 medium-risk 且必须在编辑 playbook 中单独审批；restore 是 high-risk，永远逐项用户批准，拥有自己的计划步骤和持久化调用幂等键。⑤ 备份不会自动清理，验证失败不会自动 restore；回退仍须生成新的计划、重新绑定现场并重新审批。

**为什么。** 目的地和生命周期由宿主掌握，模型只能选择“备份这个已绑定路径”，所以不会把一条看似合理的 `cp` 变成任意写入。完整复制和独占创建避免了“成功返回但备份只有半份”以及覆盖旧恢复点；restore 的双重 revision/路径守卫把“恢复旧内容”限制在用户仍确认的当前现场。逐项审批和幂等账本让 backup/restore 与既有 write/edit/restart 共享同一条权限、审计和不确定结果收口。所有行为可用内存假传输、受控 SFTP fixture 和 `127.0.0.1` 验收，不把校园网下未做的真实远端回退宣称为完成。

**代价与限制。** 512 KiB 上限、单链接和可读 stat 会排除大文件、硬链接、符号链接以及部分 Windows OpenSSH 目标；账本目前只登记备份并在恢复后消费，远端备份文件仍需要用户或后续显式清理，长期保留策略尚未设计。SFTP 没有 compare-and-swap，stat 守卫与发布之间仍有并发窗口；不确定结果不会自动重试。自动回退、备份清理/轮换、目录快照、ACL/xattr 保留和真实外部目标仍未验证。

**备选与否决理由。** 让 Agent 接受任意 destination 会扩大写入范围；调用远端 `cp`/shell 会绕过 SFTP 路径和审计边界；失败后自动 restore 会在用户未重新确认影响时执行第二个高风险动作；把备份内容放进 SQLite 会制造敏感远端数据的第二份持久化副本。因此选择宿主派生路径、独占创建、显式高风险恢复和保守停机。

## ADR 0044：备份清理必须命中宿主账本并复核内容

`Accepted` · 2026-09-20。

**背景。** 备份账本已经能证明某个恢复点由本机宿主创建，但长期保留同目录副本会留下用户不再需要的敏感配置。让 Agent 直接调用文件删除，或仅凭看起来像备份的路径清理，会把恢复保护变成任意删除能力。

**决定。** 新增 `filesystem.backup.cleanup`。调用方必须提供目标路径、宿主生成的 `backupPath` 和备份创建时返回的 `expectedRevision`；宿主先在 SQLite 账本中查找同一服务器、同一目标和同一任务（或同一无任务会话）的 `available` 记录，再由文件服务确认备份是普通单链接文件、完整读取后的内容摘要仍与账本一致、读取期间没有 stat 漂移，最后删除该精确路径。成功后账本状态变为 `deleted`，同一记录不能再次清理；工具是 medium-risk，仍要经过计划、权限和调用幂等门控。

**为什么。** 路径归属和内容摘要同时成立，才能把“清理我刚才创建的恢复点”与“删除远端任意文件”区分开。清理不读入 SQLite 的远端原文，也不自动插入编辑 playbook；用户或后续显式计划决定何时放弃恢复点，验证失败仍保留它供另行审批的 restore 使用。

**代价与限制。** SFTP 没有 compare-and-delete；stat/读取与删除之间仍有竞争窗口，远端权限或连接中断会留下 `available` 记录，需要用户重试或核对。若远端删除成功而 SQLite 更新失败，宿主返回需要 reconcile 的内部错误，不会猜测可以安全重试；自动清理、轮换策略和目录级保留策略仍未实现。

**备选与否决理由。** 在验证成功后静默删除会把 medium-risk 的数据丢失隐藏在另一项行动之后；按时间扫描同目录会接受非本机创建的文件；把备份正文复制进数据库会扩大敏感数据留存。因此只提供账本绑定、内容复核和逐项批准的单文件清理。

## ADR 0045：证据新鲜度是宿主按策略计算的响应投影

`Accepted` · 2026-09-20。

**背景。** 证据已经有宿主采集时间，但任务页和 sidecar 只能看到一个时间字符串。模型容易把昨天的服务状态当成当前事实，用户也无法从摘要快速区分“刚采集”“仍可参考”和“必须重采”。把状态永久写进证据行会让时钟推进后数据过期却仍保留旧结论，也会给不可信的 Agent 一个伪造新鲜度的入口。

**决定。** 宿主在任务详情、`host.context.fetch`、`investigation.evidence.search` 和单条 `investigation.evidence` 取回时，按 `default-v1` 和主机时钟动态附加 `freshness`：采集后不超过 900 秒为 `fresh`，超过 900 秒但不超过 86,400 秒为 `stale`，更久为 `expired`；无法解析或晚于评估时刻的时间戳为 `unknown`。响应同时带 `policy`、`evaluatedAt`、`ageSeconds`、两个边界和必要的原因。SQLite 仍只保存原始采集时间，记录请求中的同名字段会被忽略，sidecar 上下文和桌面界面都把 stale/expired 明确标为历史资料。

**为什么。** 新鲜度是“在何时看这条证据”的事实，不是证据正文的一部分；动态投影避免迁移、定时清理和时钟漂移写放大，也让同一条证据在不同展示时刻得到可解释的状态。固定策略 ID 和返回边界让用户能审计阈值，`unknown` 比把坏时间戳猜成新鲜更安全。当前只做可见性和提示，不把一条通用 TTL 偷换成所有工具都适用的行动授权；需要把新鲜度变成计划前置条件时必须另做门控决定。

**代价与限制。** 900 秒和 24 小时是保守的通用默认，并不等于所有日志、配置或指标的业务有效期；暂时不能按工具或任务声明不同 TTL。评估依赖本机时钟，时钟回拨会保守地产生 `unknown`/较小年龄而不是伪造远端事实。stale/expired 不会自动删除或阻止所有行动，Agent 必须遵守上下文提示并在变更前重新采样；真实外部时钟和远端目标仍未在校园网环境下验证。

**备选与否决理由。** 永久存一个 `expiresAt` 会在采集时猜业务有效期并在时钟推进后变成陈旧事实；让 Agent 自己填状态会把提示词变成安全裁决；按展示层各自计算会造成 UI、sidecar 和审计解释不一致。因此统一由宿主计算、返回策略元数据，仍把最终行动授权留给计划/权限门控。

## ADR 0046：停止确认先封存 durable run，再接受迟到终端帧

`Accepted` · 2026-09-20。

**背景。** `agent.run.stop` 的 sidecar 响应只是“取消已被接受”，最终 `agent.completed` 可能在另一条异步通道稍后抵达；如果桌面在两者之间崩溃或连接重连，任务账本会继续显示运行中，旧终端帧也可能与新一轮恢复竞争。单靠 sidecar 的最终帧无法给宿主一个及时、可重放的停止事实。

**决定。** 当 `agent.run.stop` 收到 `stopped: true` 时，宿主构造一个仅供内部账本使用的完整 `agent.completed`/`cancelled` 形状，先经过现有任务状态同步和运行持久化路径，立即把当前 durable run 写成 `cancelled`、任务写成 `stopped` 并清除 `active_run_id`；调度运行也沿同一终态路径收尾。后到的真实 `agent.completed`、`agent.failed`、审批和工具帧由活动运行栅栏与终态检查拒绝。`stopped: false` 或非 durable chat run 不改变任务账本。

**为什么。** 复用现有终态路径比为停止再开一套“强制写数据库”逻辑更容易保持失败分类、步骤收口和调度通知一致；`active_run_id` 在宿主侧先清空，才能让停止、恢复、重连和 sidecar 重启共享同一条迟到事件边界。完整内部事件形状也保留了未来统一校验的空间，而不会把一个只有 `state` 的半事件误送给 UI。

**代价与限制。** 这只是运行栅栏和审计收口，不是远端回滚：取消确认前已经提交的写入、或宿主/协议无法中断的在途动作仍需新的只读核对和独立回退计划。若宿主在 sidecar 已接受取消后自身持久化失败，用户仍要通过任务恢复/重开路径检查现场；当前实现不会猜测远端是否成功。合成事件不替代 sidecar 的真实文本和工具结果，UI 仍会优先收到真实终端帧（若它能抵达）。

**备选与否决理由。** 等待最终帧会留下长时间的假运行；直接让 UI 把按钮变灰不能保护 SQLite 或调度器；把停止升级成自动回退会扩大未经用户确认的副作用。因此只提前封存宿主账本，保留旧 run 作为审计记录，并把真正回退留给新的计划与审批。

## ADR 0047：持续巡检变化只触发下一轮有限只读复核

`Accepted` · 2026-09-20。

**背景。** 持续巡检已经由宿主比较相邻成功运行的证据指纹，并在 `changed` 时保存低置信度 Finding、证据集工件和决策摘要。但下一次调度运行仍只收到泛化的“收集证据”提示，模型可能重复采集无关数据，也可能把上一次差异误读成当前事实；异常本身更不能成为写入授权。

**决定。** 调度器在启动下一次只读运行前，由宿主根据上一轮 `last_outcome` 生成有界提示。`changed` 要求 sidecar 先用 `investigation.evidence.search` 查看相邻样本摘要，再在同一任务范围内采集当前只读证据，只有新样本仍支持变化时才记录新的判断；`baseline`、`no_change` 和 `insufficient_evidence` 分别得到建立基线、安静复核或补齐证据的提示。提示只改变调查重点，不改变目标、工具目录、预算、计划门控、Permission Engine 或任何权限票据。

**为什么。** 这让调度异常可以自动进入一条有限的纠偏调查，而不用把自然语言差异直接升级成维护动作。旧证据先按 ID 检索并由宿主比较无正文差异，当前状态再由真实只读工具采集，能把“历史变化”和“当前事实”分开；仍沿用原有 run、证据、Finding、决策摘要和通知账本，所以桌面重启、重复 claim 和迟到事件不会产生第二条隐式执行路径。

**代价与限制。** 复核仍在下一次保存的调度间隔运行，不会因为一次差异无限递归地启动新 run；它只会收集只读证据，不会自动规划或执行变更。模型可能仍无法解释跨来源的根因，用户需要从新的 Finding/决策摘要选择后续方案；真实外部目标、自动回退和长期基线清理仍未验证。

**备选与否决理由。** 直接在比较为 `changed` 时自动执行写入会越过用户选择和计划审批；立即创建无上限的 follow-up run 会让异常形成调度风暴；继续使用泛化提示则无法保证模型查看相邻样本。因此先采用宿主生成、预算不变、只读且在下一周期生效的复核提示。

## ADR 0048：证据比较只返回宿主计算的有界差异

`Accepted` · 2026-09-20。

**背景。** 持续巡检已经能用证据指纹发现相邻运行不同，但指纹只能回答“变了没有”。如果每次解释变化都要求 Agent 取回两份完整日志、配置或快照，提示词会变大，也容易把跨来源、过期或截断的资料误读成当前事实；如果让 sidecar 自己读取 SQLite，则会绕过任务范围和脱敏边界。

**决定。** 新增只读的 `investigation.evidence.compare`。请求必须带当前 durable task 和两条真实 `evidenceId`；Rust 宿主先确认两条证据都属于任务且目标范围完全相同，再在宿主内比较已保存的脱敏正文。JSON 只返回最多 64 条变化路径和有界变化计数，文本只返回行数及位置无关的增删/变化计数；同时返回两条证据的元数据、新鲜度、来源/种类差异和截断警告，不返回原始值。比较不写 SQLite、不生成新的 Evidence、不推进计划步骤，也不能成为行动授权。

**为什么。** 变化路径和行数足以让 Agent 判断“需要看哪类证据、是否要重新采样”，而不用把整份资料送进上下文；范围检查和新鲜度仍由唯一宿主裁决。明确的 64 路径、10,000 计数、8 层 JSON 深度、4,096 个比较节点和 100,000 行文本上限，使比较结果可预测，也保留显式单条取回原文的选择。

**代价与限制。** 通用差异无法证明根因，JSON 路径不携带值，文本计数不识别插入位置；截断或 stale/expired 证据仍然只能产生候选解释。该工具只覆盖任务内两条证据，不是跨任务基线或长期语义关联器；真实外部目标、自动回退和长期清理仍未验证。

**备选与否决理由。** 让 Agent 直接取回两份正文会增加上下文和泄露面；只比较哈希无法解释变化；让宿主自动生成 Finding 或变更计划会把观察升级成判断/授权。因此先采用无正文、同范围、有界且不改变任务状态的比较契约。

## ADR 0049：决策选项的续接意图必须显式且默认等待用户

`Accepted` · 2026-09-20。

**背景。** 任务已经可以保存决策摘要并让用户选择方案，但选择后的行为此前只停留在数据库记录，用户还要另行启动任务；反过来，若让标题、说明或模型文本推断“继续”，旧摘要和普通候选动作就可能意外触发新一轮 Agent。需要把“选择”和“继续哪条安全路径”分开表达。

**决定。** `DecisionOption` 增加可选的 `continuation`：`continue_readonly` 表示同一任务的有界只读复核，`start_plan` 表示在该用户选择已经写入宿主计划审批后启动下一轮任务，`wait_user` 表示保持等待，`stop` 表示不启动。宿主在 `investigation_brief_select` 中从已保存选项读取该字段，缺失值归一化为 `wait_user`，并把归一化结果放进响应；桌面端只有前两种值才调用既有 `investigation_task_start`，不会创建第二条启动路径。终态 run 会在调度通知发出前先清空任务的 `active_run_id`，避免用户选择与旧 run 收口竞争。自动续接不改变目标、预算、计划、Permission Engine 或高风险逐项批准。

**为什么。** 继续意图成为跨语言、可审计的白名单字段，用户选择后任务可以真正沿统一 durable run 入口继续，旧数据也安全地保持等待；宿主返回的值而不是 UI 的本地猜测避免了陈旧选项和多客户端漂移。省略即等待把兼容和失败路径都收口到最保守的默认值。

**代价与限制。** 该闭环只解决“用户选择后是否启动下一轮”的编排，不代表 Agent 自动批准写入、回退或删除；任务启动仍可能因活动 run、预算或 sidecar 状态失败，失败交给原有任务错误路径。`stop` 目前只禁止自动启动，停止/恢复仍使用专门的任务命令；真实外部目标和校园网外的部署没有因此变成已验证能力。

**备选与否决理由。** 让 UI 根据选项标题猜动作会被自然语言和旧数据绕过；让宿主无条件在选择后启动会把等待补证据或停止选项误当成继续授权；在选择命令内复制一套 Agent 启动逻辑会绕过统一的 run admission。因而保留显式白名单、宿主归一化和既有启动入口。

## ADR 0050：决策摘要的 `stop` 续接由宿主封存任务

`Accepted` · 2026-09-20。

**背景。** 决策摘要选项已经能声明 `continue_readonly`、`start_plan`、`wait_user` 或 `stop`。此前界面只对前两种值启动新运行，选择 `stop` 虽然不会启动，却没有改变任务状态；用户仍可能看到“等待选择”，也可能在选项点击和迟到 sidecar 帧之间留下活动运行。

**决定。** `investigation_brief_select` 由宿主解释 `stop`：如果当前有活动 durable run，先复用 `agent.run.stop` 的 sidecar 取消与合成终态事件路径；sidecar 未确认或活动运行栅栏仍存在时返回错误，不猜测已经停止。若运行已经由正常终态封存，或本来没有活动 run，宿主按任务状态机把任务置为 `stopped` 并写入完成时间。任务详情页的 `investigation_task_stop` 复用同一个 helper，并对已停止任务保持幂等；完成、失败或过期任务直接拒绝。选择 `stop` 不会把摘要关联的计划审批写成 `approved`；其它选项保留原有计划选择行为，是否启动仍只看显式续接枚举。

**为什么。** 停止是任务生命周期事实，不是“没有点击启动”的 UI 偶然结果。复用同一取消 fence 可以让活动 run、迟到帧、调度收尾和 Agent 面板停止按钮保持一致；把计划批准与终止分开，避免用户明确放弃任务却留下可执行的审批痕迹。没有 sidecar 或已经完成的 run 仍能通过 SQLite 终态路径收口，便于重开应用后解释状态。

**代价与限制。** 宿主只能确认 sidecar 取消和本地账本封存，不能撤销已经提交的远端副作用；真实外部目标仍需新的只读核对与独立回退计划。选择选项与停止是同一 IPC 调用中的有序写入，不提供跨进程事务，若 sidecar 停止失败，选项选择会保留但任务不会被伪装成已停止，用户可重试或回到 Agent 停止入口。该路径继续只用本地 SQLite、sidecar fixture 和 `127.0.0.1` 验收。

**备选与否决理由。** 只让 React 在选择后调用通用状态更新会留下 sidecar 继续消耗资源并让迟到帧缺少统一 fence；直接把所有任务标记为 stopped 会在取消失败时制造假终态；把 `stop` 当成计划批准会污染后续恢复授权。因此由宿主在选择路径上复用取消、终态与计划审批边界。

## ADR 0051：证据关联只做宿主拥有的确定性元数据对齐

`Accepted` · 2026-09-20。

**背景。** 任务已经能够按来源检索证据、比较两份样本的无正文差异，并按宿主运行 ID保存持续巡检样本。但健康、服务、容器和日志仍常常以并列摘要出现，Agent 容易重复读取，或者把“同时出现”直接写成根因。没有运行 ID 的历史证据也需要一个有限的回查入口。

**决定。** 新增只读的 `investigation.evidence.correlate`。请求必须带当前 durable task 和一个真实 `anchorEvidenceId`；宿主先确认锚点属于当前任务且目标范围完全相同。锚点有 `runId` 时只读取同一运行的证据；旧证据没有 `runId` 时才允许使用默认 300 秒、上限 3600 秒的采集时间窗。响应只投影证据摘要、`same_run`/`time_window` 匹配方式、去重后的来源工具和最多 8 条新鲜度/截断/无匹配警告，限制最多 64 条，绝不返回正文、不写数据库、不推进计划或授权。Agent 必须继续用真实证据 ID 取回正文，并把关联当作排查线索而非因果结论。

**为什么。** 运行 ID 是宿主已有的并发和迟到事件边界，优先级高于模型猜测的时间关系；时间窗回退只服务于旧数据，而且有硬上限和明确的匹配标签。把关联放在 Rust 宿主做，可以同时复用任务范围、新鲜度和脱敏边界，减少提示词重复，却不会把一个简单的共时关系升级成自动 Finding 或变更授权。SQLite、fixture 和受控 sidecar 可以在校园网约束下完整验收。

**代价与限制。** 该工具只做同任务、同范围的确定性分组，不理解指标语义、拓扑或因果关系；证据缺失、时间戳错误、截断或 stale/expired 仍可能产生不完整线索。没有 `runId` 的资料按时间窗关联可能包含无关样本，模型必须查看来源和警告后再决定是否重新采样。长期基线清理、跨任务关联、自动回退和真实外部目标仍未验证。

**备选与否决理由。** 让 Agent 自己按正文和自然语言猜关联会扩大上下文、泄露面和误报；只用采集时间关联带来跨运行混淆；由宿主自动生成根因 Finding 会把观察升级成未经验证的判断。因此先采用运行 ID 优先、时间窗受限、无正文且不改变任务状态的关联契约。

## ADR 0052：恢复选项只在宿主清空旧运行后自动续接

`Accepted` · 2026-09-20。

**背景。** 任务失败或中断后，宿主已经能把旧 run 和未完成步骤收口、使旧审批和基线失效，并根据用户选择返回 `investigating`/`recovery`、`waiting_user` 或 `stopped`。但桌面端原先只刷新任务详情，用户还需要手动打开 Agent 并再次点击启动；这让“重试”与“继续恢复”选项没有完成它们描述的工作，也容易让用户重新复制目标造成第二条启动路径。

**决定。** `investigation_task_recover` 的宿主语义保持不变：先完成恢复事务；只有响应任务状态为 `investigating` 且 `activeRunId` 为空时，桌面端才自动调用已有的 `investigation_task_start`。这覆盖重试、重新规划、继续恢复和不带选项的恢复请求。`wait_user`、`rollback`、`stop` 或 `inspect` 返回其它状态时不自动启动；统一启动入口仍负责新的 run、预算、目标、计划和 Permission Engine。启动失败只保留可见错误，不能把状态或 UI 当成运行成功。

**为什么。** 自动续接发生在宿主已封存旧 run 之后，旧事件由 `active_run_id` fence 隔离，新的 run 仍经过原有 admission、计划和权限门控。把动作放在桌面端对宿主响应的白名单判断中，既让用户选择真正产生效果，也不让 sidecar 或自然语言自己决定何时继续。纯状态函数和桌面测试覆盖 investigating/无活动 run、已有活动 run、等待用户和停止四种分支。

**代价与限制。** 这是本地桌面端的恢复编排，不代表远端副作用已经撤销；重试前仍必须重新采样、重新建立基线并重新审批行动计划。Provider 不可用、sidecar 启动失败或预算耗尽时，任务会停在可见错误，用户仍可检查或选择其它失败选项。真实外部目标、自动回退和无限期后台恢复仍未验证。

**备选与否决理由。** 让用户每次手动复制目标会降低长任务的可恢复性；让 React 无条件启动会把 `wait_user`、回退和停止误当成授权；让 sidecar 自己重启会绕过宿主 run fence。因而只对白名单的宿主终态响应复用统一启动命令。

## ADR 0053：任务历史清理采用预览、显式确认和事务复核

`Accepted` · 2026-09-20。

**背景。** 证据、Finding、计划步骤和阶段工件已经跨运行持久化，长期运行会让本地 SQLite 持续增长；但把“超过某个天数”直接交给 Agent 或后台定时器会误删仍被结论引用的证据，也会把远端文件备份的生命周期和本地元数据混在一起。

**决定。** 只为一个终态调查任务提供 `investigation_retention_preview` 和 `investigation_retention_prune`。Agent 可以通过只读的 `investigation.retention.preview` 请求同一份预览，但没有删除方法；预览默认使用宿主计算的保守截止时间，候选只包括未被 Finding、步骤、工件、决策摘要或计划引用的旧证据，以及状态为 `superseded` 的旧阶段工件；活动、等待用户或仍可继续的任务不参加。桌面端必须先展示候选、保护数量和字节数，再由用户确认固定的 `delete_unreferenced` 意图。清理请求必须带预览里的任务、截止时间和具体项目，宿主在同一个 SQLite 事务中重新确认任务终态、引用关系、状态与时间条件，变化的项目返回 skip 而不是删除，并写入一条 `explicit_retention_prune` 审计活动。远端 `filesystem.backup` 字节不由这条命令删除，仍需走已有的账本绑定和逐项批准路径。

**为什么。** 两步操作让用户看到“会删除什么”，事务复核让预览与执行之间新增的 Finding 或计划引用优先于旧列表；候选规则围绕本地任务历史而不是模型判断，能在无网络、fixture 和 SQLite 重开测试中完整验证。把远端备份排除在外，避免本地数据库清理误以为已经回收了目标主机上的副作用。

**代价与限制。** 这不是自动轮换：用户仍需打开终态任务并确认，候选扫描目前按单任务 bounded limit 运行；跨任务、远端备份、日志目录和自动保留策略仍未完成。删除历史记录不可逆，虽然被引用的证据会保护，用户仍应在确认前核对任务和截止时间。真实外部主机、虚拟机或网络共享没有参与验收。

**备选与否决理由。** 让后台定时器直接按年龄删除会绕过用户判断并存在引用竞态；让 Agent 自己调用删除会把不可信计划升级成破坏性授权；删除所有旧行会破坏报告可追溯性。因此保留宿主拥有的候选规则、UI 二次确认、事务复核和审计记录，并明确不替代远端备份清理。

## ADR 0054：远端备份先盘点，再进入逐项批准的清理计划

`Accepted` · 2026-09-20。

**背景。** `filesystem.backup` 已把恢复副本登记到宿主账本，`filesystem.backup.cleanup` 也能在远端复核 revision 后删除一个精确路径，但 Agent 之前没有一个只读入口查看当前任务拥有哪些恢复点。另一方面，把本地历史保留清理扩展成后台扫描远端目录，会把“账本记录”和“远端文件仍存在”混为一谈，也会绕过用户对敏感配置副本的判断。

**决定。** 新增只读的 `filesystem.backup.list`。它必须绑定当前 durable investigation task，并由宿主确认任务的服务器范围，只返回有界的账本元数据；`available` 只表示本地记录仍可尝试恢复，不是远端存在证明，列表不会打开 SSH、读取备份内容或删除任何东西。新增 `investigation.playbook` 的 `backup_cleanup` 形状：输入必须带精确目标 `path`、宿主产生的 `backupPath` 和 64 位 `expectedRevision`；计划先读取 `filesystem.backup.list`、记录 Finding 和 DecisionBrief，再把一个 `filesystem.backup.cleanup` action 交给 medium-risk 的逐项用户批准，最后重新读取 available 账本验证。宿主仍在 action 内复核任务归属、账本状态、远端普通文件、内容 revision 与读取期间的 stat，成功后才把记录标为 `deleted`。

**为什么。** 只读盘点让 Agent 可以先把“可能存在的恢复点、创建时 revision 和清理影响”交给用户判断，且不会把元数据当作现场事实；单项计划把每次清理绑定到一个具体副本，沿用现有计划、权限、幂等、审计和失败处理。末尾的账本复查能区分“远端清理成功”和“仍有可用记录”，而不是凭模型文本宣称完成。

**代价与限制。** 这不是后台自动轮换，也不是跨任务批量清理；列表受任务和 128 行上限约束，远端删除仍可能在 SQLite 标记前成功而需要 reconcile。目录级保留、跨服务器策略、备份内容异地保存和真实外部目标仍未验证，校园网验收只使用内存 fixture、SQLite、stdio 和回环路径。

**备选与否决理由。** 让 Agent 直接接受任意备份路径会绕过宿主账本；把清理接在编辑或验证成功之后会把 medium-risk 数据删除隐藏在另一项行动里；让调度器按年龄静默删除会绕过用户判断并产生远端竞态。因此保留只读列表、单项计划、远端复核和显式批准，不提供隐式自动清理。

## ADR 0055：调度重启恢复必须同时收口运行栅栏并保留上一轮结果

`Accepted` · 2026-09-20。

**背景。** 持续巡检的调度 claim、durable investigation run 和任务 `active_run_id` 分别落在同一 SQLite 数据库的不同表里。应用在 claim 或 sidecar 启动后退出时，如果只把 schedule run 标成 `interrupted`，任务仍会指向已经不存在的运行，下一次触发会被永久判定为 `task_already_running`；如果 claim 阶段把 schedule 的 `last_outcome` 改成临时 `claimed`，下一次 sidecar 也收不到上一轮 `changed`、`no_change` 或 `baseline` 的复核重点。

**决定。** 应用启动时，宿主在一个 SQLite 事务内枚举 `claimed/running` 的 schedule run：把对应的 durable run 标为 `interrupted`，关闭该 run 的 `pending/running/waiting_user` 步骤，给任务写入可重试的 `transport/application_restarted` 失败，并且只在任务仍指向这个 run 时清除 `active_run_id`；schedule run 自身记录 `interrupted` 与 `application_restarted`。claim 对正在排队的 run 只更新下一次触发时间和 `last_run_at`，保留上一轮终态 `last_outcome`，直到本轮真正完成或失败再覆盖。所有更新由宿主拥有，sidecar 不可伪造恢复或比较结果。

**为什么。** 同一事务消除了“调度行已中断但任务仍锁死”的半恢复状态；活动运行栅栏与旧 run 的终态一起收口，迟到帧不能重新打开任务。保留上一轮终态让下一次只读提示真正区分变化、稳定、基线和证据不足，而不会把内部队列状态误当成观测事实。该路径继续使用现有任务预算、权限和只读调度边界，没有引入后台写入或远程回滚。

**代价与限制。** 如果应用在远端动作已经提交但响应尚未回来时退出，恢复只封存本地账本，不推断远端结果，也不会自动重放；下一次运行仍需按任务提示重新采样。调度器仍依赖桌面进程存活，应用完全退出期间不会补跑；多进程/真实外部目标和虚拟化网络没有参与验收，当前覆盖范围是 SQLite、受控 sidecar 与回环 fixture。

**备选与否决理由。** 只更新 schedule 表会留下死 `active_run_id`；让下一次 claim 无条件覆盖任务栅栏会绕过迟到事件隔离；把上一轮结果塞进 sidecar 内存会在重启后丢失且无法审计。因此选择宿主事务收口与持久化结果保留，继续把远端不确定性交给新的只读核对。

## ADR 0056：同一 durable run 的重复证据只复用 canonical ID

`Accepted` · 2026-09-20。

**背景。** Agent 可能因为模型重复规划、工具重试或 IPC 响应丢失，对同一目标发起相同的只读采集并重复提交证据。若每次都新增行，任务上下文和历史会被重复观察污染；若按任务全局去重，又会把持续巡检中不同时间的相同状态误判成同一份资料。

**决定。** `host.investigation.evidence.record` 在宿主覆盖不可信 `runId` 后，仅在当前 durable run 内按任务、目标范围、证据种类、来源工具、输入摘要、内容类型、截断状态和内容哈希查找已有行。命中时返回已有 `evidenceId` 与 `reused: true`，未命中时保存并返回新 ID；没有活动 run 的旧会话保持原有写入语义。跨 run 永不复用，Agent 的消息和阶段工件引用宿主返回的 canonical ID。

**为什么。** run ID 是宿主已有的生命周期和迟到事件边界，能把 IPC 重试的幂等性限制在一次实际运行内，又不会丢失调度样本的时间序列。把查找放在宿主而不是 sidecar，可以复用目标范围、脱敏和持久化校验；明确返回 ID 让模型不会继续猜测证据引用。这个决定只治理本地记录，不声称阻止远端只读采集。

**代价与限制。** 查找键依赖输入摘要和内容哈希，语义等价但字面不同的结果不会合并；并发请求之间仍可能先后通过查找并各自插入，若未来需要跨进程强幂等必须增加数据库唯一约束或事务锁。跨 run 的保留会继续增长 SQLite，仍需单独的历史保留策略；真实外部目标和校园网之外的采集没有因此变成已验证能力。

**备选与否决理由。** 按任务全局哈希去重会摧毁巡检比较；让 Agent 自己记忆已写入的 ID 会在重启和多次重试时失效；直接阻断重复远端读取需要新的采样调度语义，超出本次持久化边界。因此先采用宿主同 run canonical 复用，并把采集节流留给后续调度/排查器。

## ADR 0057：计划证据步骤遇到重复样本时必须停在重规划边界

`Accepted` · 2026-09-20。

**背景。** ADR 0056 只保证同一 durable run 的重复证据不会污染 SQLite，但 Agent 仍可能把宿主返回的 canonical ID 当成一次新的成功基线，并继续推进当前计划。这样会把“没有新增观察”误报成步骤完成，尤其会让模型在目标没有变化时反复读取同一个远端状态。

**决定。** 当 `host.investigation.evidence.record` 返回 `reused: true`，且当前调用绑定到 `evidence` 计划步骤时，sidecar 将该调用的计划结果改为 `failed`、`retryable: false`，不写成功基线工件，并向下一轮模型消息说明没有产生新证据，要求改用 `investigation.evidence.search` / `compare` / `correlate`、调整采样条件后重新规划或等待用户。宿主现有步骤失败路径负责留下失败工件、阻塞当前步骤并提供后续选项；工具本身的只读执行结果仍按真实结果审计为成功。

**为什么。** 计划推进需要新增证据这一事实，而不是“写入接口返回成功”。把判断放在 sidecar 与宿主计划结果的交界处可以复用既有失败分类、预算和重规划入口，同时保留 canonical ID 供模型解释重复原因。它使“没有进展”成为可见的失败而不是伪成功，又不把一次已经发起的远端读取误称为可撤销。

**代价与限制。** 远端读取仍发生在宿主发现重复之前，因而这不是网络采样节流，也不解决没有计划门控的普通对话重复读取；语义等价但输入或哈希不同的样本仍由新证据和后续比较决定。当前覆盖是 sidecar loop E2E 与受控 host RPC fixture，真实外部目标仍未验证。

**备选与否决理由。** 继续把重复样本当作成功会破坏计划语义；在宿主执行前按工具输入强行阻断需要新的持久化采样窗口和例外规则，可能挡住合法的重试；直接让 sidecar 静默等待会丢失可审计的失败与用户选择。因此选择显式不可重试失败，把重新规划/等待交给现有任务状态机。

## ADR 0058：计划绑定的只读调用在远端执行前按逻辑动作去重

`Accepted` · 2026-09-20。

**背景。** ADR 0056/0057 解决了证据落库重复和计划推进语义，但它们发生在 Agent 已经收到只读工具结果之后。若 sidecar 因响应丢失、模型重试或并发路径再次提交同一计划步骤，第二次读取仍可能先到达远端，再在证据边界被发现为重复；这会浪费采样、给目标增加不必要的负载，也让“没有新增证据”出现得太晚。

**决定。** 宿主复用既有 `host_tool_calls` SQLite 调用账本：对绑定了 `taskId`、`planId` 和 `planStepId` 的 `server.info`、Docker/systemd/package/filesystem 只读工具，除了精确 `(traceId, callId)` 指纹外，再保存不含 provider 身份的逻辑动作指纹。相同计划步骤、目标、工具和输入再次到达 `host.tool.execute` 时，在 SSH/SFTP/MCP 或其它远端执行分支之前返回 `plan_deviation/duplicate_call`；不同计划 ID 可以重新采样，未绑定 durable 计划的普通读取仍保持原有重试语义。运行中的 observation window 验证步骤是明确例外：它由宿主在 `plan.step_result` 中按采样间隔和截止时间决定下一次样本是否可接受，不使用普通的一次调用 fence。确定性参数失败可以重试，传输、超时、取消和不确定执行结果仍按调用账本的保守状态处理。第一次读取的真实结果仍照常进入证据与步骤审计；这条 fence 不会把普通聊天或新计划变成全局采样限流。

**为什么。** 逻辑动作指纹已经用于高风险动作的重投保护，复用它可以在不增加第二套竞争窗口的情况下，把计划只读调用的边界前移到远端执行前。把 fence 限定在明确的计划步骤，既阻止同一步骤的重复样本，又保留用户重规划后重新采集的能力；宿主拒绝而不是 sidecar 猜测，也能把原因留在统一的 `duplicate_call` 审计形状里。临时 SQLite 宿主单测验证了“第一次可执行、换 callId 的同一步骤被拒绝、无计划普通读取仍可执行”的三条边界。

**代价与限制。** 逻辑指纹是工具输入级身份，不理解“语义上等价但写法不同”的采样；不同输入或新计划仍可能产生相同内容，继续由证据 canonical 去重和比较器解释。它只覆盖当前宿主拥有的列举工具，不是所有 sidecar 本地工具或第三方系统的全局采样节流；真实外部主机、断网时序和校园网外部署仍未验证。

**备选与否决理由。** 只在证据保存后去重会让重复读取已经发生；把所有只读请求都放进账本会破坏普通聊天的合法重试；按时间窗口盲目限流会挡住用户明确重采样。因而采用计划绑定、工具白名单和逻辑动作指纹三者同时成立时才生效的窄 fence。

## ADR 0059：跨层停止与迟到事件先抽成宿主状态核心再验收

`Accepted` · 2026-09-20。

**背景。** 停止确认已经会沿宿主的终态路径封存 durable run、任务和调度记录，恢复也会接管新的活动 run；但事件状态同步和 run 持久化原先都藏在 Tauri command 的事件入口里。只测其中一个 helper 不能证明“取消后的任务状态、run 终态和 `active_run_id` 清理”会一起发生，也不能证明旧 run 的迟到帧不会从另一层重新打开任务。校园网约束又不允许用虚拟机或共享网络伪造真实远端运行时。

**决定。** 把这两段逻辑抽成接收 `&AppState` 的宿主状态 helper，Tauri command 只负责取得状态并调用它们；生产事件入口继续复用同一 helper。新增临时 SQLite fixture，先发送当前 run 的取消完成事件，断言任务进入 `stopped`、run 进入 `cancelled` 且 `active_run_id` 清空；再为同一任务建立 `interrupted` 的旧 run 与新的活动 run，断言旧 run 的完成帧在状态同步和持久化两层都被拒绝，而当前 run 仍可完成；终态 run 的第二个终态帧同样被两层丢弃。

**为什么。** 这把跨层不变量放在唯一的宿主状态核心里验证，而不是在 React 或 sidecar fixture 中复制一套近似逻辑。测试仍只需要 SQLite 和进程内状态，不会触发 SSH、容器网络、虚拟机或共享网络；生产 Tauri 入口和离线 fixture 共享同一实现，减少“测试路径与生产路径分叉”的风险。

**代价与限制。** fixture 只证明 SQLite 状态转换和活动 run/终态 fence，不能证明真实 Tauri IPC 的取消时序、sidecar 进程退出、窗口重启、远端写入提交点或网络断开后的行为。停止仍不是远端回滚，远端部署、自动回退和完整部署 playbook 仍需独立的受控验收与用户授权。

**备选与否决理由。** 继续只测单个 command helper 会漏掉跨层状态组合；尝试在校园网里启动虚拟机、WSL、容器网络或桥接环境违反当前验收边界；让 UI 或 sidecar 自己拼接状态会绕过宿主 run fence。因此先抽出共享状态核心并用本地 SQLite 验收，真实运行时验证留作后续可获得合规环境后的单独工作。

## ADR 0060：把远程日志与服务发现接入同一只读排查计划

`Accepted` · 2026-09-20。

**背景。** 桌面端原本已经有 `server_logs` 和 `server_services`，但它们只服务于页面命令；durable Agent 任务只能拿到 `server.info`、Docker 工具和文件读取。结果是任务的统一证据链缺少最常见的近期日志与服务状态，模型需要用户手动切换页面才能判断“健康快照、日志、服务、容器”是否属于同一次排查。

**决定。** 新增只读 host tools `server.logs` 和 `server.services`。Rust host 复用桌面命令中的固定、受限发现命令和解析器，在 `host.tool.execute` 中重复执行目标服务器校验、取消、超时和结构化失败映射；Node sidecar 以 shared `ServerLogsResponse`/`ServerServicesResponse` schema 注册工具，成功结果沿现有 `buildEvidence` 自动保存。两者加入计划绑定只读 fence，`readonly_health` playbook 固定按 server snapshot、日志、服务、Docker 清单、Finding、DecisionBrief 和最终 snapshot 的顺序生成步骤。

**为什么。** 复用已验收的解析器避免为 Agent 复制一套日志/服务语义；让 Rust host 仍拥有 SSH 会话、命令和目标范围，sidecar 只拿到有界结构化结果。工具是只读且对不可用管理器返回明确 `unavailable`，所以模型可以把“没有日志/服务源”作为未知写入 Finding，而不是把空数组当成健康。进入 durable 计划后，同一逻辑样本也受执行前 fence 保护，并能和其它来源按 run ID 关联。

**代价与限制。** 当前命令只读取最近 120 条日志和最多 200 个服务摘要，不支持任意时间窗、服务过滤、日志索引或语义根因分析；远程输出异常会停在结构化失败。解析器与 sidecar/host fixture 已覆盖，真实 SSH 主机、权限差异、日志规模和校园网之外的部署仍未验证。

**备选与否决理由。** 让 Agent 直接调用页面 IPC 会绕过 sidecar 任务、计划和证据边界；把日志全文或任意 shell 交给模型会扩大数据泄露和命令注入面；继续只提供 `server.info` 则无法解释服务/日志层症状。因此选择固定命令、结构化摘要、宿主范围校验和统一证据链。

## ADR 0061：用回环 Provider 验收真实 sidecar durable 读链路

`Accepted` · 2026-09-20。

**背景。** 既有 TypeScript fixture 能覆盖 AgentLoop 的计划、证据和失败语义，Rust integration test 也能启动打包 sidecar、完成握手并检查工具目录；但两者之间仍缺少一条真实的跨语言任务验收。只测其中一层无法发现 stdio 帧方向、Provider SSE、sidecar 发起的 host request 或终态事件排序上的协议问题。校园网环境又不能用虚拟机、WSL、桥接或共享网络搭建外部测试主机。

**决定。** 在 `crates/core/tests/sidecar_agent.rs` 增加一条真实 supervisor 测试：Rust 启动构建出的 Node sidecar；测试内的 `127.0.0.1` TCP listener 只返回三段固定 OpenAI-compatible SSE，依次驱动 Agent 生成一条单步只读计划、调用 `server.info`、输出最终文本。测试订阅真实 sidecar 事件并回答 `host.mcp.catalog`、`host.context.fetch`、`host.investigation.plan.record`、`host.investigation.plan.check`、`host.tool.execute`、`host.investigation.evidence.record`、`host.investigation.artifact.record` 和 `host.investigation.plan.step_result`；最后断言 Provider 请求数、目标工具、证据来源、计划进入 `completed`、`agent.tool_result` 和 `agent.completed` 都真实经过 NDJSON/JSON-RPC 边界。

**为什么。** 这条测试复用了生产 sidecar bundle、Rust `SidecarHandle`、实际 Provider fetch/SSE parser 和真实 host request/response 方向，能证明比内存 Agent fixture 更接近运行时的任务闭环；Provider 与 host 都是本机内存/回环 fixture，不需要凭据、SSH 或共享网络，也不会把外部服务的偶然行为混进门禁。

**代价与限制。** 它只证明 Rust supervisor 与 Node sidecar 的 stdio/loopback 协议及任务时序，不启动 Tauri 窗口、不访问真实 Provider、不连接 SSH 主机，也不代表真实远端部署已经验证。固定 SSE 只覆盖一条 chat-completions 工具调用路径；其它 Provider 方言、窗口重连和远端网络仍由各自 fixture/限制文档负责。

**备选与否决理由。** 只增加更多 TypeScript fixture 会继续绕开 Rust/Node 边界；使用外部 Provider 或校园网中的共享主机会引入凭据、网络和不可重复性；在 Tauri UI 测试中复制 sidecar 协议又会造出第二条 transport。因而选择生产 bundle + Rust supervisor + 回环 Provider 的最小跨语言闭环，明确把 Tauri IPC 与远端部署留作未验证项。

## ADR 0062：只有 `start_plan` 选项能批准关联变更计划

`Accepted` · 2026-09-20。

**背景。** 决策摘要可以把用户选择后的行为声明为 `continue_readonly`、`start_plan`、`wait_user` 或 `stop`。调度器生成的“数据发生变化”摘要可能为了回链历史证据而带有最近计划 ID，但它的只读复核选项不应批准那个计划。此前宿主只排除了 `stop`，因此选择 `continue_readonly` 或 `wait_user` 时也会把关联计划写成 `approved`。

**决定。** `investigation_brief_select` 只在选项的显式续接值为 `start_plan` 时写入用户来源的计划批准。`continue_readonly` 和 `wait_user` 保留计划为 pending，仍可按白名单续接或等待下一次用户输入；`stop` 继续走宿主取消与终态收口路径。UI 的自动启动逻辑不变，仍只信任宿主返回的显式 continuation。

**为什么。** 计划批准是改变风险边界的持久事实，不能由“这次要继续采集”或“暂时不做决定”隐式产生。把批准条件收窄到一个跨语言枚举值，可以防止旧摘要、调度摘要和手写 IPC 请求把只读复核升级成可执行方案；实际行动仍要经过计划绑定和逐项 Permission Engine 审批。

**代价与限制。** 这只修正计划批准语义，不会替用户选择 `start_plan`，也不会让已提交的远端副作用消失。旧数据库中的省略 continuation 仍按 `wait_user` 处理；真实 Tauri IPC、Provider 和外部主机不因该修复变成已验证能力。纯函数回归测试和现有桌面命令门禁覆盖该白名单边界。

**备选与否决理由。** 让 UI 依据标题或 `requiresApproval` 猜测是否批准会受自然语言和陈旧缓存影响；让所有非 stop 选项继续批准会把只读调度结果变成隐式授权；在 sidecar 中保存批准状态会绕过宿主持久化。因此由宿主按 continuation 枚举作唯一批准门槛。

## ADR 0063：证据 triage 只生成候选信号，不宣称根因

`Accepted` · 2026-09-20。

**背景。** 任务已经能搜索、取回、比较和关联证据，但复杂只读排查仍要求模型逐条阅读正文并自行记住资源、服务、容器和日志中的重复信号。完全把这种归纳交给模型容易重复取回，也容易把同时出现的错误写成已证实根因；把它放进宿主则会让启发式结果看起来像现场事实。

**决定。** 新增 sidecar 只读工具 `investigation.evidence.triage`。请求最多带 16 个当前任务的真实 evidenceId；工具通过现有 host fetch 取回已经脱敏、有界的正文，在 sidecar 内按固定规则产生资源高水位、服务/容器不可用、日志错误模式、截断和采集失败等信号，并按信号族返回最多 8 个候选假设；当至少两条不同证据共同命中资源↔日志、服务↔日志或容器重启↔不可用信号时，额外返回标明“共同出现”的交叉候选。结果只含计数、来源 ID、警告、低/中置信度和下一步复核建议，固定带 `notCausal: true`；它不写 evidence、不生成 Finding、不推进 plan、不执行远端调用，也不改变 Permission Engine。`evidence`、`evidence.search`、`evidence.compare`、`evidence.correlate` 和 `evidence.triage` 都属于活动计划中的本地上下文读取，Agent loop 不为它们发起 `plan.check`，因此可以在活动计划内复核已保存资料而不消费或伪造远端步骤。

**为什么。** 这是对模型工作的有限辅助，而不是另一套事实来源：正文仍由宿主按任务范围和脱敏策略提供，候选仍能回链真实 evidenceId，模型必须重新取样和引用原始证据后才可形成 Finding。把规则限制在已取回数据和固定输出上，可以在无网络 fixture 中验证上限、敏感行不回显、过期/截断警告和部分取回，同时避免把业务语义、拓扑或因果判断伪装成确定性代码。

**代价与限制。** 规则只覆盖有限字段和文本模式，不能理解服务拓扑、业务指标或时间序列，也可能漏报或产生需要复核的候选；它最多并行取回 16 条证据，取回失败只作为警告，全部失败才返回错误。真实 Provider、SSH 目标和生产事故没有因此变成已验证能力，后台根因调查仍需后续 playbook 和用户判断。

**备选与否决理由。** 让模型直接把日志句子写成根因会扩大误报；让 Rust 宿主读取正文并生成 Finding 会把启发式提升成权威结论；增加一个能自动采样或执行动作的“诊断工具”会绕过现有计划与权限边界。因此保留 sidecar 本地、证据 ID 回链、固定规则、明确非因果标记和只读权限。

## ADR 0064：受限 playbook 的观察窗口只能挂在最终只读验证上

`Accepted` · 2026-09-20。

**背景。** 宿主已经能推进 `investigation.plan` 的观察窗口，但常见的配置编辑、服务/容器重启、包安装和组合部署都由 `investigation.playbook` 生成。若模型只能手工把窗口复制到通用计划，部署后的持续验证容易被遗漏；若让窗口重新声明任意工具或行动，又会把一次验证变成隐式扩权。

**决定。** `investigation.playbook` 接受可选的有界 `observationWindow`，只包含持续时间、采样间隔、成功条件和允许工具。sidecar 在生成计划后要求每个允许工具都已经出现在该 playbook 的最终 `verification` 步骤中，并将窗口初始化为 `pending`、`sampleCount=0`；不匹配时在发给宿主前以 `invalid_input` 拒绝。宿主仍是唯一能推进样本、设置截止时间、标记成功/失败和收口任务的组件；窗口中的重复样本沿用宿主的间隔与 deadline 规则，异常进入等待用户，不会自动重试写入、回退或追加工具。

**为什么。** 把窗口绑定到最终验证步骤能复用已有计划绑定、只读工具白名单和 observation window 状态机，同时让 playbook 在模型选择常见维护形状时具备部署后观察能力。sidecar 只做静态子集检查，不重新解释远端事实；宿主仍能在重启、恢复或计划变更时清空旧窗口状态。

**代价与限制。** 窗口只能采样最终验证工具，不能表达跨多个来源的语义根因、业务指标或自动回退；完成只代表宿主接受了有界采样，不代表真实外部部署稳定。真实 SSH、远端时间漂移、Tauri IPC 时序和校园网之外的环境仍未验证。

**备选与否决理由。** 让模型在每轮自行 sleep/重读会绕过持久化 deadline、重复 fence 和审计；让 playbook 接受任意新工具会扩大目标范围；让窗口成功自动批准恢复或下一项写入会把观察事实变成授权。因此只提供最终验证的只读子集，并把推进权留在宿主。

## ADR 0065：观察窗口续采样只重放宿主已批准的最终读取

`Accepted` · 2026-09-20。

**背景。** 观察窗口的状态和下一次采样时间已经由宿主保存，但 sidecar 在收到 `observation: running` 后如果让模型自行决定是否再次调用，模型很容易用一段文字结束回合，任务就会停在未完成窗口；把一段新的自然语言提示当成自动化也会让工具和参数发生漂移。

**决定。** `AgentLoop` 在宿主返回 `nextSampleAt` 时记录本轮最终验证调用的 provider 工具名和精确参数。若模型下一轮没有产生工具调用，sidecar 等待该时间（仍受运行级 `AbortSignal` 和 `maxRunMs` 约束），合成一个新的、唯一 callId 的同名调用；这个调用重新经过现有 `plan.check`、Permission Engine、宿主目标校验、证据落库、阶段工件和 `plan.step_result`，只有宿主继续返回 `observation: running` 才会安排下一次。宿主返回成功、异常、无效时间表、取消或运行超时都会停止续接；sidecar 重启不会恢复内存中的 replay，任务保持可恢复的未完成状态。

**为什么。** 续采样不再依赖模型是否记得等待，同时没有引入新的“观察工具”或绕过已有门控。每一次样本都有普通工具调用、证据和计划结果记录，窗口仍由宿主决定什么时候成功；只读、原参数和运行预算限制把自动化限制在用户已经批准的最终验证范围内。

**代价与限制。** 等待期间会消耗当前 Agent run 的 wall-clock 和 step 预算；长于 sidecar 运行预算的窗口需要用户恢复或重新采样，应用完全退出也不会在后台继续。重放的是同一工具和输入，不理解成功标准的语义，也不替代模型对样本内容的解释；真实远端时间漂移、Tauri IPC 时序和外部部署仍未验证。

**备选与否决理由。** 让模型自行 sleep/重建调用无法保证等待或参数不漂移；让 Rust 调度器直接调用远端工具会绕开 sidecar 的统一权限、证据和审计路径；新增可任意选择工具的 observation API 会扩大范围。因此选择 sidecar 内部的 exact replay，并把每个实际读取再次交给既有宿主门控。

## ADR 0066：任务 guardrails 在每次执行前由宿主复核

`Accepted` · 2026-09-20。

**背景。** 任务已经有目标范围、预算、计划和 Permission Engine，但用户还无法把“只在这个时间窗工作”“绝不调用某个工具”“绝不触碰这个路径前缀”作为一条持久化边界交给宿主。只把这些内容放进 Agent 提示词，会让重规划、重试或 sidecar 重启后的调用重新解释边界；只在 UI 创建时检查也无法防住伪造的 host RPC。

**决定。** `InvestigationTask` 增加可选的 `guardrails`：UTC `notBeforeAt`/`expiresAt`、最多 64 个精确内部工具名和最多 64 个绝对路径前缀。SQLite 以独立 JSON 列保存，旧行迁移为空边界。创建命令验证时间格式、起止顺序、最多 365 天跨度、工具名和路径形状；桌面任务页让用户直接填写这些值，任务上下文和自主启动提示也会展示它们。

宿主在任务启动、`host.investigation.plan.check`、计划保存的工具/输入绑定，以及真正的 `host.tool.execute` 之前复核同一份 guardrails。时间窗不开放时返回 `outside_time_window` 计划偏离或结构化 `denied_by_policy`；精确工具名或 `path`/`backupPath` 归一化后命中禁止前缀时返回 `scope_forbidden`。禁止路径只做词法 `.`/`..` 归一化和前缀边界匹配，不把远端 symlink、挂载或业务 ACL 伪装成已经验证；现有目标范围、计划绑定、Permission Engine 和危险动作审批仍是独立门槛。

**为什么。** guardrails 让用户目标中的负面约束进入宿主拥有的 durable 状态，并在每一个可能触达远端的入口重放同一检查。把计划保存也纳入工具和绑定检查，可以在用户看到 dry-run 方案时提前发现明显越界；把实际执行放在最后一关，可以防住模型伪造 task context、换 callId、重启 sidecar 或改写参数。旧任务仍能读取，空列表只表示没有额外限制，不改变旧 Permission Engine 语义。

**代价与限制。** 这是一个有界的词法边界，不是完整的远端策略语言；它不表达业务角色、symlink 解析、文件系统挂载或任意命令语义，也不能在应用完全退出后替用户执行。时间窗外的任务不会被后台自动推迟或续跑，调度和恢复仍需走原有任务入口；真实外部目标与远端路径语义仍未验证，验收只使用临时 SQLite、fixture、stdio 和 `127.0.0.1`。

**备选与否决理由。** 只在提示词中描述边界会受模型服从度影响；只在 UI 过滤会绕过伪造 IPC；把 guardrails 合并进 Permission Engine 会混淆“用户任务范围”和全局风险策略，也难以在计划/任务历史中解释。因而选择独立、持久化、宿主重复复核的窄契约。

## ADR 0067：持续巡检允许用户选择固定证据基线，并对终态任务自动封存触发器

`Accepted` · 2026-09-20。

**背景。** 持续巡检原先只把当前运行与最近一条成功样本比较。这个默认适合平稳观察，却无法表达“始终与发布前的健康样本比较”；同时，任务进入完成、失败、停止或过期后，活动 schedule 如果只记录一次 `task_terminal` 跳过，后续每个周期仍会不断产生无效触发。

**决定。** `InvestigationSchedule` 增加可选的宿主校验 `baselineRunId`。任务页只从同一 schedule 的运行历史发起选择；宿主读取完整 schedule run，要求它已成功结束、属于当前触发器且至少有一条证据，才把 ID 写入 SQLite。比较器有固定基线时只使用该运行，并排除当前运行；固定基线没有证据（例如历史保留清理后）就报告 `insufficient_evidence`，不静默回退到最近样本。未设置固定基线的旧 schedule 继续使用最近成功样本。调度 claim 与启动 sidecar 两层都识别终态任务，第一次到期写入 `skipped/task_terminal` 并把 schedule 置为 `revoked`；撤销仍不可逆，历史可查询但不会继续唤醒 Agent。

**为什么。** 基线 ID 是比较语义的一部分，必须由宿主验证并持久化，不能让模型用自然语言指定；证据缺失时安全降级能避免把“基线被删了”伪装成“没有变化”。在 claim 事务内撤销终态触发器可以消除重复噪声，而启动前再复核则覆盖任务在 claim 与 sidecar 启动之间变成终态的窗口。两层仍复用现有只读、预算、通知和运行账本，不增加后台写权限。

**代价与限制。** 固定基线目前只支持选择一条成功运行，不能自动维护发布版本、跨 schedule 合并或替用户重建被清理的证据；应用退出期间不会继续调度。UI 展示和本地 SQLite/fixture 已覆盖，真实外部目标、跨进程竞争和长期历史保留仍未验证。

**备选与否决理由。** 直接在 Agent 提示词中写“与这次 ID 比较”会绕过宿主范围和证据检查；基线失效后自动换最近样本会改变用户已选择的语义；让调度器每次都重试终态任务会制造无限失败通知。因此采用可选的宿主字段、失效即证据不足，以及终态自动撤销的持久化状态机。

## ADR 0068：固定巡检基线必须支持显式清除

`Accepted` · 2026-09-20。

**背景。** 持续巡检允许用户把一条成功运行固定为比较基线，但只支持选择另一条运行会让用户无法恢复默认的“最近成功样本”策略。把空字符串当作清除信号又会混淆 IPC 校验和宿主 ID 语义；把省略字段当作清除会让旧客户端调整频率或通知时意外改变比较语义。

**决定。** 共享更新契约把 `baselineRunId` 定义为可省略的 `string | null`。省略表示不修改，非空字符串仍须经过同一 schedule、成功状态和证据存在校验，显式 `null` 才清除 SQLite 中的固定基线。任务页只在当前 schedule 未撤销时提供“改用最近样本”操作；比较器清除后恢复原有最近成功样本路径，固定基线失效时仍保持 `insufficient_evidence` 的 fail-closed 行为。

**为什么。** 三种状态在宿主层可区分，更新不会因为客户端版本差异而改变用户的比较基线；清除动作没有任何远端副作用，只改变后续本地比较策略，适合在校园网离线 fixture 中完整验收。保留固定基线的严格校验和撤销不可逆规则，避免 `null` 变成绕过 schedule 归属的快捷路径。

**代价与限制。** 清除只影响后续 schedule 比较，不会重写历史运行、恢复被清理的证据或自动建立新基线；真实外部目标和跨进程竞争仍未验证。

**备选与否决理由。** 用空字符串或特殊 ID 会扩大不透明输入；把“切换到最近样本”建成新的 schedule 会丢失已有运行历史和通知设置；让模型自然语言决定清除会把持久化策略交给不可信输入。因此采用显式 nullable 字段和宿主事务更新。

## ADR 0069：副作用 Agent 工具必须绑定 durable task 和 ChangePlan 步骤

`Accepted` · 2026-09-20。

**背景。** 计划检查原本只在请求已经带 `taskId` 时运行；普通聊天因此可以绕过 durable 任务直接到达 host dispatcher。会话授权也只按工具和目标记忆，同一批准可以被改写输入重放。

**决定。** 明确声明为 effectful 的内置工具和全部 `mcp.*` 工具，在 sidecar registry 与 Rust host 两层都必须带非空 `taskId`、`planId`、`planStepId`；缺少任一字段时在执行前返回 `durable_plan_required`，不创建远端副作用。Permission Engine 对规范化输入计算 SHA-256，决策、session grant 和 registry ticket 必须匹配同一指纹。交互式终端不接入 Agent 工具目录，继续作为用户明确输入的人工旁路。

**为什么。** 双层门控覆盖被攻破或过时的 sidecar、伪造 IPC 和普通聊天入口；计划步骤把影响、证据和结果绑定到可恢复的 durable 状态，输入指纹则避免“同工具同主机”的宽泛 session grant。终端没有自动 API，因而不会被误当成可审计的 Agent 自动维护。

**代价与限制。** 普通聊天不能直接让 Agent 写入，必须先创建任务并保存计划；显式用户操作终端仍可能改变远端状态，但它不属于 Agent 自动审计链。真实外部部署、网络共享和虚拟机都不在本轮验收范围，测试只使用 fixture、stdio 和 `127.0.0.1`。

**备选与否决理由。** 只在提示词或 UI 中要求“先建计划”会被伪造 IPC 绕过；只在 host 侧拦截无法阻止 sidecar registry 误报成功；把终端强行塞进 Agent 计划会把人工会话伪装成自动授权。因此选择 sidecar/host 双栅栏，并把终端保持为明确隔离的人工路径。

## ADR 0070：后台任务弱引用加显式取消

`Accepted` · 2026-09-20。

**背景。** Rust 的安全内存保证会阻止 use-after-free、double free 和数据竞争，但不会自动终止一个持有 `Arc<Owner>` 的后台任务，也不会替子进程、SSE、PTY 或 keepalive 选择关闭时机。项目中的长生命周期任务如果跨网络等待、退避或无限循环强持有所有者，会让最后一个可见句柄释放后状态仍被任务保活；这只是逻辑泄漏或 liveness 问题，不应被误称为 Rust 的天然内存缺陷。

**决定。** 后台任务不把所有者 `Arc` 作为长期强引用根。任务持 `Weak` 或必要的配置快照，只在同步临界区短暂升级；需要停止的任务使用 `CancellationToken`、关闭通知或显式关闭入口。所有者 `Drop` 作为同步兜底发出取消并 abort 未完成任务，显式子进程、SSE、PTY 和 keepalive 路径仍负责正常收口。启动锁、退出观察和自动重启等只需独立同步状态的部分不再依赖整个 supervisor 存活。本约定已应用于 MCP HTTP GET 流、MCP supervisor、sidecar supervisor、terminal forwarder 与 SSH keepalive，并由本地回归或静态审计验证。

**为什么。** 让任务的生命周期跟随业务所有者，而不是反过来让任务成为不可见的强引用根，能让最后句柄释放、显式关闭和测试中的弱引用检查保持同一语义。短暂升级 `Weak` 既避免长等待保活，又能拒绝所有者已经退出后的状态访问；独立取消令牌使“停止”不依赖下一次事件、网络响应或异步析构是否真的运行。

**代价与限制。** `Weak::upgrade` 会失败，调用方必须把所有者已退出作为正常分支处理；显式取消和关闭比单纯依靠 `Drop` 多一套状态路径，也更容易暴露关闭顺序错误。`Drop` 不能执行异步协议，abort 也不等于远端副作用已回滚。验收目前只覆盖本机进程、临时数据库、stdio、fixture 和 `127.0.0.1` 回环；真实 SSH、Provider、第三方 MCP、Tauri 窗口退出和长时间资源曲线仍需在可用环境中复验。

**备选与否决理由。** 继续在任务中克隆 `Arc<Owner>` 会让释放顺序依赖任务调度，无法用最后一个句柄可靠判断生命周期；只依赖 `Drop` 会遗漏异步关闭和 Windows 强杀等路径；把所有资源放进全局注册表再统一扫描会增加跨模块耦合，也无法解决任务保活本身。因而采用局部 `Weak`、独立取消令牌、显式关闭和不承诺远端回滚的 `Drop` 兜底。

## ADR 0071：桌面端 SSH 首连不再自动信任主机密钥

`Accepted` · 2026-09-21。**取代 [ADR 0012](#adr-0012主机指纹默认-tofu但必须能人工核验钉住与遗忘) 中「默认首次信任」那一条决定**；ADR 0012 的探针/钉住/遗忘三入口、失败时并列两个指纹、以及「不提供不一致时仍然继续」继续有效。

**背景。** 外部工程审计（[安全与性能审计建议](./Yukinal-security-performance-audit.md) 第 3.1 节）指出一处真实的不一致：`crates/ssh` 的默认已是「必须匹配已知指纹、未知主机在 TCP 之前拒绝」，项目也早就有探针 → 确认指纹 → 钉住的完整基础设施，但桌面端唯一的生产配置把策略写死为 `TrustOnFirstUse`。于是同一次「未核验主机」在不同入口得到不同答案：探针与其余基础设施按严格模式工作，而用户最常走的终端却自动信任。审计把它列为 P0：首连被中间人劫持时，客户端会把攻击者的密钥记录为可信，后续严格匹配只是把这次污染固定下来。

**决定。** ① 桌面端所有走 `ensure_session` 的入口（终端、文件、SFTP、日志、服务、概览采集）统一使用 `RequireMatch`；② 未知主机在认证之前失败，认证处理器收不到密码或 keyboard-interactive 回答；③ UI 在会建立连接的面板上直接提供核验闸门（`HostKeyGate` 复用已有的 `HostKeySection`），而不是只用一句错误把用户引向别处；④ 显式 host CA 的服务器以证书链为信任依据，不要求叶子 pin；⑤ 新增 pin 仍然只能来自用户确认过的探针结果（ADR 0012 第 ④⑤ 条不变）。

**为什么现在改。** ADR 0012 当年拒绝强制严格模式的理由是「用户会复制粘贴指纹或绕开应用」「一次合法轮换会让用户永久无法连接」。这两条被本次审计重新评估：轮换已经有「遗忘 → 重新探针 → 信任」这条明确路径；真正的卡点不是严格模式，而是核验入口只存在于编辑弹窗里，普通用户找不到。闸门把这个入口搬到会失败的地方，于是「找不到出口」不再是保留自动信任的正当理由。把「第一次连接是一次信任决策」交给用户，是这类工具唯一诚实的位置。

**代价。** 首次连接多一步：必须先探针、核对指纹、再信任，未核验时终端等面板不能直接使用。ADR 0012 担心的「用户不去核验」在这个形状下变成「用户无法在不核验的情况下连接」：不核验的人会感到受阻，而不是被静默放行。探针仍然会在服务器上留下一次（通常未认证的）连接记录。这个摩擦是**有意接受**的，不是回归。

**备选与否决理由。** 保留 TOFU（审计已判定为 P0，且把「首次连接」这个唯一的信任决策点交给了网络）；只改终端而不改其余入口（同一次审计针对的正是「入口之间答案不一致」）；只把错误文案改好、不提供面板内入口（文案无法把用户带到另一个页面）；在未核验时用一个「仍然连接」按钮（那等于把 ADR 0012 已经否决的中间人一键化入口重新加回来）。

## 决策记录里的两处历史瑕疵

翻到这一节的人可能会注意到两个不一致，它们**不要**被当成需要修的东西，而是被记录下来的事实：

- 有一条决定从未被单独记成 ADR：**「浏览器预览里没有原生能力」**。它在早期 ADR 里被当成一条备选引用过，还写成过指向一篇并不存在的 ADR 文件的链接。那条链接随这次文档合并消失了；决定本身仍然有效，理由写在[有意为之的边界](./limitations.md#有意为之的边界不是待办)里。
- 决策记录里的计数会过期（例如集成测试的条数）。凡是与代码冲突的计数，**以代码为准**，并顺手把记录改对——这正是「决定变了就新增一条记录」这条规矩存在的原因。
