# 多会话与并行 AI 执行

日期：2026-10-17。适用工作区：`codex/ui-layout-direction` 当前桌面新版。

本文保留并行能力实施前的源码观察和完整目标。协调助手、有界后台团队分派、独立取消与批准、任务持久化、执行期间继续对话已经落地，当前结果和限制以[实施与验收记录](./dots-coordinator-implementation-20261017.md)为准。任意前台长运行的会话切换、跨窗口接管、持久循环调度和完整请求计费账本仍需继续实现。

## 产品结论

一个用户可以同时推进多台服务器上的多件事。对话承载目标、确认与结果；团队承载分工；看板汇总任务。切换对话只改变正在看的内容，不能停止后台任务，也不能把新选中的服务器变成旧任务的执行目标。

并行分三层：不同会话的独立目标可以并行；同一目标的只读调查可以拆成独立子运行并行；同一服务器的变更需要宿主协调。一个会话的主对话仍按用户消息顺序处理，协作团队在隔离的分支里执行，最后由主责团队汇总。

描边呼吸、左侧独立入口和中间四列看板、按调用隔离的操作反馈，以及运行与会话/任务的关联构成界面基础；后台执行是否成立以实际运行记录为证据。统一对话入口的设计依据见[协调助手研究](./dots-coordinator-research-20261017.md)，一次性后台团队执行的当前证据见上述实施记录。

## 实施前的代码观察

| 层 | 查明的行为 | 对并行的影响 |
| --- | --- | --- |
| Python RPC | `sidecar.py::serve_stdio` 为请求建立独立 asyncio task，输出逐帧加锁 | 不会把两个 JSON 帧交错写入；不是全局串行执行器 |
| 运行 | `_active_runs`、`_run_sessions` 以 run ID 索引，每次受理创建独立 `ModelDrivenAgent` | 不同会话可以同时等待模型或工具 I/O；不是多 CPU/GPU 进程 |
| 会话顺序 | `_hydrate_conversation` 和 `_execute_run` 共用每会话的 asyncio lock | 相同会话按序读取前序结果；第二次受理可能等到前一次释放锁，不能把 RPC 已发出当作模型已开始 |
| 上下文 | `ConversationStore` 绑定 session + server + epoch，运行只读此前 ordinal；checkpoint 带 run 绑定 | 同会话连续处理可继承结果，不同会话不会共享完整聊天；全局/服务器记忆是显式共享来源 |
| 取消和审批 | stop 指向具体 run；approval 以 approval ID + run ID 查找 | 可以只取消一个运行；批准某任务不能解锁另一个任务 |
| 前端 | `useAgentRun` 只有一个 `RunLifecycle`、一组 entries、identity、pendingAdmission、approval 状态 | 目前不是可切换的后台多会话管理器 |
| 回复落库 | `useChatSessions.recordAssistantMessage` 读当前活动会话 ref | 若直接解除切换限制，旧运行完成时可能写入新会话，必须先修改归属 |
| 导航与草稿 | `AgentPanel` 和 workspace `agentBusy` 保护切换；scopeViews 按服务器缓存视图；草稿另有会话键 | 目前同一服务器的多个正在执行的会话没有完整独立视图所有权，不能只删除 busy 判断 |
| 单运行工具 | `ModelDrivenAgent` 绑定 `parallel_tool_calls=False`，按 call_index 执行 | 后端多运行并行不代表单个运行内部工具也并行 |
| 实际文字流 | 模型节点使用 `ainvoke`；sidecar 成功后把最终文本分片发送 | 目前并非模型 token 到达即展示；需要 provider stream 接入才能形成真正增量体验 |
| 资源和计费 | 有单运行步数/时长等预算；尚未找到统一模型并发许可、跨运行服务器变更锁或 provider 请求用量账本 | 扩大并发前需要这些宿主边界，现有数据库 mutex 不等于服务器操作锁 |

主线依据：`apps/desktop/src/features/agent/{AgentPanel,useAgentRun,useChatSessions}.tsx/ts`、`stores/workspace-store.ts`、`agent/src/yukinal_agent/{sidecar,model_agent,conversation_store}.py`、`native/desktop_host/src/ipc_router.cpp::{agent_run_command,configure_sidecar}`。原生宿主会再次核对会话服务器范围，并保持 run ID 事件投递，但跨窗口运行接管和恢复仍需统一协议。

## 对话与看板的交互

看板设为左侧独立入口，在中间工作页固定四列；窄窗口在看板内部横向滚动，左右栏宽度保持不变。团队右侧保留“团队 / 值守 / 配置”。中间看板绑定打开时的服务器，后续导航不会悄悄改变它的范围；可显式选择全部服务器。

| 分组 | 任务与运行含义 |
| --- | --- |
| 待处理 | 尚未开始的已存任务、正在受理的运行；未来加入因资源不足排队的任务 |
| 进行中 | 调查、执行、验证，以及模型分析或工具调用 |
| 待确认 | 等待用户选择或运行等待批准 |
| 已结束 | 成功、失败、停止、过期、中断，各自保留实际结果标签 |

卡片采用 16:9 横向比例，标题优先，状态、服务器和已知团队作为辅助信息；点击通用属性窗口查看完整目标、验收条件、证据和可打开的产物。没有保存团队归属的旧任务显示“未记录团队”，不会根据文字猜一个团队。任务和运行以 task ID / activeRunId 且服务器一致进行关联；一次模型回答结束不能把仍待验证的任务标成完成。

当前看板读取最近最多 100 项持久任务，加上本窗口已知运行；运行投影随 UI 生命周期存在。数据读取失败显示同步错误，不能伪装空数据；没有后台运行清单时，只描述“本窗口”执行状态。下一阶段需要服务端按服务器/团队/状态分页，以及可恢复的主责团队字段。卡片不提供拖拽强行改变执行状态，等待/执行/验证/完成必须来自实际工作流事件。

多会话正式接通后，对话标题旁显示可横向滚动的短会话标签，每项只放名称和阶段点；任务记录仍负责搜索和归档。不同服务器的会话可同时打开，同一服务器可有多个目标。新建会话不覆盖旧草稿；关闭标签仅关闭视图，停止任务必须有明确操作。后台批准进入待确认中心，显示目标与变更摘要，点击回到原对话；不反复强抢当前输入焦点。

## 描边反馈规则

服务器行、对应工具入口、工作页标签和打开的工作页面板使用同一层细描边。颜色跟随实际操作团队，1.8 秒一轮缓慢呼吸；工具返回后保留 1.8 秒渐隐余光，让快速动作也能被感知。队名说明谁在做事；同一区域多个团队同时操作显示数量，提示中保留每项信息。

提示以 `(runId, callId)` 独立记录，必须匹配事件中的实际服务器与工具类别。宿主工具不继承对话选中的服务器；两个并行调用中的一个完成、取消或过期，不清除另一个。等待批准停止“正在操作”描边，批准入口以后使用静态待确认标记；失败和中断结束当前操作。减少动态效果时使用静态描边，不改变按钮的可读性和点击区。

模拟模式有明确标注的并行反馈按钮，仅演示蓝队读日志与黄队读文件；不创建任务、不调用模型、不连接服务器、不记用量。模拟演示和真实事件复用视觉层，但不共享执行授权。

## 运行与视图分离

正式实现应增加一个宿主执行目录，加一个窗口级事件归约器，避免每个可见聊天组件各订阅一份并直接写当前状态。

```text
用户消息 -> 持久 admission -> 宿主执行目录 -> 资源队列 -> 模型/工具
                                   |              |
                                   +--- run 事件 ---+
                                           |
                                 窗口事件归约器（一次订阅）
                                   /       |        \
                               原会话    任务看板   操作描边
```

每次受理冻结：session ID、task ID、父运行、主责/协作团队、服务器、范围修订、角色与模型、批准策略、上下文版本、预算。导航状态不参与后续工具授权。会话视图保存草稿/附件/滚动/展开位置；运行保存文本增量/工具卡/批准/错误/用量；不再依赖全局 agentDraft 或一组 replyIdentity 承载全部会话。

完成回调必须写显式 session ID，并使用稳定 assistant message ID / run ID 去重。两阶段 admission 沿用 message ID + run ID 的幂等约束，重试不额外插入用户消息。恢复记录时先拿宿主 active run 清单和事件游标，再接增量；旧任务晚到事件只能更新原运行，不能污染当前对话。

事件增加工作区、会话、任务、运行、父运行、团队、服务器、call、序号和 event ID。归约器核对归属、去重、拒绝终态回退；重复帧不能重复追加文本、批准、描边或用量。原始 provider SSE 不直接成为 UI 信任边界，需要宿主规范化、限制长度并校验。断流后按宿主快照恢复；无恢复证明时显示中断，不自动重放效果未知的写工具。

本轮补上了 UI 运行的 session/task 绑定、当前对话阶段条按 session 过滤，以及多调用描边容器；仍保留原有单会话运行保护。下一步应迁出 `useAgentRun` 的所有运行状态和订阅，再开启会话切换，不能先放开按钮再补归属。

## 有界并行调度

初始建议上限是配置起点，尚未做真实供应商或本地模型容量测试：前台模型请求 2 个、后台 1 个、全局最多 3 个；每个 provider 默认 2 个，本地模型默认 1 个。用户可按实际能力调整。许可应包围一次真实模型请求，不能让等待人类批准的任务占用模型槽位。排队状态写清“等待模型名额”“等待此服务器变更完成”，不得伪装分析中。

调度至少同时检查：会话主序列、父任务依赖、全局/供应商并发许可、服务器变更锁、批准有效性、预算预留。前台优先但为后台保留名额，避免“盯着”永远饿死。HTTP 429/临时错误用服务端重试时间和抖动退避，不重放完整任务；取消排队中的任务撤销队列项，取消正在请求的任务只中止其请求和相关子项。

同服务器的变更先使用保守独占锁：文件写入、安装、重启、任意 exec 不能靠不同工具名称绕过。只读采集允许有限并行，但涉及变更前后的一致性判断必须核对快照版本或在变更后重采。后续才细化资源锁，例如文件路径、systemd 单元、容器和包管理器；数据库迁移或未知 exec 保持整主机独占。不同服务器可以并行变更，前提是分别满足授权和预算。

批准等待前释放执行许可与服务器锁。批准后重新排队、检查输入指纹、目标修订、计划与证据时效，拿锁后再次校验；证据失效需重新规划或再次确认。超时、断线或取消导致写操作结果未知时先标记待核验，不能因为租约到期就执行第二遍相同变更。

锁和执行权属于宿主服务，通过数据库唯一约束、租约和 fencing version 覆盖多个窗口与进程；React store、单 Python 进程内的 Lock 和 SQLite 内存写锁都不足以保证服务器动作互斥。

## 多团队处理一个目标

部署环境由黄队主责，蓝队读现状与运行指标，紫队验证交付结果，白队核对有争议的权限边界。只有输入、权限和依赖满足的只读分支先并行；安装和配置变更按依赖图执行。不能默认七队全开、全量广播同一聊天或把全历史复制给每个模型。

子运行拿到有限目标、证据引用、当前范围、可用工具和子预算；主任务预算覆盖所有子项。主责团队负责汇总证据与最终答复，子运行输出作为有出处的结果卡，不直接向用户主消息序列插入多个冲突的最终答案。团队身份不扩大工具能力，子项授权不得超出父项；父任务取消只作用于它拥有的子项，不影响无关会话。

启动协作分支前给出可见的分工与范围；普通只读分工可在既有授权内执行，扩大范围或执行变更仍走既有批准流程。共享同一份具有相同权限与采集参数的只读证据可以避免重复 token，但不同租户、权限和过期证据不能混用。

## 统一心跳与 token 口径

30 秒固定 heart 仍是唯一到期扫描点，频率通过拍数表达。每拍只 claim 到期工作，`(scheduleId, slot)` 唯一；任务进入有界队列后再分散调度，并非整拍把所有模型同时唤醒。任务尚在执行时合并下一拍，不累计一串补跑。暂停/撤销在领取与真正发出请求前均核对。

静态规则、无变化快照、去重和聚合不调用模型。心跳没有到期模型工作时 token 为零；具体运行没有用量报告时状态为未知。每次实际 provider 请求独立 request ID，关联 run / parent run / task / schedule / session / team / server。父任务报总账时按 request ID 集合求和，不能把父项总数再与子项相加。请求取消后仍可能有供应商计费，迟到 usage 回填原请求。

模型开始前预留预算，结束后对账；异常重试另建实际请求记录。当前 run 累计 usage 是展示投影，不是 provider 请求账本。完整并行上线前需要先实现请求账本、未知用量标记和预算预留，避免把多任务的快照当作新增费用叠加。

## 接通顺序与验收

1. **本轮基础**：并行调用提示、描边与余光、看板、session/task 绑定；继续保留运行期间切换保护。
2. **多会话闭环**：运行管理移出可见面板；显式 session 落库；独立草稿/滚动/审批；两段对话同时只读执行，切换不丢流，取消一段不影响另一段。
3. **资源与账本**：宿主运行清单、模型许可、服务器变更锁、事件回放、请求级账本与预算；跨窗口恢复并验证相同动作不重入。
4. **协作与值守**：父子依赖图、授权收窄、统一 heart 领取、规则异常才唤醒团队；先读后写，合并证据并验证结果。

本地并发实验使用测试模型而非真实供应商：两个不同会话必须在任一个释放前同时进入模型节点，两个服务器的上下文互不包含对方提示；取消其中一个后另一个仍继续并完成。既有同会话排队测试另行验证前序结果继承与重置保护。UI 测试覆盖两运行同 call ID、同运行多 call、宿主空目标、单项取消、迟到/重复结果、usage 去重、任务/运行合并和终端保留。

真实供应商限流、本地模型显存并发、真实主机变更互斥、后台运行跨窗口恢复、完整 provider SSE 目前没有运行证据；后续分别按对应能力验收。

本轮验证结果：345 项桌面测试、13 项 Python 会话测试、类型检查、生产构建通过。真实窗口核对紧凑看板、中间四列看板与双队描边；浏览器动态取样确认呼吸确实变化，并检查紧凑布局、筛选、卡片展开和产物跳转。窗口材料见 [设计系统验收](./ui-design-system.md#看板与并行反馈增量验收)。
