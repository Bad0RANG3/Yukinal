# 产品定义

## 一句话定位

Yukinal 是以 AI 执行为主、以运维工作区为观察和接管入口的服务器运维桌面应用。用户提出需求与想法，Agent 使用已经配置的模型、内建工具、MCP 工具和受控 SSH 能力，对用户添加的服务器调查、调用命令、修改配置并验证结果；运维工程师随时能看清服务器状态、实际执行与失败原因。

这描述的是**目标产品**。当前工作树已有受控命令、持久任务步骤、文件传输和运维工作区的第一轮实现，但真实 Provider/MCP/SSH 工作流、原生桌面传输和完整安装版验收仍未通过。具体实现状态、施工顺序和验收证据见[目标架构与施工交接](./architecture-and-build-plan.md)。

## 服务谁

首要用户是管理少量到多台 Linux 服务器的独立开发者、运维工程师和小型技术团队。用户负责添加服务器、核验主机身份、配置 Provider/MCP、指定目标及委托范围；AI 负责在授权范围内把目标分解为操作、调用工具、读取反馈、修复或交还问题、验证结果。运维工程师使用可视化工作区查看健康、服务、日志、文件与任务进度，必要时批准、停止或从终端手动接管。

用户不应为了让 AI 工作而先学习内部工具名、手工写 `ChangePlan` 或把每一步复制到终端。输入一个清晰目标后，系统应展示 AI 的实际进展，并且只在目标不明确、能力缺失或授权边界要求时打断用户。大规模主机编排、多人共享权限和全天候无人值守仍需单独定义与验收。

## 三条核心用户路径

| 路径 | 用户起点 | 成功画面 | 失败画面 |
| --- | --- | --- | --- |
| 目标驱动的 AI 运维 | 选中已添加的服务器，输入“检查 502 并修复配置”等目标 | Agent 发现可用工具，读取证据，按权限调用命令/配置工具，验证远端状态并报告实际结果；用户可追溯每步 | 工具不可用、权限不足、命令失败或结果未知时停止假成功，说明已做的事和下一步 |
| 运维可视化与接管 | 打开服务器工作区或从任务跳转 | 看到来源、时间和新鲜度明确的健康、服务、日志、文件与 AI 任务状态，可快速定位异常并人工接管 | 断连、采集失败和旧数据明确标注，不用缓存值冒充实时状态 |
| 本机↔远端文件工作区 | 从 Windows/macOS/Linux 文件管理器拖文件，或在工作区浏览/预览文件 | 通过拖放或选择器上传、下载文件及目录，显示进度、冲突和完整性核验；预览与完整传输互不混淆 | 取消、断线、磁盘满、权限不足或文件变化时保留正确原文件，标出失败与待清理内容 |

这三条路径共同决定下一阶段的优先级。已实现的小型 Agent 文件编辑与备份/恢复仍是配置变更的辅助能力；它们不能替代用户要求的直接文件传输。

## 产品边界

- Agent 通过宿主提供的工具操作指定服务器，不能直接持有 SSH 凭据、把聊天文本灌进终端或依赖用户手动执行它写出的命令。
- 开发/预发布环境中，明确委托范围内的读取与普通结构化变更应能连续自动完成。任意 shell 命令默认逐条批准；用户也可对单个非生产任务一次性授予有期限和预算的命令权限，让 AI 连续执行并验证。生产、未知环境和关键危险操作仍按具体目标与输入等待批准；委托不能解除宿主核验。
- MCP 是工具来源，不能因为描述或自报风险就获得服务器权限。外部 Provider/MCP 会接触被送出的有限上下文，其数据边界应在设置与执行时可见。
- 可视化工作区负责观察、理解和接管；权限决策在 Agent 权限引擎与 Rust 宿主，状态采集本身不得引发远端变更。
- 手动文件传输从 UI 经 Rust 宿主到 SFTP，不穿过模型上下文；Agent 的文件修改仍走独立的工具审批。预览可截断，上传/下载必须完整。
- 停止只能阻止后续步骤；已经送到远端的命令可能已执行。结果未知时需要核对，不能写“已回滚”或“已成功”。
- 卸载始终保留数据库、设置和凭据。若未来支持删数，应设计成独立、明确、可验证的用户动作。

## 实施优先级与产品验收

| 顺序 | 工作重点 | 可交付证据 |
| --- | --- | --- |
| P0 | 受控通用命令和目标驱动工具调用链；可重置服务器上的真实 Agent 工作流 | [施工文档](./architecture-and-build-plan.md#验收条件发布必须逐项通过) A1–A4，包含真实 sidecar、Provider、SSH/MCP 与宿主审批记录 |
| P1 | 状态工作区、任务进度、文件双向流式传输、原生拖放和预览 | 同页 O1–O2、F1–F4，在 Windows/macOS/Linux 安装版逐项操作 |
| P2 | 干净环境发布、签名/公证、长期稳定性与后续扩展 | 同页 R1，结合[交付与发布](./release.md)的安装包和运行时证据 |

需求和验收以可观察行为为准：目标服务器是否真的变化、状态是否真实、文件是否逐字节一致、失败能否被识别与处理。没有真实用户基线时不虚构节省时间或自动化比例。
