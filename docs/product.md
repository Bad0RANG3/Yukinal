# 产品定义

## 一句话定位

Yukinal 是面向独立开发者和小型技术团队的安全 AI 服务器运维工作台：把服务器现场、AI 排查、可审批的变更和事后追溯放在一个桌面应用里。

产品承诺的是“帮助人更快地理解并处理自己管理的服务器”。AI 可以收集有界证据、提出判断和操作计划；真正的远端执行由本地宿主按目标、权限和用户授权决定。终端保留给用户直接操作。

## 服务谁

当前的首要用户假设是同时负责开发与少量 Linux 服务器维护的人，以及没有专职运维团队的小型技术团队。他们已经有 SSH 访问权，愿意核验主机身份，希望在故障时快速看清状态，并能知道一次修改是谁批准、执行了什么、结果如何。这个假设仍需通过真实用户试用验证。

当前阶段主要覆盖用户主动管理的服务器。产品尚未建立大规模主机编排、多人共享权限和全天候无人值守服务的交付证据。

## 要解决的三个任务

| 任务 | 用户应得到的结果 | 完成标准 |
| --- | --- | --- |
| 只读诊断 | 连接目标主机，看到健康、服务和日志的来源与时间，得到有证据的下一步建议 | 缺失数据明确显示为缺失；诊断不触发变更 |
| 受控变更 | 查看目标、操作内容、风险和变更前证据后决定是否批准 | 拒绝、取消和失败不会显示为成功；执行后有验证与活动记录 |
| 文件恢复 | 在受限文件修改前保留可识别的备份，出现问题时找到恢复入口 | 并发改写、备份失效、权限不足等情况明确拒绝或提示下一步；恢复是独立授权动作 |

这三条路径共同决定下一阶段的优先级。新能力应证明能缩短其中一条路径、降低误操作风险，或让失败更容易处理。

## 产品边界

- Agent 不是远端 shell，也不拥有 SSH 凭据。用户可以直接使用终端；Agent 的工具调用走独立的审批与审计链。
- 只读证据和模型结论不是一回事。模型可提出假设，界面应标明证据来源、采集时间、截断或不可用状态。
- 停止运行只能阻止后续步骤；已经送达远端的操作可能仍需人工核对。备份和恢复也不能保证远端系统级事务。
- 自动委托只在代码允许的目标环境、任务模式和风险范围内生效。生产环境的危险操作仍要求逐项确认。
- MCP 和模型 Provider 是扩展能力；它们必须遵守本地目标解析、数据边界和授权规则。
- 卸载只移除 Yukinal 应用本体，始终保留数据库、设置和凭据数据；卸载器不提供递归删除数据的捷径。若将来支持删除数据，应设计为独立、明确、可验证的用户动作。

## 如何决定下一项工作

| 顺序 | 工作重点 | 完成证据 |
| --- | --- | --- |
| P0 | 干净安装、真实 SSH 与模型端点验收；消除最终用户必须另装 Node.js 的安装门槛 | 目标平台安装记录和三条路径的脱敏验收报告 |
| P1 | 补齐错误提示、停止/恢复、旧库升级和桌面端到端测试 | 故障注入后状态可解释，重启后记录可追溯；2026-09-30 本机当前 Windows release 构建通过原生启动冒烟，窗口与 5 个主导航按钮均可访问，Agent acceptance fixture 已覆盖验证失败后批准/拒绝恢复的不同结果，native Host RPC 已验证 evidence 在真实 SQLite 中跨 `AppState` 重启可读；真实 sidecar 进程、SSH/SFTP 和桌面 UI 业务路径 E2E 仍未完成 |
| P2 | 根据真实用户试用决定 Provider、MCP、自动化、监控和性能投入 | 明确的使用频率、失败案例或性能基线 |

每项工作写清目标用户、起点、成功画面、失败画面和可复现的验收条件。成功指标优先使用三条任务的完成率、完成时间、误审批/重复执行事件数，以及失败后用户能否找到下一步。尚未收集真实用户基线时，不写虚构目标数值。
