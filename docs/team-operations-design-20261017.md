# Yukinal 团队执行与持续值守设计

对话负责表达目标、看进度和作决定；团队负责带着明确目标、服务器范围和工具权限推进任务；后台心跳负责调度持续任务。用户始终能看到谁在处理哪台服务器、正在做什么、何时需要介入，以及实际已上报的用量。

本文定义产品交互和后续运行机制。2026 年 10 月 17 日的界面实现及尚未接通的链路列在末节，不能把设计中的能力当成已运行的后台服务。

## 团队工作台

左侧入口由 Agent NIST 改为“团队”。颜色表示本产品的职责划分，不将这套命名表述成 NIST 的正式团队标准。保留现有七队、角色 ID、本机角色配置和模型绑定。

| 团队 | 主要任务 | 可交付结果 | 常见触发 |
| --- | --- | --- | --- |
| 黄队 | 环境部署与系统建设 | 部署计划、授权变更、验证和回滚记录 | “给这台服务器部署环境” |
| 蓝队 | 运行安全与持续值守 | 健康检查、异常证据、事件分级 | “帮我盯着”“检查服务异常” |
| 紫队 | 检测验证与防护复测 | 变更前后对比、修复验证、检测覆盖 | “确认刚才的修复有效” |
| 白队 | 范围、权限与风险控制 | 范围约束、审批节点、停止条件 | 目标不明、权限不足、危险变更 |
| 绿队 | 监测、告警与响应建设 | 指标、日志、规则与响应流程 | “建立一套告警” |
| 橙队 | 漏洞修复与安全开发 | 漏洞修复、代码改进、回归依据 | 已确认漏洞需要工程修复 |
| 红队 | 明确授权范围内的攻击验证 | 可复核攻击路径与影响证据 | 用户明确要求授权测试 |

“服务器被攻击了，帮我检查”交给蓝队；红队需要明确的攻击验证意图。每个目标先选择一个主责团队，必要时交接给一个具名协作团队，避免每次请求默认启动七个模型。

右侧保留现有列宽，分成三个视图：

- **团队**：当前协作、七个紧凑职责行。一次只展开一队，展开显示交付范围与“在对话中使用”，不堆叠全部角色说明。
- **值守**：当前服务器的计划、频率、状态、最近结果、暂停与恢复；统一心跳和实际用量单独成组。
- **配置**：角色提示词、模型绑定与记忆库入口，保留现有编辑能力。

“从对话中使用”选择团队，不自动发送、不覆盖草稿。显式 @ 或手动选择优先于自动匹配；提供恢复自动匹配的入口。阶段、风险和未知结果必须同时有文字，不能只靠颜色表达。

## 对话中的任务闭环

### 一次部署

用户说“给这台服务器部署 Node 环境”后，先生成绑定服务器的任务卡，显示“黄队 · 部署环境”。目标来源按显式 @ 服务器、当前选中服务器处理；多个候选主机时先消除歧义，不能根据相似名称猜测目标。

执行顺序为：解析目标 → 校验已登记连接与主机身份 → 读取环境 → 给出简短计划 → 按现有权限规则执行 → 验证 → 返回结果。已保存且有效的凭据可复用；凭据缺失、主机指纹变化、需要提升权限时进入明确的用户决策节点。角色名称不扩大权限。

任务卡在流式更新中依次呈现受理、连接、检查、执行、验证和结果。工具结果提供原始证据入口；失败卡包含已发生的效果、尚未完成的步骤和恢复方式。“部署成功”必须有相应版本、服务或探针验证，不能用命令返回 0 代替全部验收。

用户选择“继续盯着”或在最初请求中明确要求持续值守，才创建持续计划；部署完成不默认附加无限期模型任务。

### 持续值守

“帮我盯着这台服务器，有异常告诉我”产生绑定服务器、目标、检查项、频率、通知策略和预算的计划。默认建议每 5 分钟检查，变化或异常才通知。频率可修改为心跳的整数倍；“检查一下”只执行一次。

计划确认信息嵌在对话卡中：`蓝队 · 值守 / 每 5 分钟 / 异常时通知 / 暂停`。明确提出持续监控已提供创建计划的意图；范围和频率可用可见默认值，但需要付费模型或修改服务器的额外权限仍遵循现有规则。关键词匹配仅用于界面路由建议，不作为持久化计划或执行命令的授权依据。

对话持续显示当前服务器已登记的值守计划，点击直接打开右侧“值守”。正式后台接通后，状态需要区分等待下一拍、检查中、等待模型、等待批准、已暂停、宿主离线、检查失败和已停止；不能把“已启用”当成已经在执行。

异常与原任务、服务器和对话关联。正常且无变化时静默；出现新的有意义变化、失败或需要用户决定时追加一条事件。刷新既有状态不重复追加对话消息。暂停阻止后续调度；正在执行的操作单独提供停止，并展示取消后可能已发生的效果。

## 流式执行与可感知操作

对话只展示可公开的简短计划、工具动作、结果与依据，不要求输出模型的隐含推理。长日志、文件和完整证据沿用中间工作页，对话保留宏观控制位置。

沿用现有 `agent.started / thinking / text / tool_call / tool_result / waiting_approval / completed / failed / usage` 事件，后续统一在宿主事件信封内补齐 `eventId、seq、at、runId、taskId、scheduleId、teamId、serverId、callId`。这些字段来自运行记录，不能从模型文字反推。各运行按序重放，事件重复抵达不重复落账或生成消息；多个运行交错时按 runId 隔离。

| 真实状态 | 用户看到的反馈 |
| --- | --- |
| 已受理或规划 | 对话上方显示队名、阶段与目标 |
| 正在调用工具 | 对应服务器行和文件、日志、服务或终端入口显示队名及轻微呼吸点 |
| 工具快速返回 | “刚刚”提示保留约 1.8 秒，完整结果留在对话与记录中 |
| 等待批准 | 停止操作呼吸，明确显示“等待批准”与具体变更 |
| 结束、失败、中断 | 停止运行提示，保留实际结果与恢复入口 |

提示不自动切换用户正在看的页面、不抢焦点。减少动态效果偏好下使用静态点和文字。模拟模式的“预览操作反馈”显式标注演示，不建立任务、不连接主机、不记录虚构 token。

当前实现展示最近一次工具提示；后续并发执行应按 `(runId, callId)` 保存多条动作，同一入口合并为队名与数量，详情列出独立调用，避免一个调用的结果关闭另一个仍在执行的提示。

## AI 如何理解用户当前操作

使用语义化的界面上下文：当前栏目、选中服务器 ID、服务器视图、可见工作页的类型与绑定服务器，以及最近一次明确点击或键盘聚焦的入口。只记录这些已列举的语义，不采集鼠标轨迹、输入框草稿、终端正文、密码或任意 DOM 文本。

发送消息时冻结一次上下文；重试同一受理请求时复用该快照，避免用户切页造成原任务目标漂移。最近入口的注意力有效期为 120 秒。后续长任务可在工具边界读取新的界面参考，但不能据此自动扩大任务范围。普通点击不触发模型调用。

上下文明确标注“仅表示当前视图，不构成操作授权”。例如工具工作页绑定 B，而当前任务显式绑定 A，AI 可以知道用户在看 B 的日志，工具仍只能以任务范围中的 A 为目标；涉及切换时需要明确任务意图。服务器状态、权限和工具输出继续以宿主校验结果为准。

后续提供一个可展开的“当前上下文”入口，显示将随下一条消息传入的范围，并允许关闭界面参考；任务必需的服务器绑定和权限校验始终保留。

## 工具注册与执行链

复用现有 ToolSpec、风险等级、参数校验、目标范围、批准、执行记录和 artifact 管线。团队引用工具组与能力标签，不能各自复制一套同名工具或通过提示词绕过调用规则。

| 能力组 | 现有工具示例 | 约束 |
| --- | --- | --- |
| 连接与环境 | 已登记连接、server.info、环境快照 | 先通过连接和主机身份校验 |
| 只读观测 | server.logs、server.services、docker.ps、docker.logs、ssh.service_status、ssh.disk_usage | 时间窗、输出大小与敏感字段过滤 |
| 文件变更 | filesystem.write、edit、backup、restore | 精确路径、变更预览、备份与批准 |
| 运行变更 | package.install、systemd.restart、docker.restart、server.exec | 明确影响、权限、幂等性与恢复方案 |
| 任务编排 | investigation.plan、持久任务与 schedule 接口 | 绑定目标、预算、批准来源和去重标识 |

执行结构统一为：接收意图 → 绑定范围 → 团队路由 → 读取事实 → 生成计划 → 权限判定 → 工具执行 → 保存证据 → 验证结果 → 汇总或登记值守。每一步可暂停、取消与审计。缺少能力时返回具体缺口，不能将角色生成的文字显示为已经执行的命令。

每个工具描述补齐输入输出 schema、能力组、风险、前置条件、目标、超时、幂等键、预期影响、可恢复性和证据输出。工具失败分成可重试读、结果未知写和确定失败写；结果未知的写操作先核对效果，禁止自动重复执行。

## 服务器安全守卫

“安全墙”首先是一组可解释的检查规则、基线和升级策略。真实操作系统防火墙的读取或修改作为独立工具能力接入；不能用一张风险卡表示已完成隔离或配置修改。

基础观测覆盖资源压力、磁盘剩余与增长、服务退出与重启、SSH 认证异常、可确认的端口暴露和防火墙配置、证书有效期、备份新鲜度。缺失字段、采集失败、过期快照和无基线分别显示为未知或检查失败，不能判定为健康。阈值随服务器与规则配置，展示对应时间窗和依据。

| 事件 | 升级方式 |
| --- | --- |
| 短暂波动 | 记录采样，按持续时长与迟滞规则确认，避免反复告警 |
| 持续资源或服务异常 | 蓝队读取关联证据，生成可执行处置建议 |
| 现有采集不足 | 绿队提出观测建设方案，安装组件仍需相应权限 |
| 已执行修复或关键防护变化 | 紫队独立复核，保留变更前后依据 |
| 可能影响数据、网络入口或生产服务 | 白队明确影响与批准节点，再交具体团队执行 |
| 明确请求攻击验证 | 红队在给定目标和范围内执行，与持续值守授权分开 |

告警以服务器、规则、证据指纹和事件周期去重，设置冷却时间与恢复条件。已确认事件持续期间更新原事件；恢复后通知一次。检查失败和数据陈旧本身也需要可见，不能在无数据时保持绿色。自动修复仅限用户预先批准的具体动作、范围和预算，不能把“盯着”解释成任意部署或封禁权限。

## 统一心跳与后台调度

基础心跳采用 30 秒，按 UTC Unix 时间对齐。`slot = floor(now / 30s)`；任务频率为 `everyN = ceil(intervalSeconds / 30)`。例如 5 分钟是 10 拍，15 分钟是 30 拍。61 秒归为 3 拍，界面必须显示实际 90 秒，不能声称仍每 61 秒执行。

所有持续任务由宿主或常驻工作进程的一个调度器检查，不在每张卡片中各自启动执行计时器。UI 的统一刷新时钟只同步状态和用量；窗口休眠、隐藏或关闭不能改变后台计划的时间语义。没有常驻宿主时明确显示“宿主离线，未执行”，不承诺退出应用后仍在监控。

每一拍先选出到期任务并在数据库事务内 claim，唯一键为 `(scheduleId, slot)`，附租约、执行者和 claim 时间。多个窗口或进程争抢时只允许一个工作者获得执行权。存在尚未过期的运行时不重入；暂停、撤销与范围变更在 claim 和真正执行前再次校验。

错过的拍合并到当前一次，不补发一串模型请求。崩溃后的租约过期先核对已有结果；只读任务可重新采样，效果未知的写操作不能按超时直接重放。已发生的读写和 token 保留原运行归属。

同一拍的任务先按风险和优先级排队，设置全局、模型连接和服务器并发上限、冷却和预算。相同服务器、相同采集参数及权限范围的只读快照可以共用一次采集；不同权限的内容不能复用。模型请求分散进入队列，避免整拍同时发出大量请求。

每拍先执行确定性采集、基线差异和规则判断。没有变化且规则正常时更新采样时间，不唤醒模型；变化、异常、人工请求或配置的周期总结才生成模型工作。状态比较、去重、权限判断和最终状态提交都由宿主实现。

## token 与费用记录

统一刷新点能统一展示口径；准确计费仍需要实际请求账本。正式账本以 provider request ID 或宿主 request ID 唯一，每次模型请求记录 run、task、schedule、team、server、模型、时间和 usage 来源。重试产生新的实际付费请求时单独记账，重复接收同一结果时不再增加用量。

累计 usage 快照以同一请求的最新有效累计值替换，不能逐事件相加。乱序快照不减少已确认值。输入和输出分别统计；缓存命中与缓存写入若属于输入子集必须单列说明，不能再次加入总输入。未上报为未知，推算值与供应商实际值分开；缺少价格或 usage 时费用显示未知，不能当作 0。

心跳只对请求账本做聚合快照，显示本拍、今日、任务、团队和服务器口径。心跳、规则读取、共享采集本身不产生模型 token；可另行记录执行耗时和网络成本。父任务、子团队与计划通过同一 request ID 归集，汇总不把父子重复相加。

调用前预留预算，调用后按实际 usage 对账。超预算时暂停新的模型调用、保留无模型规则观测并提示用户；无法获知真实 usage 的供应商不能承诺精确硬上限。已有运行的迟到 usage 仍回填原记录。

当前共享契约将 `agent.usage` 定义为单次 Agent run 的累计 input/output。此轮界面按 run ID 去重并取单调累计值，随心跳汇总，明确标为“本窗口已上报用量”。它不是持久账本，也未补造 Python 后端尚未发送的 usage。后续多团队、多请求并发前，需要把 provider 请求级 usage 接入宿主持久账本，再向 UI 发聚合事件。

## 当前实现与接通顺序

| 范围 | 当前结果 | 后续必须接通 |
| --- | --- | --- |
| 团队工作台 | 看板、团队、值守、配置四视图，紧凑职责、原模型绑定 | 持久任务的主责与协作团队分配 |
| 对话路由 | 按目标自动选现有角色，@ 和手动选择优先 | 多阶段团队交接、子运行和证据交接 |
| 操作反馈 | 按 run/call 隔离的队名、描边呼吸、快速返回余光，匹配实际服务器与工作页 | 宿主事件去重、持久回放与后台运行接管 |
| 界面感知 | 发送时传入经过白名单的语义快照，重试冻结 | 可见上下文开关与长任务边界同步 |
| 持续值守 | 读取已有计划与结果，状态同步，连接已有暂停恢复接口 | 解析持续意图并持久创建计划、宿主 worker 执行与异常唤醒 |
| 心跳 | 一个对齐时钟刷新 UI 状态与运行用量 | 宿主单调度器、数据库租约、幂等 claim、崩溃恢复 |
| 用量 | 本窗口累计事件去重，未知不算零 | provider 请求账本、持久化、缓存口径、实际费用与预算预留 |
| 连接和安全 | 复用现有工具与批准边界 | 完整桌面连接与快照 IPC、安全采集规则、事件升级执行 |

原生 `investigation.schedule.tick` 目前只调用数据库 claim，到期运行还缺少完整消费和执行工作者。桌面连接与部分服务器 IPC 的迁移缺口见 [运行边界](./ops-workbench-comparison-20261017.md)。在这些链路接通前，不能宣称“说一句就已经自动部署并后台盯守”。模拟数据中的已有结果也不能作为真实服务器执行证明。

后续实施按可验收的闭环推进：先补真实连接和只读采集，再把一个任务从对话完整流式执行并验证；随后接入宿主心跳、规则值守和暂停恢复；最后补多团队交接、请求级用量与预算。每阶段保留同一套任务、事件、权限和证据记录。

验收至少覆盖：显式服务器与可见工作页不同、同一消息重试、快速工具返回、批准等待、失败与侧车重启、多个窗口争抢同一拍、休眠后恢复、未知写结果、无 usage、迟到 usage，以及暂停后不再产生新调用。真实部署与持续任务需要真实主机和后台运行证据，构建成功不能替代这些验收。
