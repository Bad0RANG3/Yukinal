# 下一阶段实施计划：可继续推进的边界与限制

> 状态：现行实施路线。盘点基于 2026-09-28 的 `main`（`5a5c065`）。[当前限制](./limitations.md)记录现状，[版本与发布历史](./changelog.md)记录已完成的变化，[架构决策记录](./adr.md)约束授权和信任模型。本文是待办与验收方案，不表示已经实现。

## 先定顺序

已完成的限制放宽（ADR 0072–0076）不再重复实施。接下来的瓶颈是安装产物、真实端点与跨进程恢复没有形成可复核的证据；继续增加工具会放大这些未验证路径。按下表推进，每项单独交付，完成后从[当前限制](./limitations.md)删去被证实解决的缺口，并把结果记入[版本与发布历史](./changelog.md)。

## A. 安装产物验收

**起点。** `scripts/package.mjs`、`scripts/check-packaging.mjs` 和 `.github/workflows/package.yml` 只保证构建与资源契约。[打包与分发](./packaging.md)已明确 Windows 的 NSIS/MSI 构建记录，安装后启动尚未验证。Node.js ≥ 24 是用户前置条件，缺失 Node 时应显示预检错误，不应把“缺 Node 也能运行”写为验收标准。

1. 在隔离的 Windows runner 上对 NSIS、MSI 各做安装、启动、sidecar 握手、退出、再次启动、卸载；在 macOS/Linux 对实际生成的目标包做同类检查。每个安装测试都从**无仓库源码、无 `node_modules`** 的位置运行，但预置受支持的 Node。
2. 另做缺失/旧版 Node 的负面场景，确认有界 `node --version` 预检给出可操作错误。检查应用退出后无遗留的 sidecar、MCP 子进程或 PTY。
3. 为每个产物保存 commit、版本、平台、包名、SHA-256、安装方式、启动/退出结果、失败日志位置；不要把凭据或远端正文放进证据包。

**验收。** 三个平台各至少一份真实安装记录；失败能区分打包、安装、运行时和环境依赖。`pnpm check` 与 `pnpm package` 仍通过。缺少某个平台时把它保留为未验证，不能用 CI 配置存在代替结果。

## B. 数据迁移与恢复演练

**起点。** `crates/database/src/schema.rs` 维护 schema，`crates/database/tests/` 有持久化测试，但发布级旧库升级、WAL 和失败恢复需要固定样本。

**进展（机制已实现，证据仍不完整）。** 迁移入口的受限备份与失败回滚已经落地：打开带待定迁移的旧库时，先用 SQLite `VACUUM INTO` 通过活动连接生成一份含未 checkpoint WAL 页的有界副本与 SHA-256 manifest，任一迁移失败时自动还原主库并删除 `-wal`/`-shm`，错误点名失败的迁移版本与保留的副本路径。`cargo test -p yukinal-database --test migration` 覆盖失败不推进版本且保留原行、副本校验值、成功升级保留上一版本副本及行、WAL-only 写入进入副本、更新版 schema 被拒绝且不留副本、全新库不产生副本。仍缺：来自真实发布版二进制的脱敏 fixture、空库/部分写入/更新版 schema 的固定样本清单与校验值，以及区分服务器配置/任务审计元数据/keychain 引用的导出导入范围。

1. 从已发布版本制作脱敏 SQLite fixture，覆盖空库、旧 schema、已有 WAL、部分写入和比当前应用更新的 schema。fixture 标明来源版本与校验值，不存操作系统凭据。
2. 在迁移入口做受限的迁移前备份和失败回滚设计；先验证原库保留、错误可定位，再实现自动保护。导出范围要区分服务器配置、任务/审计元数据和只能重新绑定的 keychain 凭据。
3. 把“旧版本 → 当前版本 → 失败后恢复”的命令与结果纳入发布证据包；迁移格式变化时新增一个固定样本。

**验收。** 每次 schema 变化有可重复升级测试；失败不丢原库；恢复后应用能读取原有任务与审计记录。不要承诺把 keychain secret 通过数据库备份跨机器迁移。

## C. 真实端点验收

**起点。** [外部验证运行手册](./external-validation.md)已有 opt-in 命令。`apps/agent/live/provider-live.test.ts` 与 `crates/core/tests/mcp_live.rs` 可复用；真实 Anthropic/Gemini、第三方 OAuth/DPoP 和远端维护仍缺证据。

1. 锁定一组可重置的测试主机、Provider 模型版本和 MCP server 版本；记录网络、认证与代理条件。凭据由环境或系统凭据库注入，不入仓库。
2. Provider 覆盖文本流、工具回填、取消、图片/PDF，以及按当前适配器声明支持的音频形状；不支持的组合应在本地明确拒绝。MCP 覆盖 stdio、HTTP JSON/SSE、OAuth 两种流程和取消；真实 server 不配合取消时记录残余副作用。
3. 在远端测试主机上走“指纹核验 → 健康/日志/服务只读证据 → 受限变更 → 验证 → 独立恢复”。断线、超时、拒绝批准和重启期间退出至少各注入一次。

**验收。** 每条场景留日期、commit、端点实现和版本、预期/实际、失败项；结论只覆盖实际跑过的组合。真实接口变化时先更新适配器/测试，再改产品承诺。

## D. 停止与恢复的运行时闭环

**起点。** `apps/desktop/src-tauri/src/commands/agent_run.rs` 和 `commands/scheduler.rs` 负责运行栅栏与启动恢复，`apps/desktop/src/features/investigations/InvestigationsPane.tsx` 当前触发部分 auto 失败恢复。已有 SQLite 状态核心测试不能替代 sidecar 进程、IPC 和窗口退出的时序。

**进展（判定与事务已移入宿主，故障注入未做）。** 自动恢复判定已从任务页移到 `commands/recovery.rs`，在应用启动、sidecar 有界就绪后执行：谓词与原来一致（`failed`、无 active run、`auto` + `goal` + `execute`、远程 development/staging、`retryable`、`attempt < maxAttempts`），命中后调用同一恢复事务（封存旧 run/步骤、使旧审批基线与观察窗口失效）再复用统一启动入口；自动启动失败退回可见 `failed`。`investigation_task_start`/`investigation_task_recover`/`agent_run_start` 抽成接收 `&AppState` 的内部函数，命令层只是包装；UI 不再持有自动判定。新增单测覆盖谓词边界与恢复事务封存旧 run。仍缺：真实 sidecar + 回环目标的受控故障注入（批准等待关窗、动作前后停止、终态帧前 sidecar 退出、恢复时旧帧迟到）与“同一副作用不因重试重复执行”的跨进程断言。

1. 用本地真实 sidecar + 回环目标建立受控场景：批准等待时关闭窗口、远端动作前/后停止、sidecar 在终态帧前退出、恢复时旧帧迟到。记录任务、步骤、工具幂等账本与远端效果四侧状态。
2. 将合规 auto 任务的恢复判定移到宿主生命周期入口；UI 只展示和发出用户动作。恢复事务必须先封存旧运行，再根据 `maxAttempts` 与既有 guardrails 决定是否新开运行。应用完全退出时不运行后台任务。
3. 在测试里断言同一副作用不会因重试重复执行，旧审批/基线/观察窗口不复活；无法确定远端结果时停在待核对状态，不显示“成功”。

**验收。** 不打开任务页也能在应用启动后处理符合条件的失败；跨进程故障演练通过；停止仍明确是栅栏而非远端回滚。若要让应用退出期间继续巡检，需要另立后台服务与授权设计，不能在这个工作包顺手放开。

## E. 用户路径与错误分类

**起点。** `apps/desktop/src/features/` 已有独立页面和局部错误处理，[历史审查](./history/project-review-and-roadmap.md)提出了三条完整路径。先跑固定场景并记录无法解释的状态，再改 UI。

**进展（分类已统一，三条端到端路径未验收）。** 新增共享 `ERROR_CATEGORIES` 词汇与 `ErrorCategorySchema`，Rust 侧 `ErrorCategory` 与 `TaskFailureCode::category()/retryable()`；`TaskFailureCode` 与 `ToolError.code` 到类别的映射写在 `packages/shared/fixtures/error-taxonomy.json`，由 TS、`crates/database` 与桌面端工具映射三处断言。可重试语义收敛到 `TaskFailureCode::retryable()`。任务页按类别展示标签与下一步，不再显示裸 `code`。仍缺：普通命令的裸字符串错误、文件恢复各失败路径的类别化，以及三条路径从干净安装环境走完的验收。

1. 服务器诊断：添加服务器、指纹核验、健康快照、服务/日志、带时间戳和来源的结论。缺失采集结果不可显示为健康。
2. 受控变更：普通聊天、只读调查、副作用任务在入口和审批卡上明确区分；显示精确目标、风险、输入摘要、变更前证据、执行结果与恢复入口。
3. 文件恢复：超限、二进制、编码错误、权限不足、并发改写和备份失效各给出具体下一步。备份清理继续逐计划审批，不引入后台自动删除。
4. 在 Rust/IPC/共享 schema 定义可操作的错误类别与可重试语义，再让 UI 按类别展示，不按英文错误文本分支。按用户实际失败路径拆分命令层，避免单纯按文件行数拆模块。

**验收。** 三条路径可从干净安装环境完整走完；拒绝/中断/验证失败不会被投影为成功；重启应用后可读到同一任务与审计历史。每个失败画面能回答“发生在哪里、现在是什么状态、下一步能做什么”。

## F. 长期运行与性能预算

用固定数据集和机器规格分别测首次可交互、sidecar 握手、十万级消息搜索、大日志/高输出终端、多个 SSH/PTY/MCP 会话，以及长时间运行后的内存、子进程、SQLite/WAL 增长。先保存基线，再从用户可见的卡顿设阈值。诊断包默认关闭，只记录阶段、耗时、错误类别与资源计数；导出前预览并扫描 secret，不收远端正文、完整命令参数或模型上下文。

**验收。** 相同环境可复测基线；阈值失败能定位到具体阶段；退出后的进程数回到基线。性能数据是指定机器和负载的结果，不写成所有平台的保证。

## 暂不作为直接实现任务的边界

| 边界 | 当前决定或前置条件 |
| --- | --- |
| 签名、公证、自动更新 | 先确定证书保管、发布渠道、产物来源与升级回滚，再做实现；可先生成哈希和发布证据包。 |
| 自定义 MCP 按请求签名、KRL signer 远程分发 | 需要服务端共同协议或可信分发根；维持当前静态配置与 DPoP 选项。 |
| MCP 取消、Agent 停止、`filesystem.edit` 并发窗口 | 外部系统不提供回滚或 SFTP compare-and-swap。继续改进检测和提示，不能宣称原子跨系统事务。 |
| 自动备份清理、自动回退、生产危险动作免批准 | 改变现有授权模型；当前路线保留逐项审批与独立恢复计划。 |
| Agent 任意 shell、无限日志、任意二进制附件、完整 CommonMark | 超出当前有界工具和渲染契约；需要明确用户任务、上限与安全评审。 |
| 应用退出期间持续巡检 | 需要独立服务、凭据和调度所有权设计；当前仅桌面进程内运行。 |
| 日志平台、自动根因分析、全局语义去重 | 属于新产品能力，先完成真实诊断闭环与数据模型验证。 |

## 每个工作包的交付规则

- 开始时写明当前代码入口、具体失败场景和用户可见结果；涉及授权/信任边界时先新增 ADR。
- 合并前运行对应的 Rust/TypeScript 测试和 `pnpm check`，外部场景按[运行手册](./external-validation.md)独立记录；无法运行的项目保留“未验证”。
- 同步更新[当前限制](./limitations.md)、[打包与分发](./packaging.md)或相关边界文档，以及[版本与发布历史](./changelog.md)。历史审计和旧实施手册只作证据，不继续追加待办。
