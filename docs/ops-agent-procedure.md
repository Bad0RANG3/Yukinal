# 运维 Agent 的处理流程与权限模型

本文说明 Yukinal 的 Python Agent 现在如何工作、能做什么，以及**哪些由代码保证、哪些是提示词约定**。
上一版本文档把「每个环境一套策略、每个动作先建计划」写成必须满足的约束；这一版按用户要求改为：
**一个权限模型、用户为结果负责、Agent 自己想办法做完**。

## 原则

1. **用户许愿，Agent 交付。** 用户描述目标，Agent 自己决定用什么手段：结构化工具优先，没有就
   用 shell。不要求用户先选任务、先建计划、或自己复制命令去执行。
2. **一个权限模型。** 不再按「开发/预发布/生产」「是否有持久任务」细分可用工具。`goal` 运行暴露
   全部注册工具，每次变更按次请求批准；`readonly` / `plan` 只暴露只读工具；「本轮不用工具」
   暴露空集。这三条是用户为本次运行做的明确选择，不是隐藏的等级。
3. **用户为结果负责。** 危险操作由用户批准后执行；Agent 不替用户反复确认，也不额外制造审批环节。
4. **代码只守它必须守的边界**：目标解析、输入校验、命令黑名单、一次性批准票据、重复调用与
   未知结果的防护。这些不因「用户负责」而取消。

## 工作方法（提示词层）

`agent/src/yukinal_agent/operations_policy.py` 的 `OPERATIONS_PROCEDURE`：

| 阶段 | 做什么 |
| --- | --- |
| 理解 | 完成时什么必须为真？哪台服务器？什么不能被破坏？能用一次读取回答就直接回答 |
| 查看 | 先读真实目标：发行版与版本、包管理器、服务状态、涉及的文件与日志。不假设路径或工具存在 |
| 诊断 | 一次一个假设，并说明什么读取能推翻它；区分症状与根因 |
| 执行 | 选能达成目标的最小机制：优先结构化工具，否则用 shell；一次一处改动，保持可回退 |
| 验证 | 用与变更前不同的读取核对效果：服务运行、端口监听、二进制可执行、文件内容已变 |
| 汇报 | 先结果，再证据，最后未完成项与风险；未验证就明说 |

**持续性**：缺包、源失效、缺少编译器、命令不支持、非零退出，都是目标主机的事实而不是停下的理由。
换包管理器或镜像、源码构建、换另一条有文档的路径。只有在多次**不同**尝试都没有新事实时才报告
阻塞，并说明试过什么、看到什么、缺什么才能继续。

**什么时候问用户**：目标无法从主机得知时——未选服务器、缺少凭据或权限、破坏性操作范围确实模糊。

这一段是提示词，不是状态机。代码不会阻止模型在未取证时变更；它保证的是每次变更都有审批、
真实目标、真实输入，并有票据可查。

## 场景手册（SOP）

`RUNBOOKS` 内置 6 本：磁盘/inode 满、服务宕或 502、CPU/内存高、日志定位、发布与配置变更、
容器不健康。每本给出必查证据（具体工具名）、常见根因、处置顺序、验证标准，以及**什么情况下
才值得停下来说明**——停下的门槛是「无法判断」，不是「环境是生产」。

选择只读当前用户指令：剥离代码块；纯知识性提问（「什么是 502」）不选手册。
`test_operations_policy.py` 校验手册里的每个工具名仍然注册，工具改名会让测试失败。

## 权限与执行路径（代码保证）

一次变更调用走这条链，任何一环都可以拒绝：

1. **注册表**：工具存在、参数通过 JSON Schema、调用者有该工具。
2. **授权**：目标必须已解析（`srv_...`），未选目标直接 `target_required`。
3. **审批**：`requires_approval` 的工具在运行时暂停，桌面弹出审批卡；批准绑定 run、call、
   目标与**完整输入**的 sha256。改一个字都需要新的批准。
4. **宿主票据**：`server.exec` / `package.install` / `systemd.restart` / `docker.restart` 由宿主
   铸造一次性票据，绑定 run/trace/call、服务器、环境、输入指纹；用一次即作废。会话批准不可用。
5. **命令黑名单**：`server.exec` 在消耗票据**之前**按运维配置的名单检查；名单读取失败按拒绝处理。
6. **目标一致性**：宿主重新解析服务器，确认环境与登记记录一致，再启动一次性 C++ SSH 服务。
7. **文件变更**：`filesystem.write/edit/backup/restore` 由 Python 侧 exactly-once 台账
   （run/trace/call + 工具 + 目标 + 参数指纹）防重放；`edit` 还要求读到的 revision 未变。
8. **循环防护**：重复的相同调用被拦截；效果性操作失败或结果未知后，必须先有一次成功的只读
   核对才能再发起变更；超时不会被自动重放。

**持久任务与计划仍然存在**，用于值守巡检、需要可复核步骤的批处理，以及用户主动选择「目标任务」
的场景。它们不再是普通对话执行变更的前置条件。

## 阶段：由实际动作推导

`agent_stage.py` 把已执行的工具结果映射为阶段，运行时**仅在变化时**发 `agent.stage`：

- `intake` 尚未执行；`evidence` 读取成功；`diagnosis` 读取失败或效果性操作结果未知；
  `plan` 记录了调查计划；`change` 效果性操作成功（或可能已执行）；`verify` 变更后读取成功；
  `report` 产出最终回答。

被拒绝、待审批、参数非法的调用**不改变阶段**。因此界面显示的进展与实际执行一致，模型无法
靠文字宣称未到达的阶段。事件带 `runId`，绑定持久任务时带 `taskId`；桌面把 `change` 映射为
值守条的「执行工具」，其余映射为「思考」，并把阶段写入持久任务的 `phase`（仅限当前持有该任务
的运行，终态任务与未知阶段忽略）。

## 只读诊断工具

`server.processes`、`server.ports`、`filesystem.list` 是为排障补的固定只读操作，模型不提供任何
参数：进程表按 CPU 排序；监听套接字在 SSH 用户无权读取进程时明确标注
`processInfoAvailable:false`；目录列表单层、不跟随符号链接，并与 `filesystem.read` 共用凭据
路径黑名单。

## 仍然缺失

- 变更没有自动回滚；只有 `filesystem.restore` 这一条显式恢复路径。
- 没有目录创建/重命名/删除、进程终止、服务启停、端口连接明细、指标历史、多主机编排。
- 单次工具调用受 `AgentBudget.max_tool_seconds`（30 s）约束。
- 方法、手册与「继续想办法」都是提示词层能力；阶段事件只反映实际执行。
- 尚未在真实服务器上端到端验收「许愿式」变更流程。
