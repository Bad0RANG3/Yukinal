# 项目自我审查与后续完善计划

> 历史审查快照，记录 2026 年 9 月 21 日的判断。后续工作的现行顺序见[下一阶段实施计划](../implementation-plan.md)，当前功能范围以[当前限制](../limitations.md#当前限制)为准。

## 1. 先给结论

Yukinal 已经形成了一套相当完整的跨层工程骨架。SSH、凭据、SQLite、PTY、Tauri、Node.js sidecar、Provider、MCP、权限引擎、审计和任务执行之间有清晰的边界，关键行为也有较多测试保护。当前本地 `pnpm check` 可以通过，Rust 与 TypeScript 的契约检查、sidecar 冒烟、跨语言集成测试和工作区测试均已跑通。

项目当前最明显的问题也很清楚。代码完成度跑在真实交付验证之前，功能面跑在用户场景收敛之前，安全模型的表达复杂度跑在界面解释能力之前。结果是项目在本地开发者视角下显得完整，在真实安装、真实远程环境和长期运行视角下仍然偏早期。

后续工作不应继续以增加功能数量为主。下一阶段应把重点放在四件事上。

1. 把可构建的安装包变成可安装、可升级、可回滚的产品。
2. 把回环测试和本地 fixture 扩展成可重复的真实环境验收。
3. 把跨层复杂度压回到几个能够长期维护的深模块中。
4. 把权限、任务和恢复机制翻译成用户能够理解、能够检查的工作流。

## 3. 当前做得好的地方

### 3.1 安全边界落到了代码路径上

项目没有把“模型应该小心一点”当作安全策略。Agent 工具、Permission Engine、Rust 宿主、凭据引用、主机指纹和审计记录各自承担了明确职责。`apps/agent` 负责提出和编排操作，宿主负责资源持有、输入校验和执行，secret 留在操作系统凭据库，审计只保存受限内容。这种分工使危险动作可以在多个层面拒绝，降低了单个模型响应或单个 UI 分支失误的影响范围。

### 3.2 资源生命周期意识强

sidecar、MCP 子进程、PTY、SSH 会话、collector 子进程和取消路径都有专门的关闭逻辑。测试里覆盖了崩溃、超时、取消、重启预算、尾部输出、进程回收和迟到事件。很多同类项目会先实现成功路径，再把关闭留给操作系统处理，Yukinal 已经避开了这个常见陷阱。

### 3.3 跨语言契约有实际保护

共享 schema、IPC fixture、Rust 序列化测试和 TypeScript schema 测试形成了多处交叉检查。版本号只有一个来源，Provider 名称、事件词汇、权限决策和 sidecar 协议也有相应测试。这让跨 Rust、Tauri、Node.js 和 React 的改动更容易被发现。

### 3.4 文档对限制的态度诚实

`docs/limitations.md` 没有把未验证的路径写成已完成能力。Windows 安装包未做安装后验收、跨平台产物未在本机验证、真实外部系统未纳入默认门禁等情况都被明确写出。这种写法值得保留，它比一份看起来完整但无法复核的功能清单更有用。

### 3.5 测试承担了实际保护职责

测试覆盖了大量边界条件，包括输入上限、协议形状、secret 脱敏、主机指纹、MCP 生命周期、任务状态、取消和恢复。当前测试量也带来了维护成本，但至少关键决策已经能够通过自动化重现，维护者不必依赖个人记忆。

## 4. 必须正视的短板

### 4.1 项目范围已经超过首个稳定版本适合承受的范围

一个版本同时承载远程服务器管理、健康采集、终端、SFTP、服务与日志、Agent 对话、多个 Provider、MCP、OAuth、DPoP、持久任务、调查工作流、备份恢复、调度和安装包。每个方向都足以形成独立产品。把它们放在一个版本里，主要风险来自每条用户路径都要跨越更多状态和权限边界，代码数量只是表面现象。

当前代码已经证明了“可以把很多功能接起来”，还没有证明“用户可以稳定地完成一件重要工作”。后续必须从完整功能列表转向少数端到端任务，例如诊断一台服务器、定位一项服务异常、审查一次 Agent 变更和安全地回滚一个文件。

### 4.2 代码质量高于交付质量

`pnpm check` 已经覆盖编译、单元测试、sidecar 冒烟和本地跨语言集成，但打包工作流仍然把安装包构建放在独立流程里，当前实际开发环境主要验证了 Windows。文档也明确记录了没有安装后启动验收、没有签名、公证和自动更新。

这意味着项目现在能够较有把握地回答“代码能否按仓库门禁编译”，还不能同样有把握地回答下面这些问题。

- 用户安装后能否首次启动并找到 sidecar。
- 升级后旧 SQLite 数据能否顺利迁移。
- Windows Defender、macOS Gatekeeper 和 Linux 桌面环境会怎样处理产物。
- 应用退出、崩溃和重新打开后，SSH、PTY、MCP 与任务状态是否一致。
- 用户遇到失败时，是否能完成恢复，而不需要打开开发者工具。

### 4.3 测试覆盖了很多边界，仍然缺少产品级外部验证

当前测试大量依赖本地回环服务、fixture、临时进程和 WSL 环境。这些测试对协议和生命周期很有价值，但它们不能替代真实网络中的 DNS 变化、代理认证、SSH 中断、慢速磁盘、第三方 MCP 差异、Provider 限流和系统休眠。

目前最需要补的是少量可重复的环境矩阵，继续堆叠同形状的单元测试收益较低。每个矩阵都要有固定版本、启动脚本、凭据注入方式、清理步骤和失败归因。没有这些信息，外部验收很容易变成一次性的手工演示。

### 4.4 宿主命令层承担了过多变化

当前最大文件集中在宿主命令和外部协议边界。`apps/desktop/src-tauri/src/commands/host.rs` 约 6,329 行，`apps/desktop/src-tauri/src/commands/mcp/oauth.rs` 约 3,803 行，`apps/desktop/src-tauri/src/commands/mcp.rs` 约 2,573 行，`apps/desktop/src-tauri/src/commands/mod.rs` 约 2,001 行。文件大并不自动等于设计错误，但这些文件同时处理输入解码、业务编排、资源生命周期、错误映射和审计，很容易让一个小改动牵动多个边界。

后续拆分应以稳定的职责为依据，不能机械地按文件长度切开。目标是让每个模块拥有一组完整的不变量，并让命令层只负责把 IPC 输入转成领域请求。

### 4.5 共享契约仍然存在重复维护的风险

TypeScript Zod schema、Rust serde 类型、IPC fixture、数据库模型和 UI 映射共同描述了很多相同的字段。现有测试能发现一部分漂移，却不能消除重复定义带来的理解成本。每增加一个状态或枚举，维护者仍然需要知道它要同步到哪些层。

下一阶段需要给跨层契约分类。适合成为单一来源的字段，应尽量生成或集中声明。确实需要双向实现的字段，应记录转换方向、兼容策略和弃用时间。测试应该保护兼容规则，不只保护当前样例。

### 4.6 安全模型的工程表达已经接近用户认知上限

`goal`、`plan`、`readonly`、`ask`、`auto`、`taskId`、`planId`、`planStepId`、风险档位、会话授权、变更基线和验证工件各自有合理来源，但用户在一次操作中需要同时理解它们。系统内部概念越多，界面越不能直接把内部字段搬给用户。

当前 UX 需要用任务阶段、影响范围和下一步动作来解释策略。用户应能回答三个问题。系统准备做什么，为什么需要确认，失败后怎样恢复。能否把这三件事讲清楚，应作为安全功能的一部分验收。

### 4.7 可观测性还偏向开发阶段

现在已有活动记录、审计、sidecar 日志和错误结构，但长期运行需要更明确的诊断边界。用户需要知道一次失败发生在连接、认证、权限、工具执行、Provider、MCP 还是持久化阶段。维护者需要知道耗时、重试、队列积压、子进程数量和资源增长，同时不能收集远程 secret 或不必要的业务内容。

应补充隐私安全的诊断包、稳定的错误分类和可选的本地性能记录。没有这些信息，真实用户反馈仍会退化成“点了以后没反应”。

### 4.8 当前版本缺少明确的停止条件

文档记录了很多限制，但路线仍容易被新 Provider、新工具和新自动化需求推动。若每次增加能力都没有删减范围，维护成本会持续上升。

后续每个阶段必须同时写出不做什么。没有验收指标、没有明确用户任务、没有可回滚路径的功能不进入稳定发布范围。

## 5. 后续目标与优先级

### 5.1 总体目标

把 Yukinal 从“边界设计完整的工程样机”推进到“少数核心工作流可重复、可恢复、可发布的桌面产品”。核心判断标准应放在用户能否在真实环境里完成任务，并能在失败后理解和恢复，工具数量只作为背景数据。

### 5.2 优先级定义

| 优先级 | 含义 | 处理规则 |
| --- | --- | --- |
| P0 | 发布阻塞或安全阻塞 | 进入稳定发布前必须完成 |
| P1 | 核心工作流质量 | 影响首批用户，按阶段完成 |
| P2 | 维护成本和体验 | 在核心路径稳定后处理 |
| P3 | 扩展能力 | 没有明确用户任务时不主动增加 |

## 6. 分阶段完善计划

### 阶段一，P0，发布可信度与数据安全

建议目标周期为 2 至 4 周。周期只是估计，完成条件以验收标准为准。

#### 工作项 A，安装后验收

涉及位置包括 `scripts/`、`.github/workflows/package.yml`、`docs/packaging.md` 和平台相关的 Tauri 配置。

工作内容如下。

- 在 Windows CI 中构建 NSIS 与 MSI 后，使用干净虚拟机或隔离 runner 完成安装、首次启动、关闭、再次启动和卸载。
- 检查资源目录中的 agent bundle、图标、数据库目录和日志目录是否位于预期位置。
- 检查没有 Node.js、没有仓库目录和没有开发依赖时，sidecar 是否仍能启动。
- 保存安装日志、启动日志和失败截图，失败时区分打包错误、安装器错误和运行时错误。
- 为 macOS 与 Linux 至少建立一次真实产物的安装启动记录。没有对应硬件时，使用 CI 产物和自动化桌面 runner，但要记录限制。

验收标准如下。

- 三个平台都能从空目录完成安装和启动。
- 关闭应用后不存在由 Yukinal 留下的孤儿 sidecar、MCP 子进程或 PTY 子进程。
- 安装产物中的版本、资源路径和 sidecar 协议版本一致。
- 文档不再把“构建成功”当成“安装可用”。

#### 工作项 B，数据库迁移和恢复演练

数据库已经有版本化 migration，但后续需要把它作为发布工件来管理。

工作内容如下。

- 为每个发布版本保存从上一稳定版本升级到当前版本的测试数据库。
- 覆盖空数据库、旧数据库、部分写入数据库、WAL 文件存在和 schema version 高于当前应用的情况。
- 在迁移失败时保留原文件，生成可定位的错误，不覆盖用户数据。
- 增加导出前检查和恢复演练，验证服务器配置、活动记录、任务记录和审计记录的边界。
- 明确哪些数据可以导出，哪些 secret 只能重新绑定操作系统凭据库。

验收标准如下。

- 每次 schema 变化都带一个可重复的升级测试。
- 迁移前自动生成受限备份，恢复失败不会破坏原数据库。
- 新版本读取旧数据时，未知字段和未知枚举有明确降级策略。
- 发布说明包含迁移影响和回滚方法。

#### 工作项 C，发布签名和升级策略决策

这项工作可以先做决策记录，再决定是否实现自动更新。不能在没有密钥管理、回滚设计和安全审查的情况下直接添加更新器。

需要产出如下。

- Windows 签名方案和证书保管方式。
- macOS 签名、公证和 entitlements 方案。
- Linux 包的发布渠道与校验方式。
- 是否支持自动更新，支持哪些版本，失败后怎样回退。
- 发布制品的哈希、来源和保留期限。

暂不把自动更新列为默认承诺。完成安全设计和真实升级演练后，再决定进入 P1 还是继续保持手动下载。

### 阶段二，P0，真实环境验收矩阵

建议与阶段一并行，目标是让外部验证可以重复执行。

#### 工作项 D，建立受控远程环境

至少准备以下环境。

| 环境 | 用途 |
| --- | --- |
| 本地或 WSL OpenSSH | 基础认证、指纹和取消回归 |
| 一台可重置的 Linux 虚拟机 | systemd、Docker、文件和网络行为 |
| 一台带代理的环境 | HTTP 代理、认证、超时和证书路径 |
| 一个本地 Provider 兼容服务 | 流式响应、工具调用、限流和错误映射 |
| 一个可控 MCP stdio 服务与 HTTP 服务 | 握手、工具审查、取消和崩溃恢复 |

每个环境都要有启动脚本、版本锁定、测试账户、最小权限、数据清理和故障注入方法。真实 secret 不进入仓库和 CI 日志。

#### 工作项 E，补充故障注入

至少覆盖以下情形。

- SSH 认证过程中断网。
- 已建立的 SSH 会话在命令执行中断开。
- Provider 在流式响应中途返回 401、429、5xx 或畸形事件。
- MCP 服务在握手后退出、忽略关闭、返回超长帧或返回未知工具。
- 应用在等待批准、写入数据库、创建备份和关闭 sidecar 时被强制结束。
- 系统休眠后恢复，时钟发生跳变。

验收重点放在安全停机和可操作反馈。系统不需要自动恢复所有错误，但不能留下重复执行或虚假的完成记录。

#### 工作项 F，建立发布前证据包

每次候选发布生成一份不包含 secret 的证据包，至少包括版本、平台、安装方式、测试矩阵、失败项、已知限制和产物哈希。证据包要能让另一位维护者在不依赖口头说明的情况下复核结论。

### 阶段三，P1，收敛三个核心用户工作流

建议先暂停扩展新的 Provider、工具和自动化类型，把现有能力收敛成三个可演示、可恢复的路径。

#### 工作流一，服务器健康诊断

用户添加服务器，完成主机指纹核验，查看健康快照，打开服务或日志，得到一份带证据的结论。

完成条件包括以下内容。

- 首次连接过程能解释认证失败、指纹未核验和目标不可达的区别。
- 健康数据带采集时间和来源状态，不把缺失数据当成健康。
- 服务、日志和快照之间能回到同一台服务器和同一次活动。
- 连接失败后重新尝试不会创建重复服务器或重复审计记录。

#### 工作流二，受控的 Agent 变更

用户提出一个目标，Agent 生成计划，用户看到影响范围和变更前证据，逐项批准必要操作，系统执行并验证，最后生成结果和恢复入口。

完成条件包括以下内容。

- 普通聊天、只读调查和有副作用任务在视觉上明显区分。
- 每个需要批准的动作显示标准化目标、风险、输入摘要和预期后果。
- 用户拒绝或中止后，任务状态不会被写成成功。
- 验证失败时显示已经发生的变化、未完成的步骤和可用恢复选项。
- 任务记录可以在应用重新打开后继续阅读。

#### 工作流三，文件变更与恢复

用户查看远程文件，进行受限编辑，看到变更基线，保存备份，验证结果，并在需要时手动恢复。

完成条件包括以下内容。

- 文件在批准后发生变化时，系统拒绝静默覆盖并要求重新读取。
- 大文件、二进制文件、编码异常和权限不足都有明确提示。
- 备份的生命周期、保留策略和恢复条件能在界面中找到。
- 恢复操作保留审计记录，并清楚说明恢复的是哪一次备份。

### 阶段四，P1，降低宿主和契约的维护成本

#### 工作项 G，拆分宿主命令层

建议顺序如下。

1. 先给 `commands/host.rs`、`commands/mcp.rs` 和 `commands/investigation.rs` 画出输入、领域调用、资源管理和 IPC 输出的边界。
2. 把纯输入校验、错误映射和状态转换提取成无 Tauri 依赖的领域模块。
3. 把外部协议实现放回对应 crate，Tauri 命令只持有应用状态和调用入口。
4. 为每次拆分保留现有 fixture 和跨语言测试，避免借重构之名改变行为。
5. 当一个模块只剩下装配职责后，再统一命名和目录结构。

建议的完成指标如下。

- 新增命令不需要修改一个集中的超大模块。
- 资源关闭路径可以在单个模块测试中验证。
- 错误代码由领域层定义，UI 层只负责展示映射。
- 任何跨层变更都能指出唯一的契约来源。

#### 工作项 H，整理跨层契约来源

建立一张契约登记表，每一行描述一个跨层对象或事件。

| 字段 | 需要记录的内容 |
| --- | --- |
| 名称 | 类型、事件或 RPC 方法的稳定名称 |
| 来源 | 唯一声明位置或明确的双向声明理由 |
| 消费者 | Rust、sidecar、桌面 UI、fixture 等 |
| 兼容策略 | 新增、删除、重命名和未知值的行为 |
| 测试 | 编译期、schema、fixture 或端到端测试 |
| 弃用计划 | 若存在旧形状，记录移除条件 |

这张表不重复所有字段定义，只记录维护者在改动时最容易遗漏的关系。

#### 工作项 I，收敛错误分类

把错误按用户可行动的原因分成连接、认证、信任、权限、输入、远端执行、Provider、MCP、持久化和应用生命周期几类。每类都要有稳定代码、用户文案、开发诊断信息和是否可重试的规则。

不要让 UI 根据英文错误文本判断下一步。错误文本可以调整，错误类别和重试语义需要稳定。

### 阶段五，P2，性能、可观测性和体验

#### 工作项 J，建立性能预算

先测量，再设预算。建议记录以下指标。

- 空窗口启动到可交互的时间。
- sidecar 启动、握手和首次响应时间。
- 服务器列表、活动记录和调查列表的最大可接受加载时间。
- 大日志、长 Agent 回复和高频终端输出下的 UI 更新频率。
- 同时打开多个 SSH、PTY 和 MCP 会话时的内存、线程和子进程数量。
- 长时间运行后的数据库大小、WAL 大小和审计增长速度。

性能测试要使用固定数据集和固定机器级别，结果存档但不把单台开发机的绝对数字写成普遍承诺。

#### 工作项 K，增加隐私安全的诊断模式

诊断模式默认关闭，用户主动开启后才记录更细的时间线。记录内容应包括阶段、耗时、错误类别、重试次数、资源计数和截断后的非敏感标识。不得记录 secret、完整命令参数、文件内容、Provider token、远程日志原文或完整模型上下文。

诊断包需要能在 UI 中预览，用户明确选择导出范围，导出前执行一次 secret 扫描。

#### 工作项 L，重新设计首次使用和失败状态

首次使用只要求完成一件可验证的事，例如连接一台测试服务器并读取健康快照。其余 Provider、MCP、计划和调度能力延后到用户确实需要时出现。

失败页面至少要同时给出发生位置、当前状态、下一步动作和是否会重试。按钮文案要对应实际动作，不能让用户猜测“重试”会重连、重跑任务还是重新提交模型请求。

### 阶段六，P3，谨慎扩展

以下能力暂不进入默认路线，除非能对应到稳定的用户任务和完整的安全评审。

- 更多 Provider 特有能力。
- 任意 shell 自动化。
- 后台常驻调度和应用退出后的补跑。
- 自动批准危险动作。
- 大规模团队协作、远程审计中心和云端同步。
- 任意二进制附件内联和无上限日志保留。

这些方向可能有价值，但会扩大信任边界和运维责任。它们不应因为已有协议适配点就自然进入产品。

## 7. 推荐的提交顺序

为了减少返工，建议用以下顺序推进。

1. 先完成安装后验收和数据库迁移演练。
2. 再建立真实环境矩阵和发布证据包。
3. 用三个核心工作流做一次完整手工验收，记录每个无法解释的状态。
4. 根据这些失败点拆分宿主命令层和错误分类。
5. 在结构稳定后再做性能预算、诊断模式和 UI 精修。
6. 最后重新评估 Provider、MCP 和调度扩展是否真的需要进入稳定版本。

这个顺序会暂时降低新功能的提交速度，但会减少在未验证边界上继续叠加代码的风险。

## 8. 每个阶段的完成定义

一个阶段只有同时满足以下条件才算完成。

- 目标用户任务可以从干净环境开始并完整结束。
- 失败路径有测试或可重复的手工步骤。
- 数据、进程、凭据和审计记录的生命周期已经说明。
- 文档中的限制、启动方式和验收结果已经更新。
- `pnpm check` 通过，必要时附带真实环境验证结果。
- 没有把未验证的路径写成已支持能力。
- 已经写出本阶段明确不做的事情。

## 9. 维护者每次改动前应回答的问题

1. 这个改动服务于哪个用户任务。
2. 它会改变哪一条跨层契约或安全边界。
3. 它失败时会留下什么状态。
4. 用户如何知道发生了什么，如何恢复。
5. 是否有真实环境或安装产物需要重新验收。
6. 它能否在不增加另一份事实来源的情况下实现。
7. 如果现在不做，具体风险是什么。如果做了，新增的维护责任是什么。

如果这些问题答不清楚，优先补设计和验收条件，不要直接增加工具或 UI 入口。

## 10. 复盘方式

每个阶段结束后保留一份短复盘，内容只记录事实。

- 做成了什么。
- 哪些验收失败。
- 哪些限制被解除，哪些限制仍然存在。
- 哪个假设被实际环境推翻。
- 下一阶段是否需要调整范围。

复盘应链接到具体提交、测试、产物或问题单。不要用“整体稳定”“体验提升”这类无法复核的结论替代证据。

## 11. 最终判断标准

Yukinal 适合继续投入，但下一步不适合继续单纯扩张功能。项目已经有足够多的技术资产，真正稀缺的是可验证的产品闭环和能长期维护的结构。

当用户可以在真实安装环境中安全地连接服务器、完成一次有证据的诊断、批准一次受控变更，并在失败后恢复，同时维护者能够用固定矩阵复现问题时，项目才算跨过从工程样机到可交付产品的门槛。
