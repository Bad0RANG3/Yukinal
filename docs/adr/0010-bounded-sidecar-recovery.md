# ADR 0010 崩溃后的自动恢复有界，且只恢复能力、不复活状态

Status: Accepted
Date: 2026-09-12

## Context

[ADR 0008](0008-sidecar-launch-and-lifecycle.md) 明确选择了「当前不自动重启」，并写下了两个前置条件：一次坏 bundle 不能变成重启风暴；在途审批与运行状态的含义必须先被回答清楚。这条 ADR 记录这两个条件被如何回答，以及为什么现在值得付这份代价。

代价在实践里是清楚的：sidecar 是独立进程，任何一次瞬时崩溃（Node 的 OOM、开发时 `pnpm build` 覆盖了正在运行的 bundle、用户机器上的杀毒软件）都会让整个 Agent 面板停止工作，直到用户自己点一次「重新启动」。界面能显示原因，但一个可自愈的故障却要求人工介入，这本身就是缺陷——尤其是崩溃往往发生在用户正在等待长任务的时候。

同时必须承认另一件事：进程死了，它内存里的东西就没了。任何「自动恢复」如果不先把这句话说清楚，就会变成「假装任务还在继续」。

## Decision

**只重启不是被要求的退出。** 判据是 pid，不是标志位：`Supervisor::stop()` 在关闭子进程**之前**先取走运行槽位，因此「Watcher 观察到的退出，其 pid 已经不是当前记录的 pid」只有两种可能——用户要求过（`agent_kill`、窗口关闭、`ExitRequested`），或者已经有更新的进程顶替了它。用标志位意味着要信任现在和将来每一个调用方都会去设置它；用槽位状态则不需要。

**重启是有界的**（`crates/core/src/supervisor.rs` 的 `RestartPolicy`）：

- 默认最多 5 次，延迟从 1 秒开始翻倍、上限 30 秒。
- 连续服务超过 `healthy_after`（默认 60 秒）的进程被视为新的基线：一个跑了几小时后的偶发崩溃，不应该消耗掉上一次事故留下的预算。
- 预算用尽后 supervisor **停止尝试**并把这件事写进状态（`restart.exhausted`），不会静默地永远重试。
- 重启本身失败（`node` 被移除、bundle 不再可解析）也消耗同一次预算：失败的重启不会产生 `Exited` 事件，没有任何其他机制会注意到它，如果不在同一条重试循环里记账，supervisor 会停在「还有额度但不再尝试」的状态。

**重启必须留下痕迹。** 一次自动重启如果抹掉了自己的起因，就和「什么都没发生」无法区分：

- `agentStatus.lastExit` 不被清除（只有用户主动的 `start` 才清），界面因此能同时显示「正在运行」和「它是被重启回来的」。
- `agentStatus.restart` 报告第几次尝试、上限是多少、是否已经放弃。
- stderr 尾部（200 行）插入进程代次标记与重启原因，否则上一个进程的遗言和新进程的开场白会连在一起，而「这一行是死掉的那个进程说的吗」恰好是最需要答案的时候。

**重启只恢复能力，不复活任何状态：**

- 崩溃时在途的每一次运行与每一条审批都随进程一起消失，不会被恢复。界面已有的 `Agent sidecar 已退出，本次运行已中断。`（`apps/desktop/src/features/agent/useAgentRun.ts`）就是这条语义的用户可见面；重启后用户重新发起，就会得到一条新的运行。
- 账本不允许留下一个看起来还活着的运行：进程死掉后仍在 `traces` 里处于 `running` 的记录，由下一次启动的 sidecar 收尾为中断。一条永远 `running` 的 trace 会让「正在跑」这个判断永久失真——这比丢掉一次运行的细节更糟。

**事件转发器变成窗口级单例**（`apps/desktop/src-tauri/src/lib.rs` 的 setup 里创建一次）。它原来由每次 `start_sidecar` 创建，并依赖 `SidecarEvent::Exited` 来结束自己的任务，而 supervisor 当时刻意不转发该事件——于是崩溃后重启会挂上第二个转发器，每一帧被转发两次，而每一个 `host.*` 请求都会被**执行两次**（响应者是按事件派生出来的任务）。这不是自动重启引入的问题，是自动重启会把它从「偶发」变成「每次崩溃必现」。

## Consequences

**收益**

- 瞬时崩溃可以自愈：OOM、开发时被覆盖的 bundle 不再需要人工点一次按钮。
- 失败仍然是可见且可解释的：崩溃原因、重启次数、预算耗尽都在状态与日志尾部里，不是「面板突然又好了」。
- 用户要求的退出依旧是确定的：`agent_kill` 之后不会有一个进程自己爬起来，停止按钮不会说谎。
- 顺带修掉了双重转发：一次 `host.tool.execute` 现在只会被执行一次。

**成本**

- 崩溃循环（打包产物损坏、Node 版本不兼容）会消耗最多 5 次尝试后才停手：这段时间内界面会反复显示启动中，日志尾部会留下 5 条失败记录。
- 重启后的进程是全新的：没有会话记忆、没有待审批请求、没有正在执行的工具。用户会看到一次中断提示，必须重新发起。
- `lastExit` 与 `restart` 会在自动重启后继续存在，直到下一次用户主动启动：界面必须同时渲染「在运行」和「上次崩溃过」，不能用其中一个掩盖另一个。
- 判断「这次退出是不是被要求的」依赖「取走槽位」这一约定，是隐式耦合：将来若有人写出不经过 `Supervisor::stop()` 的关闭路径，它会表现为「不该重启的重启」。这条约束写在代码注释里，也由 `a_requested_stop_is_not_restarted` 这条集成测试固定住。
- 重启策略目前是编译期默认值，没有用户可调的开关；真要做成可配置的，必须同时给出「关掉自动重启之后用户从哪里恢复」的答案。

## Alternatives considered

- **维持 ADR 0008 的「不自动重启」。** 把恢复成本转嫁给用户，而且崩溃最常见的场景（开发时覆盖 bundle）恰恰是用户正在等长任务的时候。否决。
- **无条件重启每一次退出。** 停止按钮会变成谎言，关闭窗口时也会拉起新进程。否决。
- **把运行状态检查点化，重启后接着跑。** 需要回答「上一个进程执行到哪一步、哪些副作用已经发生」，而这个问题在工具已经发出请求之后无法可靠回答；半执行的工具调用是不能安全续跑的。否决。
- **由界面负责重启。** WebView 与窗口生命周期绑定，面板关闭、路由切换都会让恢复逻辑消失，而且会把进程决策重新放回 React（ADR 0008 已经否决过这一点）。否决。
- **用指数退避无限重试。** 坏 bundle 会形成后台重启风暴，日志尾部被同一段错误刷满，真正的原因反而被挤掉。有界预算是这个代价的上限。
