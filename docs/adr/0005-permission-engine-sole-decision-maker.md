# ADR 0005 Permission Engine 是唯一的执行授权决策者

Status: Accepted
Date: 2026-09-09

## Context

一次工具调用是否该被执行，取决于三类互相独立的信息：这个工具本身有多危险、这一次具体要做什么、它发生在哪里。三者当中任何一个单独看都不够：`filesystem.write` 本身只是写文件，但目标可能是生产环境的配置文件；`docker.ps` 只是查询，但如果被塞进一段 shell 片段就完全不同；同一个 `system.echo` 在本机和生产环境的风险含义也不一样。

如果允许每个工具、每个 Provider 或模型输出自行决定「这次可以执行」，会同时失去两样东西：**可解释性**（用户无法回答「为什么它被允许了」）和**隔离性**（一次在开发环境获得的放行不能被误用到生产环境）。更危险的是，模型输出天然会说「我已经得到授权」，而这句话在协议里没有任何证据效力。

## Decision

风险**事实**可以有多个来源，但只有一个地方能把事实变成**决策**：`PermissionEngine.evaluate()`。

三层事实：

| 来源 | 位置 | 提供什么 |
| --- | --- | --- |
| 工具声明 | `ToolDeclaration.risk` | 这个工具的静态风险底线，由工具作者声明 |
| 命令分析 | `analyzeCommand()`（16 条规则） | 这次调用里内嵌的 shell 命令的风险，规则编号如 `rm-rf`、`drop-database`、`curl-pipe-shell` |
| 目标环境 | `ENVIRONMENT_RISK_FLOOR` | 本机与开发为 `low`，预发布为 `medium`，生产与未知为 `high` |

合成过程是确定的：

1. `intrinsicRisk = max(工具风险, 命令风险)`——只描述动作本身。
2. 环境只**抬高**风险：读类动作在生产环境仍然保持读类，否则「生产环境只读自动执行」这条策略永远无法成立；其余动作取 `max(intrinsicRisk, 环境底线)` 得到 `finalRisk`。
3. 风险等级折叠成权限档位：`read`/`low` → `read`，`medium` → `write`，`high`/`critical` → `dangerous`。
4. 由目标环境选内建策略（本机：写与危险都询问；开发与预发布：写自动、危险询问；生产与未知：写与危险都询问）。
5. 按档位得到初步结果，然后依次施加以下不可绕过的约束。

不可绕过的约束：

- **`dangerous` 档位永远不会自动执行。** 即使策略表说 `auto`，也会被强制改为 `ask`。高危与 critical 操作必须得到用户对该次操作的明确批准。
- **只读运行模式先于一切委托。** 当一次运行处于 `plan` 或 `readonly` 模式时，任何非 `read` 档位的调用直接被 `deny`，而且这个判断发生在策略、Agent 委托和会话授权之前——模型无视指令也没用。
- **Agent 自动委托的范围是封闭的。** `auto` 只覆盖 `write` 档位且目标环境是 `development` 或 `staging` 的调用；其余非读操作一律回到 `ask`。任何 `deny` 都不会被模式重新打开。
- **会话授权只放宽非危险操作。** 内在风险已是 `dangerous` 档，或最终风险为 `critical` 的操作不会被记住，每次都要重新询问。
- **决策绑定到一个具体的工具与目标。** `PermissionDecision` 里带着 `toolName` 和已解析的 `target`（host、serverId、workspaceId、environment），审批 ID 只在 `outcome === "ask"` 时生成。

ToolRegistry 只接受四种执行票据，并逐个字段复核（`checkTicket()`）：

| 票据 | 含义 | 复核条件 |
| --- | --- | --- |
| `policy_auto` | 环境策略自动批准 | 决策结果必须是 `auto`，且来源标记为 `policy` |
| `agent_auto` | 用户在运行级委托 Agent | 来源必须是 `agent`，且档位为 `write`、环境为开发或预发布 |
| `session_auto` | 用户已批准过同名同目标的操作（作用域为单次运行） | 来源必须是 `user` |
| `user_approved` | 与挂起审批完全匹配的逐项批准 | 审批 ID 必须与决策中的 `approvalId` 一致 |

所有票据都还要满足：工具名与决策一致、目标四元组完全一致、`deny` 一律拒绝、`dangerous` 档位只接受 `user_approved`。任一字段不匹配都会得到一个 `denied_by_policy` 的工具结果，而不是被忽略的日志。

会话授权的生命周期由 agent loop 管理：引擎实例比单次运行长命，因此 loop 在没有运行在飞时调用 `clearGrants()`。没有这一步，「批准本会话」会一直授权到 sidecar 进程退出，跨越多次无关运行。

等待审批的运行有 2 分钟上限（`approvalTtlMs`），超时按「已过期」处理：向界面发出 `agent.approval_expired`，把拒绝原因回灌模型，运行继续而不是永久挂起。

## Consequences

**收益**

- 界面可以展示构成决策的风险事实（工具风险、命中的命令规则、目标环境），用户能看到**为什么**这次操作被批准、被询问或被拒绝。
- 授权来源在审计里可区分：`policy`、`agent`、`user` 三种自动批准分别记录，Agent 的自主批准不会伪装成用户的批准。
- 越权尝试有确定的失败模式。模型伪造票据、复用其他工具的审批、把开发环境的决策用到生产目标上，都会在 `checkTicket()` 处被拒。
- 安全逻辑集中在一个可测试的边界上：风险分层、策略表、档位折叠和票据复核都有单元测试，不需要启动模型或真实服务器。

**成本**

- 需要维护风险事实与票据两套契约，任何新增工具都必须声明风险、超时和重试策略，否则注册就被拒绝。
- 需要区分「内在风险」与「最终风险」两个概念。它们在跨服务器复用审批时是防止误操作的关键，但也让阅读代码时需要多一层注意。
- 未来的团队策略或 RBAC 只能扩展策略来源（例如增加策略提供方），不能在其他模块里再建立第二个授权决策点。

**危险档位的加严（已决策）**

dangerous 档位永远需要逐项的直接批准，会话授权不能替代它。这条规则此前在实现里是分裂的：`evaluate()` 命中会话授权时按**内在风险**判断，而执行闸口 `checkTicket()` 拒绝任何 dangerous 档位且非 `user_approved` 的调用。生产环境的风险下限是 `high`，任何普通写入都会被升级到 dangerous，因此「在生产目标上批准本会话」会得到一个引擎报告为 `auto`、执行却必然拒绝的决策。

收敛方向是**收紧引擎**，理由有三：

1. 引擎在更早的位置已经确立过同一不变式（「危险与 critical 操作不能被自动批准」），会话授权分支把它重新打开了，属于内部自相矛盾。
2. 引擎是唯一的授权决策入口，所以它**不能宣布一个执行层会拒绝的批准**。错误的 `auto` 不可见，而安全的失败——多一次确认点击——是可见的。
3. `ToolRegistry.checkTicket()` 是唯一的执行闸口，放宽它等于让一次未经逐项批准的写入通过唯一的防线。

因此会话授权的判断依据改为 `decision.tier`（环境升级后的最终风险）。代价是：在生产或未标注环境上，普通写入不再能通过「批准本会话」免除确认，每次都重新询问。这与「生产写入应当有摩擦」的设计意图一致。

**已知缺口**

- 无（上述冲突已收敛）。

## Alternatives considered

- **每个工具自行判断是否允许执行。** 规则会被复制到每个工具里，策略变更需要改 N 处，且无法给出统一解释。否决。
- **由 Provider 或模型声明风险等级。** 模型输出是最不可信的输入，用它决定自己的权限等于没有权限。否决。
- **只按目标环境做策略、不做命令分析。** 会漏掉「同一条只读工具被塞进破坏性命令」的情况；命令分析虽然会误报（一次误报的代价是一次确认点击），但漏报的代价是生产事故。否决。
- **把审批结果做成全局开关（例如「本次运行全部允许」）。** 会让一次同意覆盖它没有涵盖的操作。取而代之的是绑定工具与目标的会话授权，以及逐项批准。否决。
