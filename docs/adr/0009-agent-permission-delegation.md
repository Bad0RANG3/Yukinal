# ADR 0009 Agent 权限采用显式运行级委托

Status: Accepted
Date: 2026-09-09

## Context

仅按目标环境策略执行时，模型会遇到两种截然不同的使用方式，而策略表只能服务其中一种：

- 有人在**逐项审查**一次变更。此时任何写入都应该停下来等他看一眼，即使用目标环境是开发环境、即使策略认为写入可以自动执行。
- 有人**委托了一项明确的任务**（「把这个容器重启一下，确认健康后再看日志」）。此时反复弹出确认框并不会提高安全性——用户已经在运行开始前表达过授权意图——只会让人习惯性地点「批准」，反而降低警觉。

这两种需求无法用同一档策略表达。放开自动执行又带来一个新的安全问题：**模型输出不能等于授权**。如果模型在文本里说「用户已经同意」，协议里必须有东西能证明这句话是假的。系统需要区分三种自动执行的理由——策略允许、用户逐项批准、用户委托 Agent 自主判断——否则活动记录无法说明责任落在谁身上。

## Decision

每次 Agent 运行可以在请求里带上一个用户选择的委托模式：

| `permissionMode` | 行为 |
| --- | --- |
| `ask` | 只读操作自动执行；写入、部署、重启和危险操作在执行前等待用户批准，即使策略表允许自动执行。 |
| `auto` | 用户明确委托 Agent 在**开发或预发布**目标上批准 `write` 档位的操作。高危与 critical、本机、未知和生产操作仍需逐项人工批准；策略拒绝仍然拒绝。 |
| 省略 | 保持「只按环境策略执行」的行为，契约保持向后兼容。 |

委托**不是**一个新的授权入口。`auto` 只是让 Permission Engine 在既有策略之上做一次收窄判断：只有当档位是 `write`、且目标环境是 `development` 或 `staging`、且策略本身没有拒绝时，结果才会变成 `auto`，并且**来源被标记为 `agent`**。其余情况一律回落到 `ask`。

**同时引入了第二个正交的轴：运行模式。** `mode` 决定这次运行**能改到什么程度**（`goal` 不限制、`plan` 只调查并给计划、`readonly` 只看不改），`permissionMode` 决定**允许的部分由谁点头**。两者独立：`plan` + `auto` 是合法组合，表示「只做计划，计划里允许的部分不用再问我」。`plan` 与 `readonly` 下的非读操作由 Permission Engine 直接 `deny`，而且这个判断发生在策略、委托和会话授权之前——限制是被执行的，不是被请求的，模型无视指令也无法写入。

两种模式的区分会体现在审计里，而不是只体现在提示词里：

- Permission Engine 生成带 `approvedBy` 的决策，取值 `policy`、`agent` 或 `user`。
- agent loop 依据来源生成不同类型的执行票据：`policy_auto`、`agent_auto` 或 `session_auto`（逐项批准则是 `user_approved`）。
- ToolRegistry 会复核票据与决策是否自洽。对 `agent_auto` 额外要求：档位必须是 `write`、目标环境必须是开发或预发布；对 `policy_auto` 要求来源必须是 `policy`；对 `session_auto` 要求来源必须是 `user`。模型伪造的票据会在这里被拒。
- SQLite 的 `tool_executions.approved_by` 允许值从 `('user','policy')` 扩展为 `('user','policy','agent')`，通过一次表重建迁移完成，并保留已有数据。

界面把两轴分开呈现，并随每次运行发送：默认值是「请求批准」+「目标模式」（`agentPermissionMode: "ask"`、`agentRunMode: "goal"`）。Rust 只做转发，不解释这两个字段的含义——语义由 sidecar 的权限引擎拥有，这样两侧不会各自演化出一套理解。

## Consequences

**收益**

- 用户可以在每次运行前明确选择「逐项确认」或「委托 Agent 自动批准」，并且在活动记录里看到这次操作究竟是谁批准的。
- Agent 可以连续完成已委托的开发或预发布写入任务，而每一项自动执行的操作都会标为「Agent 自主批准」，并保留风险、目标与结果。
- 责任来源可审计：`policy`、`agent`、`user` 三种自动批准在数据库里可区分，事后统计「有多少操作是模型自主决定的」变成一个查询。
- 运行模式给了用户一个比提示词更强的约束手段：`readonly` 下的写入是硬拒绝，可以用来安全地做一次纯调查。

**成本**

- 需要维护票据与决策两套结构的自洽性，任何一侧新增取值都要同步更新校验逻辑与迁移。
- 两个轴增加了界面与文档的复杂度。这个代价是必要的：把它们合并成一个「权限等级」会让「只读 + 自动批准」这种组合无法表达。
- 自动委托的边界是硬编码在权限引擎里的（`write` 档位 + 开发/预发布）。放宽它需要一条新的 ADR，而不是一次配置改动——这是有意的防误改设计。
- 会话授权的作用域需要 agent loop 主动维护：引擎命中的授权集合会一直存在到进程退出，因此 loop 在没有运行在飞时清空它。会话授权永远不覆盖 dangerous 档位——包括被环境升级到该档位的普通写入——那里必须逐项批准；收敛过程见 [ADR 0005](0005-permission-engine-sole-decision-maker.md)。
- 运行模式与委托模式都会随运行进入协议，因此旧的客户端省略字段时必须仍然按环境策略工作；契约把两者都定义为可选字段，正是为了这一点。

## Alternatives considered

- **只提供「本次运行全部允许」的总开关。** 会让一次同意覆盖它并未涵盖的操作，尤其在目标环境判断出错时后果放大。否决。
- **把委托做成持久化的用户偏好（例如「以后自动批准开发环境写入」）。** 会让授权脱离具体任务与具体目标，而本项目的整条审计链都建立在「这次是谁批准的」之上。否决。
- **让模型在工具调用里声明「用户已授权」。** 模型输出是最不可信的输入，用它决定自己的权限等于没有权限。否决。
- **用提示词请求模型遵守只读。** 提示词不是执行机制：模型忽略指令时不会有任何东西阻止写入。只读限制因此被实现在权限引擎里。否决。
