# Yukinal 2.1.0

2026-11-27 正式发行。应用版本统一为 `2.1.0`；Python Agent 继续独立使用 `0.1.0`。

## 本版主题

本版来自一次完整的实机 E2E 回归：真实 Provider、真实 SSH 目标，从创建目标任务开始，
经证据采集、方案发布、用户选择、行动执行，一路跑到计划验证完成。回归过程中暴露的缺陷
全部修复，其中最关键的一类问题是**计划结算链路断在几处看不见的地方**——每一步单独看都
"实现"了，串起来却走不通。

## 本版变化

### 免审批固定读有了自己的通道

`system.swap`、`filesystem.inodes`、`filesystem.mounts`、`system.time`、
`filesystem.exists` 五个固定读工具此前借道 `server.exec` 实现，于是被审批门禁和
"`server.exec` 只能出现在 action 步骤"的规则双重拒绝：健康检查既跑不通，也永远无法在
证据步骤里结算。现在它们走新增的 `read_probe` SSH 操作，命令文本来自共享工具目录
（同一份 `toolkit_catalog.json` 编译进 C++ 与 Python），模型不提供任何 shell 文本。
`server.exec` 的审批要求与 action-only 规则没有任何放松。

路径前缀白名单的边界也修了：`/var/log/` 这类以斜杠结尾的前缀现在包含目录本身，
此前 `/var/log` 会被 C++ 侧拒绝、而 Python 侧放行，两边规则不一致。

### 记录工具补全，决策摘要真正可用

host 侧的 `host.investigation.evidence/finding/brief/artifact.record` 早已实现且校验严格，
但没有任何 Python 工具能调用它们，也没有任何东西写入证据表。结果是决策摘要永远不存在，
"选方案 → 计划获批 → 续跑执行"这条路在 UI 上完全不可达。本版补齐四个只读记录工具，
并让 host 在调用方未提供 `contentHash` 时自行认证写入。

### 计划上下文与执行时间线

- 新增 `autonomous_task_plan_context`：证据/决策/验证步骤续跑时也会把
  `{planId, planStepId, evidenceIds}` 交给 Agent。行动绑定仍然只给 action 步骤，
  这不是授权，只是"这一轮你在做哪一步"的陈述。
- `investigation_steps` 此前全库没有 INSERT，任务详情的执行时间线永远是空的。现在步骤
  开始时建行、结算时写结果；结算不会覆盖开始时记录的工具名与输入。

### 失败语义不再有死路

`goal_blocked`、`goal_no_progress`、`goal_review_invalid_evidence`、
`goal_review_failed`、`confirmation_turn_required`、`plan_step_settlement_failed`
此前都落到 `unknown`，而 `unknown` 只有"检查"和"停止"两个选项。现在它们各自映射到
重新规划的语义，操作者始终有前进路径。

更根本的一处：**发布决策摘要后不再被判为失败**。评审说 blocked、而本轮已经发布方案时，
run 以成功结束、任务停在 `waiting_user`，等用户选方案后由界面续跑。此前会直接把任务
置为终态，选择方案只会得到 `INVALID_STATE`。

### 计划可以真正完成

`waiting_user` 现在允许流转到 `completed`/`failed`。计划最后一步验证结算时，任务通常正
停在 `waiting_user`（run 完成不会替用户宣布任务完成），缺这条边则完全验证通过的计划永远
无法收尾。任务完成时 phase 一并落到 `completed`。

### 审批票据

任务绑定的行动审批现在带上**当前**计划步骤。此前只认 run 启动时捕获的绑定，而首次启动时
计划还不存在，于是审批事件缺 `planId`/`planStepId`，host 拒绝铸票，用户点批准只会得到
`AGENT_APPROVAL_UNKNOWN`——一个任何答复都无法兑现的提示。同时，尚无计划步骤时的
`server.exec` 不再弹出审批，而是回给模型一条可自纠的说明。

### Agent 韧性

- 工具调用预算不再挂在计划步数上。一步通常要"读取、记录证据、引用"三次调用，25 步的
  任务在 23 次调用时以 `tool_call_limit_exceeded` 崩掉，已结算的步骤全部作废。
- 参数不是合法 JSON 的工具调用、以及本地 schema 校验拒绝，都会回给模型自纠（有次数上限），
  兄弟调用照常执行。此前批量调用里只要一个参数不合格，整个 durable run 直接失败。
- 证据的 `contentType` 由产品自行推导，不再要求模型在两个枚举值里二选一。
- 自动批准模式下，一次变更之后的确认轮在成功读取一次后即关闭。此前它只在 run 结束时关闭，
  导致后续每次验证读都被当成新的变更提议，三次拒绝后杀死一个没有任何过错的 run。

### 界面与 Provider

- 任务仍持有活动运行时选择方案不再直接报 `INVALID_STATE`，而是延后启动并提示
  "当前运行仍在进行，结束后会自动继续"。
- 新增 favicon，加载不再 404。
- 真实网关返回 `{"data","object","success"}` 时不再被白名单拒绝；此前聊天可用但
  "获取模型"永远失败。

## 验收

本次验收使用真实 Provider 与一台真实 Linux 服务器，通过驱动原生宿主的 IPC 完成：

- 目标任务从创建到计划 `completed`、任务 `completed`：5 步计划（证据、行动、决策、行动、
  验证）全部 `succeeded`，10 条证据、3 条结论、9 个工件，`waiting_approval` × 5 全部
  经 `agent_approval_respond` 通过并真实执行。
- 免审批固定读在审计里显示 `approval_status: not_required`，全部成功。
- 发布决策摘要 → 用户选择保守方案 → 计划获批 → 界面续跑 → 执行 → 验证，全链路走通。
- `filesystem.list`/`filesystem.read` 在 `sftpAllowedRoots` 之外仍被正确拒绝
  （`denied_by_policy`），这是设计意图，不是回归。

门禁：CTest 14/14、Python Agent 545 项（5 项跳过，均需外部环境）、桌面 661 项、
workspace 类型检查与生产构建通过。

## 限制

- 验收只使用一台真实服务器与一个 Provider，未覆盖真实多目标并行与长时间压力。
- 安装版 GUI 的人工验收仍未完成。
- 安装包未签名，macOS 应用未公证。
- 结构化 SSH 操作仍以只读与受审批的少量写操作为主；`sftpAllowedRoots` 之外的路径一律拒绝。

不要把上述证据扩展为未测组合均已通过。
